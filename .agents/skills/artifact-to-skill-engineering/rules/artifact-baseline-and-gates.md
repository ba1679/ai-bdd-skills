# Rule 1 - 主要 Example 與目標 Skill 必須可唯一辨識

- Level: `MUST`
- 主要 Example 是本次用來決定期望產物的基準；其他參考資料可補充背景，角色及優先順序須能區分。
- 已知資訊須足以辨識產物用途、主要來源、可編輯工作檔、目標 Skill 及本次要完成的範圍。使用者已指定的來源、位置及排除範圍優先。
- 外部或唯讀來源可保留為參考，在已授權位置建立工作版本；後續修改與確認都指向同一份主要工作檔，保留來源脈絡。
- 缺少的資訊會改變工作對象時才需要確認；檔名或版面等低影響細節可採專案慣例並說明。

## Good Example

- 工作對象、參考角色及目標位置都清楚。

```md
主要 Example：使用者提供的規格文件，工作版本為目標 Skill 的 spec.example.md。
其他參考：舊版需求表，只補充欄位背景。
目標：在本專案建立 specify，先修改 Example，再抽模板與開發 Skill。
使用者排除的同名版本不作為實作來源。
```

## Bad Example

- 多份參考資料未分主從，就開始建立不同產物。

```md
手邊有三份規格，選一份抽欄位、另一份抄章節。
目標 Skill 名稱還沒確定，就先建立兩套模板再讓使用者選。
```

# Rule 2 - 階段定位須根據完成證據

- Level: `MUST`
- 使用對話中的確認紀錄及目前檔案內容判斷階段；檔案存在、名稱含 final 或曾被稱為完成，均不足以取代成果核對。
- 每個階段的最低完成證據如下，從最早尚未成立的成果接續：

| 階段 | 完成證據 |
| --- | --- |
| 選定 Example | 主要基準、工作位置與目標 Skill 已明確。 |
| Example 定稿 | 使用者已認可目前版本，且沒有會改變產物設計的阻塞決策。 |
| Template 抽取 | 骨架與範例忠實對應已認可設計，且符合受委派 Skill 的完成要求。 |
| 目標 Skill 開發 | 實作已落地，必要模組已接入執行流程；只有工程提案時標示為提案成果。 |
| 成果驗證 | 有與目前設計及實作相符的檢查或測試紀錄，驗證範圍與未解事項可辨識。 |

- 可沿用仍有效的完成證據；使用者只要求其中一段或只要提案時，該請求可以完成，但須區分整條鏈路的完成程度。

## Good Example

- 已定稿的 Example 可沿用，模板抽取成為本輪起點。

```md
對話已確認 Example，檔案內容也未改變；目前尚無骨架。
本輪從 Template 抽取接續。
若使用者只要求 Skill 工程提案，交付後記為「提案完成，實作尚未開始」。
```

## Bad Example

- 以檔案數量代替階段證據。

```md
有 example.md、template.md 與 SKILL.md，所以整套 Skill 已驗證完成。
不必確認 Example 是否被認可，也不必檢查 SKILL.md 是否真的使用模板。
```

# Rule 3 - Example 修改以具體差異與高影響決策為界

- Level: `MUST`
- 修改須對應使用者的客製化要求，讓使用者能從工作檔看見結果；建議、未決事項與已採用內容須可區分。
- 改動會影響章節階層、欄位含義、必填或可選邊界、涵蓋範圍或生成方法時，須有已確認依據；仍有歧義才交給主 SOP 的 clarify 步驟。
- 已明確授權的調整可直接修改，低影響格式選擇可沿用既有慣例；不把每次文字修訂都變成新的澄清循環。
- 澄清過程沿用目前任務的已確認答案與停止狀態；非規格類產物透過需求模式收斂決策，檔案語法由適用的編輯工具維持。

## Good Example

- 先辨識真正會改變結構的決策，再修改工作檔。

```md
使用者希望 FR 與 NFR 放在 US 底下。
已明確的部分：將需求按主要 US 分組。
需確認的差異：共享需求要在主要 US 定義後引用，還是全部移至全域。
取得答案後修改同一份 Example，回報結構與引用方式的改變。
```

## Bad Example

- 將有多種合理解釋的結構改動直接視為使用者選擇。

```md
使用者希望分組更清楚，所以自行新增三層分類與一套需求矩陣。
順便抽出模板，之後再問使用者是否喜歡這個格式。
```

# Rule 4 - Example 認可須對應目前版本與完整設計

- Level: `MUST`
- 認可須能對應到目前 Example 的內容與版本；可以來自明確表示滿意，或指示以目前版本抽取模板、開發目標 Skill。
- 對單一問題的選項回答、局部修訂的同意或沉默，不自動代表整份產物已定稿。
- 對同一未變動版本的有效認可持續適用，無須重複索取；使用者已指示後續階段時，將該指示一併作為本次授權範圍的證據。

## Good Example

- 清楚區分局部決策與對整份產物的認可。

```md
「共享需求選 A」：確認需求歸屬規則，修改後仍需確認 Example 整體。
「這份 Example 可以，照這版抽 Template」：目前版本已認可，可進入抽取。
同一版本未再修改時，後續委派沿用這次認可。
```

## Bad Example

- 以局部回答或時間經過推定定稿。

```md
使用者回答一個欄位問題後沒有再回覆，因此視為整份 Example 滿意。
每進入一個後續步驟，又要求使用者重新核准同一份未變動的 Example。
```

# Rule 5 - 後續變更須回查最早受影響成果

- Level: `MUST`
- Example、Template 與目標 Skill 須指向同一版設計；上游改動後，先判斷影響，保留仍有效的內容與認可。
- 僅更正案例資料而結構與語意不變時，核對範例及相關測試的預期結果；不必因此重建所有檔案。
- 欄位、階層、必要性或語意改變時，回查 Example 認可、雙檔及生成判準；原來的定稿證據只覆蓋未受影響部分。
- 模板抽取錯誤須與產物設計改變區分：前者依原定稿修正抽取，後者需要先收斂新的產物設計。

## Good Example

- 只重做失效的成果與檢查。

```md
Example 更正一筆示範金額：更新範例與對應驗證資料，骨架結構仍可沿用。
Example 將必填欄位改為依條件出現：確認新語意，更新雙檔，並回查生成規則與驗證案例。
```

## Bad Example

- 下游仍沿用已失效的設計。

```md
Example 已改為新的需求階層，但模板仍保留舊章節。
目標 Skill 已有 SKILL.md，所以不再回查它生成的結構。
```

# Rule 6 - 外部能力的重用與客製化須保留來源

- Level: `MUST`
- 需要外部 Skill 或產物時，先確認其能力與環境是否適合本次用途；新增依賴或安裝須符合使用者授權及專案範圍。
- 複製或客製外部內容時，保留適用授權、原著作權聲明、來源位置與版本，並標明本地調整；授權或使用限制不明時先釐清可用範圍。
- 客製版本須有明確名稱及入口，依賴方須指向實際採用的版本，避免官方與本地版本的職責混淆。

## Good Example

- 客製版本與上游來源都可追溯。

```md
官方澄清流程依賴原專案環境，因此在授權範圍內建立專案版 clarify。
保留上游內容、來源版本及授權聲明，說明路徑與產物結構的本地對應。
目標 Skill 明確呼叫專案版入口。
```

## Bad Example

- 改名後失去來源與授權資訊。

```md
複製外部 Skill，改成自己的名稱並移除原作者、來源與授權檔。
依賴方仍呼叫舊名稱，實際執行哪一版也未確認。
```
