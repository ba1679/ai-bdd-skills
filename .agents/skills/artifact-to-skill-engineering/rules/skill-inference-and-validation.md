# Rule 1 - 模板雙檔須足以重現已認可的產物設計

- Level: `MUST`
- 雙檔的格式、命名與填位符號規範由 skill-form-template 負責；本流程核對它們與已認可 Example 的語意一致性。
- 骨架須保留穩定結構、固定語法、欄位關係及必要的條件分支；可變內容須可依新輸入改寫，不能把個案角色、數值或項目數量固化為通用要求。
- 範例須是具體且完整的對照成品。使用骨架並依其提示重複或省略適用區塊，應能表達該範例的主要結構與語意。
- 產物格式及使用者指定的命名持續有效；雙檔仍含需要重新決定的設計問題時，尚不足以作為目標 Skill 的穩定輸出契約。

## Good Example

- 保留產物設計，數量與個案內容可隨輸入改變。

```md
Example：八個 US，各自包含驗收、FR 與適用的 NFR，並引用共享需求。
骨架：一組可重複的 US 區塊，保留需求分組與引用欄位。
對照結果：填入已確認案例後，可表達 Example 的八個故事；新案例可以只有兩個故事。
```

## Bad Example

- 檔名成對，但語意無法對照。

```md
骨架固定八個故事與三種角色。
Example 已將 FR 放入 US，骨架卻仍將所有 FR 放在頂層。
範例內容只是另一份尚未替換的填位符號。
```

# Rule 2 - Skill 反推須交付輸入與期望產物之間的差距

- Level: `MUST`
- 交接資料須包含目標 Skill、已認可 Example、骨架與範例位置、代表性 Input Prompt、本次授權範圍及影響生成的已確認約束。
- 代表性輸入須反映預期使用情境。可從 Artifact 整理測試用輸入，但須標明它是測試案例，不能冒充使用者原始需求或已確認的產品決策。
- 須區分 Prompt 已提供的資訊、可以推導的必要條件，以及依賴背景或澄清才能取得的資訊，讓 skill-engineering 設計取得及轉換資訊的方法。
- 交接的目標是產出符合契約的 Artifact，能力不以範例的篇幅、項目數或逐字相同程度判定。

## Good Example

- 將缺少的決策明確交給生成流程處理。

```md
輸入案例：要有人資角色、行政登記請假、負責人審核與員工看薪資。
期望產物：符合已認可模板的功能規格。
已知差距：審核對象、薪資來源與公司政策尚未由這句輸入決定。
工程目標：設計需求推導與必要澄清，再組裝規格；不從範例自行複製政策。
```

## Bad Example

- 只有產物外觀，缺少輸入與生成工作的對應。

```md
交給 skill-engineering：「照這份長篇範例寫一個 Skill，最後內容要一模一樣。」
不提供使用者會輸入什麼，也不區分哪些內容需要補問。
```

# Rule 3 - 專職委派須實際執行並保留授權範圍

- Level: `MUST`
- 依目前可用的 Skill 目錄定位並讀取受委派 Skill，再依其工作流程執行與接回結果；只輸出命令名稱或表示將委派，不算完成委派。
- 使用者已確認的目標、版本與授權須一併傳遞；只要求工程提案時，交付提案並保留實作閘門，已有有效實作授權時沿用。
- 受委派 Skill 負責其專業判準，本流程核對交接結果；格式與提問細節不在本流程另立平行版本。
- 必要依賴無法取得時，回報實際缺少的 Skill 或資源及其影響，不將未執行的步驟標示完成。

## Good Example

- 委派有實際輸入、執行及可檢查的結果。

```md
讀取可用的 skill-form-template，傳入已認可 Example、目錄與指定檔名。
依其流程完成雙檔並核對結果，再將實際檔案位置交給 skill-engineering。
工程任務若只要求提案，回報「提案完成，等待使用者決定是否實作」。
```

## Bad Example

- 命令文字被當成已執行，且超過使用者指定範圍。

```md
回覆「/skill-form-template」，然後宣稱模板已建立。
使用者只要求理解與提案，就直接修改目標 Skill。
```

# Rule 4 - 最小 SOP 與必要判準須同時成立

- Level: `MUST`
- 由 skill-engineering 決定控制平面與模組編排，本流程須交付「先有最小 SOP、再按需要展開模組」的設計約束。
- 需要穩定判斷才能達成產物品質的內容，須在工程結果中有足夠的承載位置。反覆會出錯的分類、邊界、例外及取捨，不能只縮成「完整分析」等抽象指示。
- Rules 須有實際讀取時機並足以指導判斷；固定輸出格式沿用模板，適合機械處理的重複工作才考慮 scripts。
- 避免過度工程以模組是否有具體用途判斷，不以規則檔越少越好判斷；亦不預設每個目標 Skill 都需要相同的模組數量。

## Good Example

- 將已識別的品質判斷放到可執行的位置。

```md
先建立從輸入、澄清、需求推導到產物檢查的 SOP。
若故事拆分會影響產物品質，展開判準與正反例，並在拆分步驟載入。
機械檢查是否需要 script，依重複工作及驗證效益決定。
```

## Bad Example

- 精簡流程時也刪掉維持品質所需的判斷資訊。

```md
THINK：完整理解並產出高品質規格。
因為不要過度工程，所以不展開已經發現難以穩定執行的核心判準。
```

# Rule 5 - 驗證須區分結構檢查與實際生成能力

- Level: `MUST`
- 檔案、引用與格式檢查可證明結構有效；目標 Skill 的生成能力須由代表性輸入與實際結果核對。
- 依目標能力選擇案例：資訊充分時能依契約生成；存在關鍵歧義時能收斂或保留待確認狀態；宣稱跨案例可重用時，須檢視不同內容或較小需求的表現。
- 已有範圍或模組變更時，核對受影響的案例及產物；保留對應的輸入、所用版本、實際結果與未解事項，可沿用受委派 Skill 的驗證紀錄。
- 報告須區分靜態檢查、桌面流程演練與實際產物測試，僅聲稱實際執行的驗證；只有提案、檔案存在或模擬預期結果時，不能宣稱已證明可靠生成。

## Good Example

- 可辨識實際做到的驗證及尚未證明的範圍。

```md
已完成：Skill 格式與引用檢查。
已完成：以資訊充分的輸入實際產生一份 Artifact，核對章節、內容依據與引用。
已做桌面演練：遇到審核對象不明時的澄清分支。
尚未實測：多輪使用者回答後的完整生成流程。
```

## Bad Example

- 將檔案存在或自行列出的預期當成生成證據。

```md
SKILL.md 與模板都在，所有連結都能開啟，所以可靠生成驗證通過。
只寫出三個測試的預期行為，卻回報「三類案例實測全部通過」。
```
