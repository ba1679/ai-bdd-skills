# 產物憲法

由產品專案維護適用於 SDD 產物的要求與通過判準。一次可以完成一條規則，後續再依需要補充。

# SOP

## Phase 1 -- 定位專案與本輪產物

1. READ 從使用者指定位置或目前專案定位目標 repo，讀取需求及已確認決策。讀取該 repo 的 `constitution/README.md`、適用的 `constitution/shared/rules.md`，以及索引中對應本輪產物或明顯重疊的 `rules.md`。
2. READ 索引缺少對應項目或主責不明時，查閱相關 skill 的 `SKILL.md` 與專案交接文件，找出實際產物、寫入主責及適用的下游驗證者。已有明確對應時直接沿用。
3. THINK 跨多種產物且適用條件、必要結果相同的要求，放在 `shared/` 並列明範圍。單一產物及其下游實作共用的契約，沿用該產物的既有模組。首次建立且歸屬明確時，以產物命名模組。模組歸屬或適用 skill 仍不明時，列入 Phase 2 的待確認事項。若需求在指定流程、測試順序、skill 調度或審查方式，先確認使用者希望產物呈現的結果。若只有流程需求，回報適合承接的流程位置。

## Phase 2 -- 逐題釐清並累積已確認規則

1. THINK 先從現行契約、使用者輸入和已接受答案確定每條規則的模組、適用 skill、產物與情況、必要結果及通過判準。依既有約定決定 ID、標題、索引列與檢查表示方式。
2. THINK 找出已確認且尚待寫入的獨立規則。使用者已授權寫檔時，先進入 Phase 3 寫入這批規則，仍有待定規則時回到本 phase。若使用者只要求提案，將已確認內容保存在對話中並交付候選規則。
3. DELEGATE 若仍有會影響模組歸屬、適用 skill、規則內容或驗證的決策，呼叫 [$clarify](../clarify/SKILL.md) 的需求模式，交付候選規則、已查來源、已確認決策與同一份澄清狀態，向開發者逐題確認。答案保存在本輪工作狀態，由本 skill 寫入憲法。接回答案後從本 phase 第 1 步重新判定可寫入範圍。資訊足夠時直接交付。若停止提問或用盡額度，回報已交付的增量與待確認規則。

## Phase 3 -- 寫入並驗證本輪增量

1. WRITE 正式規則寫入 `constitution/<產物模組>/rules.md`，共用規則寫入 `constitution/shared/rules.md`。每條規則具備穩定 ID、標題、適用範圍、必要結果與通過證據。例外與覆寫只在影響結果時列出。要改寫 skill 預設時，讀取該 skill 已公開的可覆寫項目，並在規則指名該項目。有衝突時暫緩受影響的規則，指出原因。
2. WRITE 只增修本輪已確認的規則，保留未受影響的文字與既有 ID。若本輪寫入的模組尚未登記或對應有變，建立或更新 `constitution/README.md` 的相關項目，列出規則入口連結、對應產物及寫入主責，需要時加上下游驗證者。只有附檔具備獨立引用或驗證用途時才新增，並由規則明列連結。
3. READ 檢查本輪差異。確認每條新編 ID 唯一、相關索引與附件連結可解析、適用範圍和通過判準可以判定，且同一要求只留一份定義。若更新會影響已有契約或證據，指出需重驗的產物及範圍。
4. WRITE 回報實際新增或更新的檔案、已寫入的規則 ID，以及仍待決定的項目。寫入範圍以憲法索引、規則及必要依賴為限。既有 SDD skill、流程與產品產物的接入另依需求處理。

## 憲法套用約定

各 SDD skill 直接讀本節，在各自的來源讀取、驗證及交接步驟套用。憲法規則由目標專案維護。

- **載入範圍**　各 SOP 的 `constitution/` 路徑皆相對於目標 repo 根目錄。先讀 `constitution/README.md`，再讀 SOP 點名且適用的規則檔，以及規則明列且本輪需要的附件。同一產物若在索引登記其他路徑，讀索引指向的檔案。若索引存在且未登記該產物，SOP 點名的預設檔存在時可直接讀取。未導入憲法或適用產物沒有模組時沿用 skill 預設。若目標 repo 已有規則但缺索引，或適用的已登記模組、必要附件讀不到，記錄受影響產物的驗證缺口。
- **覆寫優先權**　憲法可加上適用的產物要求。需要覆寫時，先查閱對應 skill 公開的可覆寫項目，憲法明列該項目才優先於對應的 skill 規則、模板與範例預設。所有 SDD skill 都開放 `artifact-language`，涵蓋憲法適用範圍內供人閱讀的產物敘述，其他項目由各 skill 明列。保留格式所需的識別字、語法和下游交換契約。遇到未開放項目、已確認需求或其他憲法規則的衝突，指出各來源及受影響範圍，交回主責或開發者確認。憲法作用於產物要求，流程與委派照各 skill 的 SOP。
- **版本與重驗**　每次啟動讀取現行規則。交接保留規則入口及可定位的版本，可用 Git commit 或所用規則與相關附件的內容摘要值。受委派者以同一目標 repo 查核交接版本。若現行版本不同、上游結果缺少可定位的版本或證據，或相關規則在本輪變動，判定哪些產物定位與證據受影響，只重驗需要承接的範圍。上游產物需要修正時交回原主責。
- **判定就緒**　依規則的通過證據檢查實際產物，分別記錄通過、違規、未驗證及不適用的原因。必守規則違規、未驗證或適用來源無法取得時，受影響產物可保留草稿，依賴該部分的工作須等它就緒。文件、原型與真實執行結果各自判定。只以本階段應有的證據判定本階段產物，仍需下游驗證的條件依其實際責任交接。
- **交接紀錄**　在既有交付、清單、Plan、Tasks 或驗證紀錄留下規則 ID 與入口、規則版本、產物定位、實際結果與證據，以及仍須下游確認的事項。可共用同一份證據並以連結引用。獨立執行且無既有紀錄位置時，在回傳結果交接。
