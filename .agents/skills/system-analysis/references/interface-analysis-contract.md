# 界面分析共同交接契約

本契約供 `system-analysis` 與三個 Planner 共用。Planner 可直接讀取本檔並獨立工作，無須先執行主 skill；主責領域的判斷與產物細節留在各 Planner。

## 單次任務與輸入

一次任務對應一個端點界面及其「界面名稱＋分析」工作，不因同屬一個 Planner 而合併。跨端點同名時，在名稱補上端點或用途。

啟動前確認下列資訊；可以從已提供來源補齊，不要求使用者重複填表：

| 輸入 | 需要確認的內容 |
| --- | --- |
| 任務範圍 | 界面、所屬端點、分析目的、主責 Planner 與本次不處理的相鄰責任。 |
| 已有依據 | 實際可讀的需求、研究、技術棧、現況及共同約束；明確區分已有決策、規劃方向及未知。 |
| 必要前置輸入 | 具體需要的內容、來源檔案與段落、來源目前狀態；不能只給「參考上一波」或尚未取得的產物名稱。 |
| 交付位置與用途 | 本次輸出檔與格式、需要交給哪些後續工作及其必要結果。 |
| 限制與回饋 | 已知缺口、外部文件、影響範圍、需要回報主流程的依賴變更或需求衝突。 |

獨立呼叫時，由目前需求與可用文件收斂同一組資訊；沒有 `plan.md` 或完整研究文件仍可分析。只有缺少會影響分析正確性的必要資訊時，才提出最少必要問題或交回待補事項。單純規劃中的技術決策應在領域內分析，不把所有設計選擇都升級成使用者提問；角色、業務規則或範圍無法確認時，交由 `/clarify` 收斂。

## 輸出位置與寫入責任

- 使用者或主流程指定的路徑與大小寫優先；更新既有產物時沿用原路徑及仍有效內容。
- 未指定時，在本次 `plan.md` 同目錄的 `analysis/` 輸出；沒有計畫則採 `spec.md` 同目錄。只有需求輸入時沿用已確認的專案文件慣例，無法定位才詢問。
- 依主責與界面性質交付可直接使用的檔案：UI／UX 為 `<界面名稱>.md`；HTTP API 為 `<界面名稱>.openapi.yaml`；非 HTTP 服務或環境維運為 `<界面名稱>.yaml`；資料分析為 `<界面名稱>.dbml`。API／Data 不另交 Markdown companion。
- HTTP 的路徑、操作、請求、回覆及安全定義集中在 OpenAPI；必要來源、分析狀態、環境維運與交接使用 `x-analysis` 擴充欄位，相關對外行為寫在對應 description。非 HTTP 分支使用結構化分析 YAML，不宣告為 OpenAPI，也不虛構路由。
- 資料表、欄位、型別、鍵、關聯及約束集中在 DBML；分析摘要、來源、未決事項與交接放在 Project Note，資料操作、交易、權限與生命週期等補充放在適當的 Project／Table／column Notes。同一內容在最適合的位置維護，不另複製一份結構表。
- 非關聯式資料不為 DBML 虛構資料表或外鍵；可用 Project Note 記錄 DBML 結構不適用的原因、已確認模型與可用來源，必要原生模型另列交接需求。
- 檔名保留可辨識界面名稱；跨端點同名時加入端點或用途，處理路徑分隔符等不適合檔名的字元，並在計畫記錄最終路徑。啟動前核對不同工作不會寫入相同檔案。
- 每個 Planner 只寫本次被分配的界面產物，回報需要協調的其他修改；`plan.md`、主責分配、依賴與整體狀態由 `system-analysis` 統一更新。獨立呼叫時回報結果供之後整合，不自行改其他工作。
- 產物使用繁體中文，保留必要的程式識別字與專有名詞。移除填位符號與填寫提示；不適用內容寫明原因或依樣板用途精簡。

## 每份分析產物的共同內容

各 Planner 的骨架與範例承擔格式；內容至少能追蹤以下資訊，API 置於 YAML 的 `x-analysis`，Data 以 Project Note 的可辨認標籤表達，UI／UX 沿用其文件結構：

- 任務摘要：界面、端點、主責 Planner、狀態與實際輸入來源。
- 分析範圍、已有約束、責任內的具體設計與其需求或來源依據，以及適用的格式與解析檢查結果。
- 下游交接：接收工作、可用結果、產物內位置、限制或狀態，以及需要對方回饋的事項；API 可引用 operationId／component，Data 可引用 DBML 物件與 Note 標籤，沒有下游時說明直接用途。
- 未決事項：缺少內容、影響、是否阻塞本次或後續哪項工作、取得方式；非阻塞未知也保留。
- 完成檢查：本次範圍與必要交接是否齊備、來源或契約是否有衝突，以及尚待實作驗證的情境。

預期服務契約、資料欄位或產品規則尚未獲來源支持時，清楚標為設計提案或待確認，不能以其他 Planner「將會決定」取代可用前置輸入。分析產物可規劃驗證方法與預期結果，不宣稱未執行的測試、部署或服務配置已成功。

## 工作狀態與可用性

| 狀態 | 判定與可承接範圍 |
| --- | --- |
| 待執行 | 任務已列入計畫，尚未啟動；預期結果不能視為已有依據。 |
| 分析中 | Planner 正在執行；尚未回收驗收的結果不能供依賴工作當成定案。 |
| 待補輸入 | 必要資訊、外部文件、產品決策或執行能力尚未取得；列明缺口與受影響結果。 |
| 待修正 | 產物不足、跨界面衝突，或來源變更已使既有結果需要重新檢查。 |
| 已完成 | 本界面必要分析及交接通過完成檢查；保留的非阻塞未知有明確影響範圍。這表示文件完成，不表示軟體已實作或驗證通過。 |
| 不適用 | 已確認本次不涉及此工作，記錄理由並解除相關失效依賴。不能用來掩蓋缺少輸入。 |

Planner 回報其完成檢查結果，主流程讀取實際產物及其分析資訊並驗收後才更新工作紀錄；需要 OpenAPI 或 DBML 的任務，缺少結構、必要補充分析或兩者不一致時不能標已完成。個別產物整體待補時，只有經主流程確認可用且清楚界定的部分可以被其他工作承接；不能宣告該工作已完成或使用其未定部分。

## 回傳與接續

回傳界面工作名稱、實際產物路徑與格式、完成檢查結果、可用下游結果、未決事項與新發現的依賴。需要補做其他領域時，回報所需內容與理由，讓主流程調整工作及波段；Planner 不自行啟動跨領域委派或改寫他人產物。

產物可規劃程式、資料、託管或維運設計，實際實作與操作須由後續任務承接。完成現有分析範圍後回傳，不自動啟動開發或部署。
