# Rule 1 - 只以實際取得的來源建立規劃

- Level: `MUST`
- 可用來源包括使用者需求、規格、研究、技術棧、現況及既有成果，不要求湊齊文件才開始。
- 分開辨識：來源明定的需求／選型、由來源推導的規劃、尚未確認的產品或環境決策。前言只列實際讀取的來源；必要決策不足時記錄影響。
- 技術選型理由、版本及相容性結論沿用有效研究；本輪缺少研究時只界定問題與影響，不為填表另造比較結果、訪談或已完成驗證。
- 尚未執行的 Planner 工作及模板範例不是本案已確認依據；回收後可以記錄採用的結論及位置，保持它與原需求的來源差異。

## Good Example

- 只有使用者描述也能規劃，且保留未知。

```md
依本次需求整理離線盤點工具；已知在筆電登錄，規劃本機保存與操作恢復。
現有資料格式未取得，僅阻塞匯入設計，手動登錄仍可分析。
```

## Bad Example

- 把不存在的研究或範例當成已確認事實。

```md
未讀 research.md，仍宣稱已驗證套件相容性。
範例採用雲端登入，所以單機工具也必須採用它。
```

# Rule 2 - Plan 保留共同輪廓，領域細節交給其權威產物

- Level: `MUST`
- Plan 須能回答系統邊界與責任、核心流程、跨領域共同約束、目標目錄、主責與產物入口、必要依賴，以及未知的影響／接手時點。
- 邊界圖與責任表互補；模組責任不另複製一套相同表格。核心流程可用短文或必要流程圖，簡單順序不強制再畫圖。
- 共同約束只列多個產物必須維持的行為，交代影響與實際依據。例如可信身分、共享狀態權威、重送一致性、私密資料可見性；不把單一資料表欄位或畫面布局升為共同約束。
- 完整 DTO、資料欄位、交易／鎖定方法及畫面行為留在各主責產物。已知實作策略在 Plan 轉成須維持的結果與來源，不重述算法。
- 目標專案結構及粗略實作順序只到已確認的責任層級，不生成完整 tasks、測試案例、CI 或部署程序。時程、人力、預算及里程碑僅在本次要求且有實際依據時簡要記錄。

## Good Example

- 共同規則交代結果，細節可直接定位。

```md
共同約束：同步失敗或命令重送不得重複扣量；API 定義恢復語意，DBML Notes 定義原子性。
資料來源與依據：需求 FR-07、已確認研究 R02。
Plan 只連到 API 與模型，不複製所有錯誤碼、索引和畫面欄位。
```

## Bad Example

- 管理表及內部設計取代共同輪廓。

```md
Plan 完整複製 API requests/responses、資料欄位、五層工作追蹤及每個測試步驟。
共同約束只寫「用 row lock」，沒有說明需維持的結果。
```

# Rule 3 - 範圍與階段決定分析深度

- Level: `MUST`
- 核心分析先完成本輪操作的角色、狀態、資料及服務規則；保留影響可行性與安全的最低執行前提，例如 credential 持有者、公開／私密設定、跨來源授權與必要依賴。
- 公開發布、備份／復原演練、密鑰輪替、監測、限流與 CI 的詳細程序，依本輪實際交付需要展開。尚未決定時保留限制與接手時點，不自動建立多份維運分析。
- 延後詳細程序不能抹除資料一致性、秘密保護或公開啟用的必要限制。對重送窗、刪除／匿名化、restore 等可能改變現有契約的事項，記錄具體局部影響。
- 本次明確只要 Plan 時交付規劃及索引中的待執行項，不宣告領域成果已生成。完整分析則需讀回相關產物，必要 UI 原型亦須檢視。

## Good Example

- 記錄最低約束與何時補齊，不提前寫整份手冊。

```md
目前做本地核心分析：公開設定可進前端，服務密鑰留在 server。
receipt 保留與輪替相容性未決，列明會影響舊命令恢復；發布前完成設定與實測。
資料復原須保持狀態與 receipt 同時點，完整演練程序延至發布工作。
```

## Bad Example

- 過度前置或把延後等同完成。

```md
所有核心分析先完成正式告警／restore runbook，否則一律不能開始。
沒有正式 origin、授權或輪替驗證，但因維運延後而宣稱可公開啟用。
```

# Rule 4 - 更新沿用有效來源，只有阻塞決策需要提問

- Level: `MUST`
- 使用者指定位置與大小寫優先；未指定時沿用功能規格目錄的 Plan 及共同契約的預設位置，無法定位專案才詢問。
- 更新既有成果時保留仍有效內容，來源變動才回查實際受影響範圍；不建立平行 Plan，也不以模板抹除已認可決策。
- 缺口只有在無法合理形成邊界、責任或必要契約時才阻塞相關工作。明確範圍、業務或權限衝突須收斂；負責人、容量、日期、保存期等未定值不可自行補造。
- 非阻塞未知在 Plan 集中記錄影響、所需決策及處理時點，子產物只記局部影響。已確認答案持續有效，不因切換 Planner 再問一次。

## Good Example

- 尊重既有路徑及可繼續部分。

```md
使用者指定 docs/count/Plan.md，就更新該檔。
尖峰量未定：保留容量影響，繼續操作契約。
來源同時要求完全離線與每次即時驗證：先收斂這個衝突。
```

## Bad Example

- 多建一份計畫，或用未知停止全部工作。

```md
另建 plan.md 取代指定的 Plan.md，移除已認可離線範圍。
未定保存期直接填七天；缺所有資料欄位就停止全部分析。
```

# Rule 5 - 模板只固定形狀，內容與數量依本案調整

- Level: `SHOULD`
- 以繁體中文保留短而完整的輪廓，同一原則在最相關位置維護，其他地方引用或只補局部影響。
- 六個 Plan 主題可依本案省略不適用內容或合理合併；依據、分工、實際成果、必要依賴與未決影響仍須可辨認，不保留空表格、提示與未替換槽位。
- 不從範例複製角色、品牌、檔案數量、里程碑、驗證成功紀錄或既定產品政策。單端點也可合格，沒有的登入、背景工作、設備或公開 Demo 不因模板而加入。

## Good Example

- 小需求保持小，重要資訊仍在。

```md
單機計時工具：一張本機邊界圖、短流程、一項 UI 任務及 HTML/紀錄入口。
無服務與資料責任在索引說明不適用，不生成空 OpenAPI 或 DBML。
```

## Bad Example

- 固定套用 PVP 或較大系統的配置。

```md
每個系統都要雙人房、Supabase、五張資料表與四階段波段。
照抄範例的瀏覽器檢查成功，不實際開啟本案 HTML。
```
