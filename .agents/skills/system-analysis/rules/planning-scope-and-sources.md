# Rule 1 - 以實際來源區分已有依據、規劃方向與待定事項

- Level: `MUST`
- 規劃依據可以來自使用者輸入、已取得的 `spec.md`、`research.md`、`techstack.md`、現況資料與既有有效規劃；依本次實際可用來源取用，不要求湊齊所有文件。
- 前言與正文只能宣告實際讀取的來源。缺少規格或研究時，應改寫模板中「依規格／研究」等敘述，將必要缺口列為未決事項。
- 來源中的明確需求與既定選型屬於已有依據；由來源推導的系統分工及粗略安排須表達為規劃；尚無依據的決策標為待定。引用研究結論時，可以說明其對規劃的影響。
- 尚未執行的界面分析屬於未來工作，其預期輸出不能寫成已確認結論。不得補造文件、研究結果、訪談紀錄或已完成的驗證。

## Good Example

- 僅有需求輸入時，仍能提出有來源與狀態的規劃。

```md
依本次使用者需求，規劃離線盤點工具的系統輪廓與後續分析流程。
已知：需在筆電上離線登錄盤點結果。
規劃：先釐清操作界面及本機資料存取邊界。
待定：既有盤點資料的格式與承接範圍。
```

## Bad Example

- 未取得研究文件，卻將模板文字與未執行分析當成事實。

```md
依 spec.md、research.md 與 techstack.md，已確認資料模型及 API 契約。
採用範例中的資料庫，所有相容性均已驗證。
```

# Rule 2 - 以 Phase 1 初步規劃粒度交付系統輪廓

- Level: `MUST`
- 系統輪廓涵蓋有依據的系統邊界、主要模組責任與依賴、核心流程、後續分析的共同約束、大致專案結構、粗略交付順序及未決事項；後續分析規劃涵蓋分析對象、必要輸入、順序與平行安排。
- 需求、現況及既有研究支持的粗略架構方向與既定技術選型可以保留；只展開其對範圍、分工及後續分析的影響。已知實作策略須轉寫為分析須維持的前提並引用原來源；版本／工具清單與選型論證留在原來源，未確認配置列為未決事項。
- 「後續分析的共同約束」只收錄多個界面須共同遵守的已確認前提。每項須清楚表達共同前提、哪些後續分析須承接何種影響，以及支持該前提的實際來源；可引用需求、既有研究或已確認的使用者輸入，不要求另建文件。
- 本階段不新做技術研究、另行比較選型或為填滿架構表提出無據方案。需要補研究的部分，記錄問題與影響，留待相應工作處理。
- 資料欄位、完整 API spec、UI／UX 設計、交易或鎖定策略與詳細架構設計，交由主流程後續委派的 Planner 承接；形成規劃時只界定其分析工作與必要前置輸入，領域結論寫在各界面產物，不回填成初步規劃的既有依據。Planner 的內部方法由其自身 skill 決定。
- 交付時逐項核對共同前提、分析影響與來源；未能同時表達三者的內容須合併或移回適當位置。僅單一界面或無符合條件的前提時，可簡述無共同約束；單端點仍可能涵蓋多個界面，不以端點數量決定取捨。

## Good Example

- 規劃交代責任與待分析邊界，詳細設計仍待後續完成。

```md
操作端提供盤點與查詢；同步服務接收盤點結果並管理回傳狀態。
既有研究已選定關聯式資料庫，資料存取界面分析須承接離線同步需求。
待分析：同步服務契約、衝突處理與目標資料模型。
```

- 將已有研究中的並行策略轉為共同前提，說明各界面分析須承接的要求並保留來源。

```md
| 共同約束 | 對後續分析的影響 | 依據 |
| --- | --- | --- |
| 並行操作與請求重試須維持一致性 | 操作、服務及資料界面分析須維持同配對碼唯一有效房間、兩人上限與唯一勝者，失敗或重送不得部分或重複生效。 | FR-003、FR-007、FR-010、NFR-001、NFR-005；R02 |
```

## Bad Example

- 提前選定實作細節，並將其當成已完成的分析。

```md
本階段另比較三種同步框架並選出優勝方案。
已完成 POST /sync 的 request schema、資料表欄位及衝突鎖定流程。
同步畫面採三欄布局，子技能須依指定六步驟產出所有元件。
```

- 即使引用已有研究，照搬策略名稱仍未交代共同前提與分析影響。

```md
| 共同約束 | 對後續分析的影響 | 依據 |
| --- | --- | --- |
| 使用 partial unique index、row lock 與 receipt | 各界面直接沿用實作策略。 | R02 |
```

# Rule 3 - 尊重輸出位置與既有有效規劃

- Level: `MUST`
- 使用者指定的輸出路徑與檔名優先，包含大小寫；例如指定 `Plan.md` 時，不得另建 `plan.md`。
- 未指定輸出時，若已有本次規格檔，預設使用該規格同目錄的 `plan.md`；只有需求輸入時，沿用明確的專案文件慣例。仍無法定位目標專案或輸出位置時，才提出最少必要問題。
- 更新既有規劃時保留仍有效的來源、結論與安排；需求或來源變動影響端點、界面、前置輸入或交付順序時，須同步修正相關內容。
- 不把一次更新變成另一份平行規劃，也不以模板覆蓋使用者已確認的內容。

## Good Example

- 路徑與既有內容都承接本次上下文。

```md
使用者指定 docs/inventory/Plan.md：更新同一檔案。
保留仍有效的離線操作範圍；新增掃描器介面後，同步更新端點分類與分析波段。
```

## Bad Example

- 擅自更改輸出名稱並丟棄有效規劃。

```md
使用者指定 docs/inventory/Plan.md，仍另建 docs/inventory/plan.md。
直接複製模板，移除既有已確認的離線操作範圍。
```

# Rule 4 - 只讓真正阻塞規劃的決策成為提問閘門

- Level: `MUST`
- 只有需要使用者決定的重大範圍或責任問題，或無法依上下文消解的來源衝突，才在不能形成合理系統邊界或分析安排時提問。
- 提問應聚焦於會改變規劃的最少必要決策；使用者已明確確認的事項不重複詢問。
- 其他不足以阻塞規劃的缺口，寫明未知內容、規劃影響、待取得的結果及合理處理時點，繼續完成不受影響部分。
- 負責角色、承辦人、規模、預算或日期應按來源寫入；已有結論不沿用模板中的「未定」，沒有依據不補造負責人與期限。

## Good Example

- 將可延後事項與阻塞決策分開處理。

```md
可繼續：同步尖峰量尚未確認，列為容量分析輸入，不阻擋操作與同步界面規劃。
需確認：使用者要求完全離線，但既有規格要求每次操作即時連線驗證；須先確認實際使用限制。
```

## Bad Example

- 非阻塞缺口造成停工，真正衝突卻被猜測帶過。

```md
尚未取得每張資料表欄位，先停止所有規劃。
完全離線與即時連線驗證互相衝突，直接假設使用者接受全程連線。
```

# Rule 5 - 依實案精簡模板，保留人類可讀的共同輪廓

- Level: `SHOULD`
- 以繁體中文簡潔撰寫；一項原則在最適合的位置完整交代，其他段落只補充其局部影響，避免重述功能清單、研究論證與通用操作規則。
- 保留系統邊界圖、核心流程圖及大致專案目錄的表達方式，依本案需要增刪節點、分支與目錄，維持初步規劃粒度。
- 模組、角色、規模、MVP、交付順序及未決事項均依實際需求改寫；沒有登入、背景工作、審核發布或公開 Demo 需求時，不因範例包含這些能力而加入。
- 範例中的領域、技術品牌、項目數量與編號均非固定要求。既有需求引用及里程碑命名按專案慣例保留，不額外建立不必要的識別系統。
- 簡單案例可以只有單一端點、界面或波段；不為填滿模板而虛構分類、依賴或待定事項。

## Good Example

- 範例提供形狀，實際內容由需求決定。

```md
單機計時工具：保留一張使用者到本機應用的邊界圖與簡短啟停流程。
專案目錄只列應用與測試；後續僅安排使用者操作界面分析。
使用者已確認單人維護，直接寫入，不保留「人力待定」。
```

## Bad Example

- 將領域範例當成所有專案的固定規格。

```md
單機計時工具仍照搬其他系統的多角色、審核流程、雲端登入與背景任務。
固定套用範例的界面數、波段數與編號，空缺由推測補齊。
```
