# Rule 1 - 依需求盤點技術端點、角色及跨端點互動

- Level: `MUST`
- 技術端點是本次需求涉及、可界定互動邊界的應用、服務、設備或資料來源；不是 HTTP 路徑，也不要求能獨立部署。每個端點都視為獨立的後續分析對象。
- 依實際需求掃描下列候選，不把候選清單當固定分類或必要數量；需求涉及其他類型時也須納入：
  - Frontend：前端應用程式及使用者操作入口。
  - Backend：後端服務、API 與必要的背景執行能力。
  - Database：資料庫、資料儲存與既有資料來源。
  - Mobile：原生或其他手機應用程式；若只有手機瀏覽 Web，依實際邊界納入 Web。
  - Hardware：感測器、讀取器、控制器或其他硬體設備。
  - Cloud：雲端服務、託管與基礎設施。
  - Third-party：外部平台、第三方服務與整合。
- 每個納入的端點須說清楚在本案的角色，並盤點來源、去向及互動目的等跨端點關係；可以由前文邊界圖與責任說明承接，避免重複整張表。
- 端點分類按本案角色組織，例如應用端、資料端、支援服務、執行環境；供應商品牌與技術種類不應取代角色判斷。

## Good Example

- 候選掃描能辨識硬體與外部服務，同時避免重複列入手機入口。

```md
應用端：倉庫 Web，提供盤點操作，手機以瀏覽器使用同一入口。
設備端：掃描器，向 Web 提供條碼輸入。
資料端：本機儲存，保存離線盤點結果。
外部服務：庫存平台，接收同步資料並回傳受理結果。
互動：掃描器 → Web → 本機儲存；Web 連線時與庫存平台同步。
```

## Bad Example

- 把端點誤當 URL，遺漏非 HTTP 的跨端互動。

```md
端點只有 /inventory、/login、/sync。
掃描器不是獨立部署，所以不列入；第三方庫存平台之後再看。
固定依 Frontend、Backend、Database 分類即可。
```

# Rule 2 - 每個端點界面保留可辨識的獨立分析工作

- Level: `MUST`
- 端點界面是該端點與使用者、其他端點或管理者互動、存取或控制的邊界，例如操作、服務請求、設備通訊、資料存取或維運控制界面；一般品質話題或功能主題本身不等於界面。
- 從每個已盤點端點列出所有需要分析的界面；一個端點可以有多個界面，每個界面至少分配一項獨立分析工作。
- 界面間有關聯或共用來源，仍各自保留分析工作，不因計畫同波平行、由同一子技能承接或屬於同一端點而合併省略。
- 以單一分類表呈現「分類 → 端點 → 待獨立分析界面」，同列可列多個界面；端點角色及跨端互動承接前文。順序、前置輸入與平行分組集中在波段計畫。
- 界面與工作命名清楚到能區分範圍即可；盤點與規劃階段不提前展開界面契約，實際分析由後續委派工作完成。

## Good Example

- 單一表格呈現歸屬，每個互動邊界保留獨立工作。

```md
| 分類 | 端點 | 待獨立分析的界面 |
| --- | --- | --- |
| 應用端 | 倉庫 Web | 使用者操作界面<br>掃描器輸入界面 |
| 外部服務 | 庫存平台 | 盤點同步界面 |

後續各自安排使用者操作界面分析、掃描器輸入界面分析、盤點同步界面分析。
```

## Bad Example

- 用籠統主題取代界面，或因有關聯而刪除獨立工作。

```md
倉庫 Web：分析效能、安全與庫存。
掃描器輸入與盤點同步互有關聯，合成「整體分析」，不再分配獨立工作。
```

# Rule 3 - 用一致名稱連結界面、工作與波段

- Level: `MUST`
- 分析工作以「界面名稱＋分析」命名；在分類表、波段表、必要前置輸入及條件說明中使用同一名稱。
- 不同端點的界面若重名，補上端點或用途以消除歧義；不要依賴另一套識別編號讓讀者來回查找。
- 端點、界面、分析工作與 Sub-action 不新增 E／I／A 或流水編號；波段以其階段成果命名並依表格由上至下排列，不使用 Wave 數字。
- 每個 Sub-action 清楚對應單一界面的分析工作，同一波段內可以用換行或分列列出多項工作；不以「分析前端與後端」取代個別工作。

## Good Example

- 名稱本身足以追蹤，不需要額外對照編號。

```md
界面：倉庫操作界面、管理操作界面。
工作：倉庫操作界面分析、管理操作界面分析。
波段「操作邊界」：兩項工作各自列出，可平行執行。
後續同步界面分析的必要輸入引用「倉庫操作界面分析的同步操作需求」。
```

## Bad Example

- 同一對象使用多個名字或多層編號，難以判斷歸屬。

```md
E01 → I03 → A07 → Wave 2 / Sub-action 1。
分類表稱「Web 操作界面」，波段表改稱「前端規格」，前置輸入寫「畫面設計」。
```

# Rule 4 - 以必要前置輸入決定分析順序

- Level: `MUST`
- 對每項界面分析工作，根據界面間依賴、跨端點資料流與互動，說明開始分析所需的具體輸入，以及輸入來自已取得來源、待取得外部資料或哪項較早的分析工作。
- 尚未取得的外部文件、設備協定或現況資料，標為待取得輸入及啟動條件，與前波分析產物分開表達；排入波段不代表這些輸入已具備。
- 只有缺少該輸入就無法合理啟動分析，才列為前置依賴；共用需求、同屬一個流程或技術上會互動，不自動代表必須串行。
- 前置工作需要提供的結果應足夠明確，例如操作需求、整合邊界、服務契約或資料範圍，讓讀者理解排序原因；不將預期取得的結果當成已確認內容。
- 不預設 Frontend、Backend、Database 的先後。若 API 只需操作清單，無須等完整 UI／UX 設計；若既有有效契約已提供必要輸入，後續工作可以直接據此安排。
- 分析順序與開發交付里程碑分開追蹤；不因開發先後或同一發布日期，強加無關的分析依賴。

## Good Example

- 排序說明必要內容，也容許既有來源解除等待。

```md
已有有效共用服務契約時，操作界面與服務接收界面分析可在沒有其他相依的情況下同波開始。
裝置通訊格式未定時，裝置通訊界面分析先釐清必要格式，服務接收界面分析再承接。
裝置手冊尚未取得：另列為待取得輸入，並標明裝置通訊界面分析須取得手冊後啟動。
API 若只需操作清單，不等待完整 UI／UX 視覺稿。
```

## Bad Example

- 按技術層固定串行，沒有指出必要輸入。

```md
所有專案一律先完成全部 Frontend 與 UI／UX，再分析 Backend，最後 Database。
因為備份與部署同屬雲端，所有部署分析必須等待備份、排程及遷移分析全部結束。
```

# Rule 5 - 以實際依賴建立可平行執行的波段

- Level: `MUST`
- 分析流程可有一個或多個波段，每個波段可包含一個或多個獨立界面分析工作；單端點、單界面與單波段也可完整合格。
- 波段依表格由上至下推進。每項工作的必要前置輸入，都須由已取得來源或較早波段提供；有待取得外部輸入時，須明示條件成立後才能啟動。同一波段中的工作彼此不能存在尚待產出的直接或間接依賴。
- 依賴先前結果的工作安排到後續波段；無相互依賴且前置輸入已具備的工作，可以同波平行。不要為了增加平行數或套用範例而強行拆分、合併或增加波段。
- 波段表至少呈現語意波段名稱、各個獨立分析工作、必要前置輸入及足以理解分組的原因；同波各工作前置輸入不同時，分列或逐項交代，避免混成無法對應的總清單。
- 每個工作的委派邊界描述單一界面與分析任務，另依主責選擇規則記錄對應 Planner；不規定子技能內部方法或預先指定無來源的實作方案，Planner 名稱不決定波段先後。

## Good Example

- 同波工作共享已具備輸入，後續工作等待其真正需要的結果。

```md
| 波段 | 獨立分析工作 | 必要前置輸入 |
| --- | --- | --- |
| 操作與設備邊界 | 倉庫操作界面分析<br>掃描器輸入界面分析 | 已確認需求；兩者無互相等待的輸入 |
| 同步契約 | 盤點同步界面分析 | 倉庫操作界面的同步操作需求、掃描器輸入界面的資料限制 |
```

## Bad Example

- 同波工作須等待彼此結果，或單純照範例湊數。

```md
波段「同時完成」：操作界面分析與同步界面分析平行。
同步界面分析的前置輸入：尚待本波操作界面分析產出的操作需求。
其餘無實際工作，但為符合範例仍增加四個空白波段。
```

# Rule 6 - 以界面覆蓋與依賴一致性判定規劃完成

- Level: `MUST`
- 逐一對照端點分類表與波段計畫，確認每個已盤點界面至少有一項獨立工作，工作名稱與歸屬一致，沒有遺漏、無來源的新增工作或循環依賴。
- 檢查每項前置輸入來源，排除同波等待、尚未安排的工作結果及未來波段結果被當成前置的情況；發現新依賴時同步調整波段與說明。
- 適用性待確認的端點與界面，標明成立條件及相關分析的影響；確認不適用後保留原因，並同步移除或調整受影響工作的前置依賴，不能直接消失或繼續阻塞其他工作。
- 規劃完成品須能清楚回答：本次有哪些技術端點與界面、各自分析工作是什麼、依什麼順序分析，以及哪些工作可以分波平行執行；主責、產物路徑及狀態須能逐工作追蹤。
- 規劃完成與分析完成分開判定。既有輪廓及有據選型維持原狀態，未執行分析標為待執行；規劃檢查通過後由主流程按依賴委派 Planner，不把待取得的結果寫成已確認內容。

## Good Example

- 條件端點退出後，後續工作仍有可追溯的輸入安排。

```md
現況確認無既有檔案需匯入：記錄「舊檔讀取界面分析不適用，因無承接來源」。
歷史資料承接界面分析據此調整為僅確認期初輸入範圍，前置依賴同步更新。
分類表及波段表其餘界面逐項對應，主責與輸出位置清楚後，由主流程按計畫委派分析。
```

## Bad Example

- 覆蓋未完成就執行分析，且留下失效依賴。

```md
刪掉舊檔端點，不說原因；承接工作仍等待舊檔讀取分析結果。
分類表有掃描器輸入界面，波段表未安排。
先呼叫資料模型與 API 子技能補齊結果，再把分析流程標成規劃完成。
```
