# Rule 1 - 掃描實際端點與互動邊界

- Level: `MUST`
- 技術端點是可界定互動責任的應用、服務、設備或資料來源，不是 HTTP 路徑，也不要求可獨立部署。
- 依需求掃描下列候選，只納入實際存在者，其他類型同樣依責任判斷：
  - Frontend：使用者入口、操作與客戶端恢復。
  - Backend：服務呼叫、業務規則及必要背景處理。
  - Database：權威儲存、既有資料與本機保存。
  - Mobile：獨立原生／行動應用；手機瀏覽同一 Web 不重列一個應用。
  - Hardware：感測器、讀取器、控制器及設備協定。
  - Cloud：託管、身分、通知與執行環境。
  - Third-party：外部平台、回呼與整合服務。
- 對納入的端點辨認來源、去向、互動目的及信任／資料所有權邊界；可由 Plan 邊界圖及責任表承載，不強制另一份分類矩陣。
- 界面是使用者、其他端點或管理者與該端點的互動／存取／控制邊界。效能、安全等品質題目屬跨切關切，結合實際操作分析，不單獨虛構端點。

## Good Example

- 掃描全面，呈現簡潔。

```md
倉庫 Web（含手機瀏覽）接收掃描器輸入，離線保存，恢復網路後同步庫存平台。
邊界圖與責任表已表達四個端點，不再建一套相同分類表。
```

## Bad Example

- 以 URL 或固定三層代替實際邊界。

```md
端點只有 /inventory 與 /login；掃描器不可獨立部署所以忽略。
只要分析 Frontend、Backend、Database，就視為所有外部服務都已覆蓋。
```

# Rule 2 - 覆蓋界面，按整合責任安排任務

- Level: `MUST`
- 每個必要互動都須有主責，但界面、任務與檔案不是一對一關係。共用模型、身分、狀態或恢復語意且可由同一主責維護的內容，整合成同一領域任務。
- UI 操作與客戶端同步屬同一體驗時一起分析；同服務的命令、讀取、session 及事件由 API 主責整合，共用標準型別與具名擴充區；相關資料模型由 Data 一次收斂。
- 不同應用、資料所有權、傳輸對象或必要輸入有真正獨立邊界時可分開工作，但必須說清楚覆蓋與交接，不能讓同一決策出現兩份權威版本。
- 任務命名只需辨認領域責任，跨文件保持一致，不增設端點／界面／工作流水編號。產物種類與唯一寫入責任沿用共同契約，不因分工數量增加交付類型。

## Good Example

- 保留互動分析，同時減少文件重複。

```md
玩家體驗：涵蓋輸入、等待、結果與重連，交付一份 HTML + 短紀錄。
服務契約：涵蓋命令、GET、session、私有通知，共用一份 OpenAPI。
設備協定仍在 x-interfaces 中保留交換格式與權限，沒有因整併而消失。
```

## Bad Example

- 拆分等於檔案膨脹，或整併等於遺漏。

```md
同服務的每個 GET、POST、session、通知各建一份分析，重複定義相同 DTO。
為只留三個工作，直接刪除掃描器格式及第三方授權分析。
```

# Rule 3 - 只以必要輸入建立依賴

- Level: `MUST`
- 對每項任務確認沒有它就無法合理分析的內容，指出來自既有來源、待取得外部資料或其他主責的具體結果。預期產物及檔名不等於輸入已具備。
- 共用來源、技術互動、同一發布日期或開發先後不是必然分析依賴。UI 可先交操作與狀態供 Data/API 使用；完整視覺及最終 DTO 不一定是所有工作的前置。
- 某領域需較早版本結果時，界定可用的先行部分，最後由其主責回查契約；不把互相等待的結論偽裝成可平行，也不代替對方決定未確認語意。
- Plan 以短文或一份精簡依賴表表達即可；只有多分支且短文無法清楚安排時才展開波段，不預設 Frontend→Backend→Database 或固定波段數。
- 同波工作不得引用同波尚未取得的直接／間接依賴；順序以所需資訊而非 Planner 名稱決定。來源變更先修正受影響依賴。

## Good Example

- 先行可用結果解除等待，最後仍回查。

```md
已有需求與操作條件，UI 先分析角色／狀態；Data 收斂交易，再由 API 定義共用 wire 契約。
UI 原型回查已完成 DTO，不要求先完成所有畫面才能分析資料。
掃描器手冊未到只阻塞該協定；其餘工作照可用輸入進行。
```

## Bad Example

- 虛假平行或固定串行。

```md
UI 和 API 平行，但 API 必須等待本波 UI 尚未產出的唯一業務規則。
無論需求為何，都要 UI 全部完成後才做 API，最後才能做 Data。
```

# Rule 4 - 規劃以覆蓋、可啟動性與可追溯狀態判定

- Level: `MUST`
- 逐項對照需求互動與任務，確認角色／端點／資料責任均有主責，整併未遺漏必要契約，也未生成無來源功能。
- 檢查必要輸入是否真實可讀、是否循環等待、是否有待取得外部來源；適用性未定者記錄成立條件，不適用者交代原因並解除失效依賴。
- 主責、實際產物、可用結果與未決影響能從一份 Plan 索引追蹤即可，不強制端點表、波段表、執行表各抄一遍。
- 規劃完成不同於分析完成。未委派工作標待執行；只有回收驗收後才可將其結論當作下游依據。

## Good Example

- 一份索引足以安排工作及接續。

```md
無歷史匯入來源：此能力不適用，刪除相關失效前置。
UI、服務、資料各有主責、產物路徑與明確必要輸入；UI 原型尚未產出則仍待執行。
```

## Bad Example

- 表格齊全但覆蓋或狀態不實。

```md
分類、波段、執行表都有，卻沒有主責分析外部付款回呼。
只列出預定 HTML 檔名，就說原型與整體分析都已完成。
```
