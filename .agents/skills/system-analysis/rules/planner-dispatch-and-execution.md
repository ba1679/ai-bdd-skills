# Rule 1 - 按主要責任選擇主責，相關界面整合交付

- Level: `MUST`
- 每個整合任務指定一個主責，依需釐清的互動、資料或控制責任決定，不依供應商品牌或端點種類機械映射。
- `ui-ux-plan`：操作與角色呈現、資訊結構、輸入回饋、畫面狀態、無障礙、響應配置及客戶端恢復；交付互動原型與短紀錄。
- `data-plan`：資料權威、識別與關聯、讀寫、狀態不變條件、交易／競態、資料授權、投影、必要生命週期與復原約束；以 DBML/Notes 承載。
- `api-plan`：服務命令／讀取、caller 信任、session、事件／設備／第三方協定、錯誤與恢復、必要服務設定；整合於 OpenAPI 標準區與具名擴充區。
- 身分體驗歸 UI、驗證信任歸 API、交易內授權與一致性歸 Data；service role／背景身份不能替代 caller 過濾。UI 顯示、服務 wire 與資料結構各自保持權威來源。
- Cloud、Auth、Realtime、Hardware、Third-party 及維運的必要互動仍須覆蓋，依責任併入產物；只有當前必要的詳細控制程序才展開，不因沒有獨立文件就省略邊界。

## Good Example

- 同供應商按責任分工，事件仍有承載位置。

```md
UI 主責匿名身分失效時怎麼恢復；API 定義 JWT/caller 與 x-realtime 授權；Data 定義 membership/RLS。
命令與 snapshot 使用同一 API 主責的 DTO，不另建互相競爭的定案。
```

## Bad Example

- 用品牌分派，或由主流程越界補專業結論。

```md
Supabase 所有內容一律交 Data；事件不是 HTTP 所以略過。
system-analysis 自行補上鎖定 SQL、授權規則及原型程式，假稱各主責已完成。
```

# Rule 2 - 委派須有可用輸入與唯一寫入責任

- Level: `MUST`
- 啟動前依共同契約交付清楚範圍、實際來源、必要前置結果、指定位置、下游用途及局部未知。確認對應 skill 可讀可執行；缺少能力如實回報影響。
- 同一產物的相關工作交給同一 Planner 整合；多個平行任務不得同寫 Plan、OpenAPI、DBML 或 HTML。需要分階段承接時，由原主責接續該檔，而非新增相同定義。
- 必要輸入已具備且互無依賴者可平行；環境只支援順序呼叫時保持相同依賴邏輯。不把未取得手冊、預期回覆或其他工作的計畫當成可用結果。
- 原型如何製作及是否需要視覺研究由 UI 主責決定；主流程驗收 HTML 與短紀錄，不固定啟用 Pencil 或研究階段。
- 缺口只阻塞實際受影響工作；局部可用部分經驗收並界定限制後，仍可交給下游。

## Good Example

- 依賴及寫入邊界具體。

```md
UI 初步操作已確認 → Data 可分析不變條件。
API 的 HTTP 與事件交同一任務寫 analysis/api.openapi.yaml。
UI 回查契約後接續原型，system-analysis 最後統一更新 Plan。
```

## Bad Example

- 以多 agent 製造共寫或虛假依據。

```md
兩個 API agent 同時修改 api.openapi.yaml，各自重寫 RoomSnapshot。
設備手冊未取得仍宣稱協定資料已備齊。
```

# Rule 3 - 驗收實際成果與必要交接

- Level: `MUST`
- 讀回產物而非只收摘要，核對責任、來源與需求覆蓋、格式解析、內部引用、實際連結及必要結果。結構與補充規則互相矛盾時交回原主責，附上位置與期待。
- 共同概念須一致：識別與資料含義、狀態前置／轉移、caller／角色／會員授權、輸入與回覆、錯誤／重試、可見性、事件與權威讀取分工。共用 HTTP 型別集中 components，非 HTTP payload 引用或對照相同語意。
- 需要 UI 時，實際開啟 HTML、操作主要成功與代表性拒絕／載入／恢復，檢視指定裝置、鍵盤與文字狀態。純假資料及未模擬能力寫明；文件存在不能代替互動檢查，工具不足則保留限制。
- 確認子 Planner 的結果足以支持下游，而非要求完整交接矩陣。新發現依賴先更新安排；同一阻塞沒有新輸入時保持待補，不反覆委派空轉。
- 完成分析不等於完成軟體；OpenAPI/DBML parser 不證明授權及 SQL 已運行，原型不證明真實 session／並行／服務通知。範例過往的成功紀錄不當成本次證據。

## Good Example

- 回收能支持接續，也如實限定驗證。

```md
拒絕回覆缺必要恢復語意 → 交 API 修正；Data 已確認部分仍可用。
HTML 能走完流程，仍未連真服務 → 記為原型已檢查，整合測試待實作。
必要原型無法開啟 → UI 待補，API 可承接已驗收的操作規則。
```

## Bad Example

- 用摘要、未執行的測試或越界補寫當驗收。

```md
Planner 說完成就通過，未讀 API 或 HTML。
範例寫已通過多瀏覽器測試，所以新原型也標通過。
```

# Rule 4 - 接續只回查受影響成果，如實判定本輪完成

- Level: `MUST`
- 對照來源、範圍、共同約束及既有產物；有效結果沿用，上游變動時追查真正引用的下游，需重驗者標待修正。
- 本輪適用的領域產物、必要交接與跨產物一致性均通過，且沒有阻塞本輪分析的未知，才稱分析完成。非阻塞未知保留影響／接手時點，不適用項說明原因並解除依賴。
- 以實際狀態更新 Plan 索引及下一步；必要 UI 原型未產出／檢視時，不能因業務規則可用就稱 UI 已完成。
- 交付限共同契約的五類，檢查過程的輸出放暫存；不因驗證再新增永久的審計報告、交接摘要或截圖交付。本輪不自動啟動正式前端、SQL migration、服務設定或部署。

## Good Example

- 變更影響清楚，未受影響者不重做。

```md
結果可見性改變 → API 投影、Data Notes、UI 原型回查；配對輸入規則仍沿用。
所有必要分析驗收後更新 Plan；公開配置未完成仍列發布前待處理。
```

## Bad Example

- 過時狀態或額外交付掩蓋缺漏。

```md
取消欄位後，UI/API 仍各自保留舊定義卻都標完成。
為證明只有五類交付，另產一份 audit.md、handoff.yaml 與多張永久預覽圖。
```
