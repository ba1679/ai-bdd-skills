# Rule 1 - 依單一界面的主要責任選擇主責 Planner

- Level: `MUST`
- 每項界面工作指定一個主責 Planner，按本次需要釐清的互動、資料或控制責任判斷，不按技術品牌、端點分類或波段名稱機械對映。
- 使用下列候選判斷主要交付；各 Planner 的內部分析方法由其自己的 skill 承擔：

| 主責 Planner | 適合的主要交付 | 容易跨域的界線 |
| --- | --- | --- |
| `ui-ux-plan` | 使用者操作、資訊呈現、畫面狀態、輸入回饋、可及性、客戶端顯示與重連體驗。 | 匿名身分的使用體驗可屬 UI；身分驗證與 caller 信任契約屬 API。公開設定如何呈現可屬 UI；secret 管理與執行入口屬 API。 |
| `data-plan` | 資料來源與權威、模型與關係、狀態不變條件、資料存取與交易、並行一致性、保存與復原。 | RPC 交易內部與 RLS 資料政策可屬 Data；RPC 對外請求回覆、caller 及錯誤映射屬 API。資料遷移、備份與還原可屬 Data。 |
| `api-plan` | 服務命令與讀取、身份及授權、事件與第三方整合、服務或環境控制、託管與交付維運契約。 | 不限定 HTTP；涵蓋 session、通知、設備協定與管理控制。部署流程、CORS／secrets、CI gates 與觀測可屬 API；其資料復原內容承接 Data，操作畫面承接 UI。 |

- Cloud、Third-party、Hardware、Auth、Realtime、託管及維運仍保留為獨立端點或界面，不因三個 Planner 的名稱而刪除或強併；依實際責任選最適合者並說明理由。
- 同一界面跨領域時，主責負責本界面的完整交付；其他領域所需結果用已有來源或獨立工作的輸入承接。若尚缺必要分析，先補足工作與依賴，不能由主 skill 代寫，也不能同時讓兩個 Planner 各寫一份互相競爭的定案。

## Good Example

- 同一供應商可以對應不同主責；交付界面仍被覆蓋。

```md
玩家操作界面分析 → ui-ux-plan：輸入與畫面狀態。
狀態資料與 RPC 存取界面分析 → data-plan：資料不變條件與交易責任。
匿名 session 與 caller 身分界面分析 → api-plan：caller 信任與失效契約。
Web 託管與 CORS／secrets 界面分析 → api-plan：執行環境與設定邊界。
資料備份與還原界面分析 → data-plan：一致復原結果；維運控制流程另承接其輸入。
```

## Bad Example

- 只按端點品牌分派，或忽略三層名稱以外的界面。

```md
Supabase 的所有工作都交給 data-plan。
Realtime 不是 HTTP，所以沒有 Planner。
託管與維運由 system-analysis 自己詳細分析。
同一個界面讓三個 Planner 各產一份定案，之後任選其一。
```

# Rule 2 - 委派需具備可用輸入與隔離的輸出位置

- Level: `MUST`
- 每次委派以已載入的共同交接契約確認範圍、實際來源、必要前置結果、輸出位置及下游用途；先確認主責 skill 可讀取並能執行，缺少時回報其影響，不能假稱已委派成功。
- 按既有波段與必要依賴啟動工作，不固定三個 Planner 的先後；同 Planner 的多項獨立工作也可以各自執行。
- 同波無相互依賴且輸入已具備時可分別平行委派；逐項呼叫的環境採相同依賴安排執行，不能為了平行讓工作引用同波尚未產出的結果。
- 每項工作有唯一產物位置；依共同契約安排 UI／UX 文件、OpenAPI YAML、非 HTTP 分析 YAML 或 DBML。API／Data 的分析補充直接保存在各自格式中。Planner 只寫自己的產物，由主 skill 統一寫 `plan.md`，不讓平行工作共寫總表或同名結構檔。
- 外部輸入缺少只阻塞受影響工作及依賴鏈；其他工作必要輸入已具備時仍可繼續，不把無關前波工作全部完成設成額外門檻。

## Good Example

- 前置已具備的兩項 UI 工作，分別執行且不互相覆寫。

```md
倉庫操作界面分析 → ui-ux-plan → analysis/倉庫操作界面.md。
管理操作界面分析 → ui-ux-plan → analysis/管理操作界面.md。
主流程收回兩份文件後更新 plan.md；API 工作若只需已驗收的操作清單，不等待完整視覺稿。
```

## Bad Example

- 有排程表就直接啟動，且讓委派工作互相覆寫。

```md
裝置協定文件尚未取得，仍把「待取得手冊」當作可用輸入。
所有 Planner 同時寫 analysis/plan.md 與 plan.md。
兩項無關工作只因共用一個 Planner 就強制互相等待。
```

# Rule 3 - 以實際產物驗收工作並處理回饋

- Level: `MUST`
- 取得回傳後實際讀取產物，包含 OpenAPI 的 `x-analysis` 或 DBML Notes，確認指定界面、需求與共同約束覆蓋，必要結果有內容與來源；核對格式解析、引用與補充分析的一致性，預期設計及未定事項沒有被當成已驗證事實。
- 核對後續工作需要的具體結果是否可用；缺失或衝突交回該主責 Planner，附上問題位置與所需修正，不在主流程自行補寫領域細節。
- 依共同契約更新工作狀態、實際產物連結、未決事項及受影響工作。呼叫完成、檔案存在或收到摘要本身都不是「已完成」的充分條件。
- 回饋出現新依賴時，先更新波段與必要輸入，再重啟相關工作；循環依賴須藉明確的已有來源、先行可交付結果或範圍調整解除，不互相假設對方已定案。
- 同一阻塞沒有新輸入時保留待補原因，不重複委派空轉；若剩餘適用工作全部無法推進，交付現況與所需輸入，不能宣告整體完成。

## Good Example

- 產物有寫出缺口時，保持其狀態並繼續可用部分。

```md
服務回覆仍缺少拒絕條件 → 交回 api-plan 修正。
保存期未定 → data-plan 列明影響與待決事項；若本次必要存取設計不受影響可完成。
若清理命令必須依保存期才能定義，該命令相關工作仍標待補輸入。
```

## Bad Example

- 將收到文件等同完成，或由主流程自行越界解決。

```md
Planner 回覆「完成」但文件不存在，仍將後續工作全部標可啟動。
沒有保存期決策，system-analysis 自行指定七天並代寫清理規則。
同一缺口未補齊，無限重送相同委派直到出現不同答案。
```

# Rule 4 - 接續時重驗受影響結果並如實判定整體完成

- Level: `MUST`
- 重新執行時先對照來源、範圍、共同約束、必要輸入及既有產物；仍有效的結果沿用，避免重做已完成且不受影響的工作。
- 上游結果變動時，追查實際引用該內容的下游工作，將需重新檢查者標為待修正，驗收後才恢復可用；不因檔案存在就保留過時的完成狀態。
- 整體核對至少涵蓋：同名概念的資料含義、操作權限、狀態轉移、輸入與回覆、錯誤與重試、資料可見範圍、通知與權威讀取，以及適用的執行設定和維運責任。
- 所有適用界面均有經驗收產物，跨界面必要交接一致，且沒有阻塞分析的未決事項時，才標記整體分析完成；不適用工作須有理由及已調整的依賴。
- 分析文件中的實作與驗證計畫不等於已完成開發、測試或部署；回報清楚區分文件完成、待補輸入與後續實作工作。

## Good Example

- 只重新檢查變更影響的部分。

```md
Snapshot 的可見欄位變動 → snapshot 讀取與客戶端顯示工作待修正。
玩家操作清單及匿名 caller 邊界未變 → 沿用原已驗收結果。
全部必要交接完成 → 整體分析已完成；實際功能驗證留待開發任務。
```

## Bad Example

- 未檢查舊產物，或把文件完成當成軟體已交付。

```md
上游取消一個欄位，但下游仍引用舊欄位，全部保持已完成。
尚有必要界面無產物，因規劃檔已寫好就標整體完成。
分析文件列出部署步驟，因此宣稱正式環境已部署成功。
```
