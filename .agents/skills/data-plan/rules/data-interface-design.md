# Rule 1 - 資料模型必須承接來源、所有權與不變條件

- Level: `MUST`
- 以本輪整合的實際讀寫需求決定資料範圍，標示已有依據、設計推導或待確認；儲存產品、資料量與效能目標沿用現有研究，缺少來源時保留缺口。同一權威模型供多個操作使用時整合分析，不以界面數量拆檔。
- 對每項資料說明權威來源、擁有端點、合法寫入者、讀取者，以及複本、快取、衍生值或外部資料的更新責任；同一資料有多個寫入來源時，需有衝突裁決與同步依據。
- 模型至少辨識實體或記錄、識別碼與唯一性、關聯或參照、必要欄位與空值、型別與單位、合法值與預設、不變條件；版本、時間來源、租戶或分區邊界依實際需求處理。區分欄位 check、鍵／參照能強制的限制，以及須由交易或政策強制的跨表條件。
- 有狀態變更時列出來源狀態、觸發操作、前置條件、目的狀態及拒絕條件；可直接由欄位與不變條件表達的簡單資料不強制另造狀態機。
- 資料讀寫要能對應到呼叫者、篩選或定位方式、排序與分頁需求、回傳資料含義、寫入前置條件及結果；索引、分區、冗餘或物化設計須連結實際存取模式與已知規模。非關聯式資料使用相應的鍵、文件、物件或事件結構，不強套資料表。
- 必要分析面向須形成結論或明確缺口；內容放在相關結構或 Notes，不為未涉及的分支填寫空表或重複「不適用」。

## Good Example

- 這個例子是好的，因為權威資料、識別與規則可對應到實際操作。

```md
庫存記錄以「倉庫識別碼＋品項識別碼」唯一定位，庫存端點為唯一權威寫入者。
數量為非負整數，單位為件；任何扣減都必須在同一原子操作中檢查餘額並更新版本。
列表依倉庫篩選；尚無排序與資料量需求，因此保留實體索引設計為待研究，未指定儲存產品。
本界面沒有額外業務狀態，數量與版本不變條件已涵蓋此次變更規則，獨立狀態機不適用。
```

## Bad Example

- 這個例子是壞的，因為選了儲存方式，卻沒有資料責任與合法變更規則。

```md
建立 stock table，所有欄位用字串；需要時加索引，前端與後端都可直接更新庫存。
```

# Rule 2 - 寫入設計必須說清楚原子性、競態與重試結果

- Level: `MUST`
- 每項寫入須說明原子更新的資料集合、提交前檢查、部分失敗的可見結果與復原責任；跨來源操作需區分可用交易保證、補償或尚待研究的能力。
- 對可能同時操作相同資料的情境，列出競爭者、可接受結果及採用的保護條件；可用條件寫入、版本檢查、鎖或序列化等設計，但需證據支持儲存端具備所需能力。
- 對讀取說明可接受的新鮮度、提交後可見性及快取或複本延遲；需求沒有指定一致性時，指出它對業務結果的影響，不能默認所有副本同步。
- 若操作可能重試，區分同一請求重送、不同請求競爭及相同識別碼搭配不同內容；有去重需求時說明識別鍵作用域、內容比對、與業務變更原子保存的結果、原結果回放及同鍵異內容拒絕。並行首次寫入只能形成一個結果，輸家重讀比對；提交後回覆遺失不能造成第二次變更。
- 去重以操作意圖及 canonical payload 判斷；含低熵秘密時使用 server-side keyed HMAC 等受保護指紋，避免儲存原秘密或可枚舉的無 key hash。金鑰不進資料、回覆或日誌，輪替須保留舊請求比對能力。僅在本案需要時使用 receipt／版本設計，不因範例新增此類資料。
- 去重保留、清理及復原須與承諾的重送範圍一致；缺少期限需求時引用 Plan 的局部影響，不能任選天數或保證永久回放。回放若含歷史投影或版本，保留原結果語意並交接不能倒退的要求。
- RPC 或儲存函式只在此定義資料輸入含義、前置條件、交易責任、結果與失敗語義；路由、傳輸欄位、wire 錯誤碼、session 與事件格式由 `api-plan` 的 OpenAPI operations／擴充區承接。

## Good Example

- 這個例子是好的，因為明確區分同時更新與重送，並保留尚未確認的能力。

```md
扣減以預期版本與足夠餘額為條件，同一提交內更新數量及版本，並記錄命令結果。
同一命令鍵與相同內容重送回放既有結果；同鍵不同內容拒絕，不能再次扣減。
不同命令競爭同一版本時至多一筆成功，其餘取得版本衝突結果。
業務變更與原結果同交易提交；回覆遺失後以原鍵取得結果，不重做業務變更。
研究尚未確認資料端可跨兩種記錄原子提交，此為阻塞輸入，狀態維持待補輸入。
wire 錯誤碼與重試提示交由 API 契約界面分析承接。
```

## Bad Example

- 這個例子是壞的，因為「有交易」無法處理重送與跨來源失敗。

```md
扣減放在 transaction 裡，失敗就重試。去重資料保存 30 天，API 一律回傳 500。
```

# Rule 3 - 權限與生命週期須落在具體資料邊界

- Level: `MUST`
- 依已確認角色與資料歸屬，說明可讀、可寫、可刪及管理權限、租戶或所有者隔離，以及權限實際由何處強制；外部身分如何驗證由對應 API 界面決定，本界面定義所需可信身分與資料政策輸入。
- 對直接資料存取、RPC、服務帳號及維運入口分別判斷適用性，說明 grants／RLS 或對應政策的執行位置、最小權限、環境分隔及憑證責任。採特權身分或可繞過 RLS 的儲存函式時，仍須逐次檢查可信 caller、所有權及狀態，不能將 service role 視為終端授權；適用時固定安全 search_path 並限制函式 EXECUTE。
- 有個資、敏感資料或稽核需求時，對應欄位與暴露位置，處理回傳投影、記錄、匯出、快取與備份的最小揭露、刪除及保護。衍生 snapshot／receipt 只保存 caller 可見內容；前端隱藏欄位不是資料授權，原秘密與指紋不進對外投影或日誌。
- 記錄建立、變更、封存、過期及刪除等適用生命週期，含關聯資料、衍生值、去重與稽核記錄的連動影響；保留期限與刪除例外採需求依據，法規或產品決策未明時交回所需決策。

## Good Example

- 這個例子是好的，因為資料政策與執行責任清楚，未把技術偏好當產品規則。

```md
資料端只接受庫存服務身分，依倉庫授權集合限制讀寫；終端使用者無直接資料寫入權限。
API 界面需提供已驗證操作者與授權倉庫集合，本界面不定義 session 或 token 格式。
若服務身分可繞過 RLS，交易仍逐次檢查該操作者；回傳只含其可見資料。
操作記錄保留期限尚未確認；刪除與去重失效行為依此決策，相關設計維持待補輸入。
```

## Bad Example

- 這個例子是壞的，因為缺乏執行位置，且擅自補出保留政策。

```md
資料有登入就安全。操作記錄永久保留，帳號刪除時只刪除使用者資料即可。
```

# Rule 4 - 依本輪深度保留演進、復原約束與驗證期待

- Level: `MUST`
- 評估本次資料設計對既有資料、格式版本與使用端的影響；有變更時列出相容順序、資料轉換或回填、切換條件、失敗處理與回復限制。全新資料且無舊使用端時，可說明遷移不適用。
- 對持久化資料保留復原後一致性及跨來源時間點關係；含去重時須同時恢復業務狀態與結果，不能將失去 receipt 的舊請求當新寫入。快取或可重建資料說明重建來源與失敗影響。
- 備份責任、可接受遺失與中斷、RPO／RTO、供應商能力及詳細 restore 演練，只在本輪交付依賴時展開；其餘在 Plan 引用處理時點與公開啟用限制，無 Plan 時記於相關 Note。延後操作程序仍須保留最低一致性約束，未知值維持未決。
- 對必要規則給出精簡驗證期待，涵蓋合法變更、無效輸入、權限隔離、相關競態、同鍵重送／異內容、提交前後失敗與資訊遮蔽。涉及本輪遷移或復原時補完整性檢查；完整 BDD 案例與執行步驟交後續測試工作。
- 驗證情境是後續實作與測試的輸入；只有已有可核對證據時才能記錄實測結果。完成資料分析不等於已執行 migration、SQL、測試或復原演練。

## Good Example

- 這個例子是好的，因為交代復原設計缺口，並提供可供後續驗證的預期。

```md
此為全新資料界面，沒有舊資料與既有讀取端，資料遷移不適用。
詳細備份／復原程序延至公開交付，待決責任與目標見 plan.md；本輪保留庫存與命令結果須同時點一致復原的約束。
後續驗證：兩個扣減同時競爭最後一件庫存，預期僅一筆成功且庫存不為負。
復原後需核對庫存數量、版本及命令結果的一致性；以上是驗證方案，尚未執行。
```

## Bad Example

- 這個例子是壞的，因為把設計文件當成已執行的遷移與驗證。

```md
備份延後，所以可分開還原庫存與 receipt，再將沒有 receipt 的舊請求當新命令。
分析文件完成，因此遷移、競態測試與公開上線都已通過。
```
