# Rule 1 - 以服務責任整合契約與來源

- Level: `MUST`
- 分析範圍以本輪服務責任及實際互動決定。同一責任共用的命令、查詢、身分建立、事件與恢復約定一起分析，界面數量不決定工作或檔案數量。
- 區分需求已確認、既有實作、資料契約與本輪設計；在前言或影響決策的位置引用實際可讀來源。未知與矛盾須指出受影響結論，來源沒有提供的產品政策不能從範例移植。
- 任務、完整交接矩陣、全域未決清單及完成宣告由共同契約處理；子產物保留局部決策、限制與可接續內容，不固定展開大型管理框架。

## Good Example

```md
範圍：庫存預留的命令、預留查詢、工作者通知與使用者 session。
共用：預留識別、權限、對外狀態與錯誤命名，在一份 OpenAPI 中維護。
依據：規格 FR-03 與 data-model.dbml 的原子預留約束；保留期限尚未確認，引用 Plan U2 並標明對重送的影響。
```

## Bad Example

```md
每個 HTTP 操作、session 與事件各寫一份 YAML，再各自定義預留模型。
因範例有 24 小時保留期，本系統也直接採用；所有界面已完成。
```

# Rule 2 - 對外契約承接資料權威與原子結果

- Level: `MUST`
- 持久化模型、狀態轉移、交易、一致性、資料層授權與存取引用有效的 `data-plan` 產物或來源中已確認的既有契約；服務負責映射對外格式、可見欄位、授權、錯誤與恢復，新增資料需求交回其主責確認。
- 分析每個操作的觸發者、提供者、前置狀態、可控制內容及成功觀察點。區分接受、提交與送達，明確說明並行變更或版本衝突時的結果；不得以先讀到的 client 狀態代替 server 的原子判斷。
- 命令回覆、查詢與事件所引用的狀態及欄位須語意一致；區分持久化資料與 caller-safe 投影、權威查詢與提示訊息。需要版本時說明比較範圍、精度與過時回覆處理，不套用範例的特定欄位名稱。
- 資料分析尚未完成，只阻塞依賴該決策的部分；與必要資料規則矛盾時保留待修正，不自行改定上游政策。

## Good Example

```md
資料規則：原子預留，庫存不足不建立任何預留。
服務映射：201 帶已提交的 caller-safe Reservation；不足回 409 STOCK_INSUFFICIENT。
事件只表示有更新，client 經受權查詢取得真相；回覆採同一 Reservation 定義。
```

## Bad Example

```md
先信任 client 顯示的庫存再扣減，衝突時可能部分建立。
命令回完整資料列、查詢遮蔽其他租戶、事件又回另一組同名狀態；由 UI 自行解釋。
```

# Rule 3 - 身分與授權覆蓋每個可控制動作

- Level: `MUST`
- 辨識 caller 與執行身分、憑證來源及驗證方、資源／租戶範圍、可控制欄位與授權檢查；server 憑證或可定位的資源 ID 不能代替 caller 授權。角色或 actor 由可信來源決定，明示如何處理不可信的指定值。
- session／token 依實案交代建立、傳遞、恢復、到期、refresh、撤銷與新身分的限制。使用平台 SDK 時記錄其約定，不虛構應用認證路由。cookie 型介面另交代 CSRF、跨來源及 credentials 條件。
- 服務、排程與第三方回呼交代服務身分、最小權限、偽造／重播判準及稽核責任。秘密僅記錄名稱、持有者與用途，不放實際值。
- 事件分別分析發布、訂閱及接收權限、topic／channel 範圍、授權變更後的既有連線行為及 fallback；private channel 的建立成功不證明後續持續有權。限制來自實案，不預設所有系統都禁止 browser 發送。
- 區分缺少身分、授權不足與不存在的可見差異；有隱私需求時使用一致遮蔽結果，並讓有權 caller 知道可恢復的下一步。

## Good Example

```md
SDK 恢復原 session；新匿名身分不繼承舊資源。
HTTP 先驗 token，再核對 caller 的倉庫 membership；URL warehouseId 只定位。
private 通知只供 active member 接收、由受控 worker 發布；撤權後停止接收，既有 socket 撤權時點待整合驗證，不降級 public channel。
```

## Bad Example

```md
只要有 token 即可指定 actorId 或任意倉庫；worker 具有管理權所以不用核對 caller。
private join 曾成功即可永久接收；斷線時改用 public topic。
```

# Rule 4 - 交換資料與傳輸語意可供接收端實作

- Level: `MUST`
- 交換格式交代識別碼、型別、必填／可省略／可空差異、值域、時間、排序與敏感欄位可見性。共用模型以同一份定義引用，不為不同操作或傳輸另造同義欄位。
- 查詢按需求分析篩選、分頁、快取、新鮮度及可讀資源；命令分析前置條件、提交結果、衝突及重送；第三方整合分析雙方格式、認證與錯誤映射。真實存在的 HTTP webhook／callback 使用對應標準結構。
- 非 HTTP 訊息明確記錄傳輸、topic／channel、label、payload、來源、發布時點、確認、遺失／重複／亂序、相容與恢復。只在提交後發布的系統須說明 rollback、拒絕、重放與無狀態變更是否發布，以及發布失敗會否影響已提交結果。
- 接收端須能判斷訊息是權威內容或失效提示、未知 label／schema／資源不匹配怎麼處理、重連／refresh 後如何授權及補足狀態。需要版本時說明比較單位與表示法，不能把通知數量當資料版本。
- 只記錄來源要求或明示的設計提案；版本演進交代相容範圍、未知欄位與停用期待，不自行承諾 durable replay 或 exactly-once。

## Good Example

```md
通知 InventoryInvalidated：僅 resourceId、revision，指向已提交變更。
publish accepted 不等於 client 收到；rollback、receipt replay 與查詢不發通知。
可遺失、重複、亂序；同資源較舊 revision 忽略，新訊號合併為權威 GET，重連重新授權後無條件讀取。
```

## Bad Example

```md
送 JSON，欄位之後決定；accepted 代表使用者已看到。
transaction 還沒 commit 就發送；每收到一次事件把 client 庫存扣一次，斷線期間資料由事件自動補齊。
```

# Rule 5 - 失敗與未知結果有可恢復策略

- Level: `MUST`
- 分析適用的輸入錯誤、身分／授權失敗、業務衝突、重複、逾時、依賴失效與部分完成；每類給對外結果、能否重試與下一步。穩定業務拒絕和結果未知分開，回覆不可洩露受保護資料。
- 有副作用或重送風險時交代冪等識別、caller／操作範圍、canonical payload、同鍵同內容、同鍵異內容、平行重送與保留期限；引用資料規則的持久化判重。低熵秘密的 fingerprint 須避免可枚舉的無 key hash，raw secret 不流入 receipt 或日誌。
- 診斷 correlation 與操作冪等識別各自定義，不能混用。重放原結果時說明是否帶原 snapshot、可能過時及 client 如何避免倒退；憑證／身分改變及 key／格式演進不得默默把舊操作變成新副作用。
- transport timeout 或結果未知可能已提交；保留原操作識別與內容，以既定查明方法恢復。權威最新狀態不必然證明某個命令是否執行，重試前不得擅自新建識別。
- 依實案交代 deadline、退避／預算、速率／大小、背壓、取消、過期與人工恢復。未定數值引用影響與決定時點，不從範例複製；必要恢復條件未知時只將受影響結論列待補。

## Good Example

```md
預留逾時可能已提交，沿用同 caller、operationIdempotencyKey 與 payload 查明。
同鍵同內容回原結果；同鍵異內容拒絕；requestId 只用於診斷且每次請求可不同。
重放 snapshot 若較舊不套回畫面，另外經 GET 更新；receipt 保留期未定，Plan U2 限制長期 replay 承諾。
```

## Bad Example

```md
503 表示一定沒執行，重試隨機產生新 key；所有錯誤無限重試。
用 requestId 同時作診斷與去重；四位秘密以一般 hash 存入 receipt 方便比對。
```

# Rule 6 - 執行與維運約定依交付階段展開

- Level: `MUST`
- 本輪先交代使服務契約成立的最低設定與啟用限制。下列維度依實案掃描，適用內容放在相關 operation／schema 或具名擴充區；不用逐項填「不適用」。
  - **建置與執行**：產物、執行環境、相容條件、入口／路由、依賴、啟停與健康；辨識設定於建置或執行時注入。
  - **信任與跨來源**：對外／內部邊界、origin／method／credentials、預檢責任；允許的請求標頭與瀏覽器可讀的暴露回應標頭分開。需要讀取 Retry-After／診斷標頭時明列暴露方式；cookie 另考慮 CSRF。
  - **設定與秘密**：公開／私密分類、名稱用途、持有及注入方、失效行為。服務秘密、token、低熵秘密與敏感 fingerprint 不進公開產物或日誌。
  - **驗證與啟用**：必要配置、環境差異、相容與健康條件、執行者；缺少必要授權／private policy 時保留啟用限制。
  - **變更與恢復**：會影響當前契約的相容、cache／session 失效及不可逆限制；引用資料主責的相容與回復約束。
  - **觀察與責任**：必要診斷識別、健康與稽核訊號、判斷依賴故障及接手者。
- 完整發布順序、備份演練、憑證輪替、監控與 CI 程序，只有本輪交付確實依賴時才展開於最相關位置；其餘引用 Plan 的未決、啟用限制與處理時點，不另建立維運 YAML。
- 分析文件可定義後續操作期待，不代表設定、部署、policy 或恢復演練已執行。

## Good Example

```md
browser 只有公開 API origin；worker token 在 server 注入。
CORS 允許核定 origin、Authorization；另暴露 X-Request-Id 與 GET 429 的 Retry-After。
權限及 private policy 未驗證，禁止宣告可公開啟用；完整 restore／rotation 程序在發布前依 Plan U3 接手。
```

## Bad Example

```md
所有環境變數打包到前端；CORS 用 *。
每個端點另外附完整 CI、備份與維運 YAML，抄一份「全部檢查通過」。
```

# Rule 7 - 交接及驗證期待保持具體且有界

- Level: `MUST`
- 主要成功、授權拒絕、衝突／重送與恢復有可觀察結果；依傳輸提供必要的契約、整合或環境驗證期待，不以完整測試任務清單取代契約。
- 來源、局部未知與證據放在相關位置，UI 可取得對外狀態及恢復動作，資料主責可辨認需確認的存取／交易要求。交接短訊息指出實際產物、可用範圍、檢查結果與需回饋的依賴即可。
- 區分文件解析、schema／範例驗證、服務整合、授權 policy、實際部署。未執行的檢查明列限制，不能用例子中的過往結果或語法有效宣告系統安全與可發布。

## Good Example

```md
文件：OpenAPI 結構、local refs 與成功／錯誤範例已檢查。
擴充訊息：payload 的 JSON Schema 與範例另檢查；接收授權、重連與已連線撤權仍待實作整合。
UI 可依 getReservation 與 retry 約定處理；資料新需求已交回呼叫者。
```

## Bad Example

```md
YAML 能載入，所有 API、事件送達、授權、維運檢查通過；下游自行推論恢復行為。
```
