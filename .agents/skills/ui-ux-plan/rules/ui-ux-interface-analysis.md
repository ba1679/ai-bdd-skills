# Rule 1 - 依本輪使用者任務組織操作與畫面

- Level: `MUST`
- 以使用者目標、角色及相鄰責任界定範圍；相關入口、表單、結果與同步體驗可整合為一份原型，不把每個界面固定拆成一份文件。
- 每項範圍內操作都要能追溯需求或已確認決策，包含執行者、前置條件、輸入驗證、成功後狀態、適用拒絕及可恢復的下一步。沿用既有設計只取本輪需要的部分。
- 主要流程須能在 HTML 實際操作；Markdown 只記入口、意圖、契約對照與限制。相鄰 API／Data 所需保證交回其主責，不在 UI 任務自行修改其他產物或實作正式應用。
- 範例的角色數、數字規則、導覽數、版型、色彩與第三方服務皆屬個案。只有來源需要的功能才納入，不為填滿原型新增權限、通知、計時或重開功能。

## Good Example

```md
庫存調整整合商品摘要、表單、提交與結果確認；原型可實際完成一次調整。
低庫存拒絕時保留輸入，更新預覽並要求重新確認。
服務路由尚未定稿，UI 提交必要語意供 API 主責承接；不新增商品目錄管理。
```

## Bad Example

```md
為每個欄位、同步界面和結果畫面建立獨立 UI 文件；HTML 只放截圖。
照雙人遊戲範例新增第二位倉管、回合規則及重新開局，並一併實作正式 API。
```

# Rule 2 - 非同步結果必須可辨認且可恢復

- Level: `MUST`
- 依本案操作覆蓋適用的初次載入、空資料、可編輯、不可操作、處理中、成功、確定拒絕、讀取失敗與恢復；每種狀態連到觸發條件、可見內容、保留輸入、允許操作及離開條件。無關狀態不生成空畫面。
- 區分未送出、已送出等待與結果未知。送出中抑制重複提交；確定拒絕依原因允許修正，未確認結果前不得把逾時描述為「沒有執行」或建立第二筆可能重複的操作。
- 需要冪等恢復時，原型保留同一次操作的識別及內容，演示確認／回放原結果與避免重複變更；識別欄位與重試保證承接實際契約。讀到目前狀態不一定能證明特定命令是否已執行。
- 明確區分畫面模擬與已實作服務保證。記憶體 receipt 可示範體驗，不代表生產系統已具有持久化、並行序列化或授權能力。

## Good Example

```md
提交中：保留輸入，暫停重複提交。
確定拒絕：顯示可理解原因；有權威資料時更新預覽，再由使用者修正確認。
結果未知：保留原操作 ID／內容，提供「確認這次操作」；假服務回放原結果，不再調整一次庫存。
```

## Bad Example

```md
任何失敗都清空欄位，顯示「未成功，請建立新調整」。
逾時後改用新 ID 自動重送；HTML 有一個 retry 按鈕，所以正式 API 已保證不重複。
```

# Rule 3 - 契約、可見性與權威資料保持一致

- Level: `MUST`
- 可先由需求推導流程與所需語意；完整 API／Data 不是全部 UX 分析的共同前置。具體欄位、路由、錯誤碼、版本與重試方式有來源才稱已確認，其餘標為建議或待主責確認，附局部影響。
- 逐角色檢查顯示欄位與可用操作：必要時區分所有者、被指派者、管理者等本案角色。敏感資料接受後的清除、遮蔽及歷史可見性沿用需求與契約；不得因假資料可取得就顯示給所有角色。
- 區分本地未送出輸入、顯示暫態、服務接受結果與權威讀取。涉及通知／版本時，處理初次讀取、刷新、過期資料、重複／亂序回覆、重連與 session 恢復；比較與訂閱策略依既有契約，不將所有通知直接覆寫畫面。
- stale／斷線時說明保留哪些內容、哪些操作暫停、恢復成功條件及仍待確認的原操作；重新讀取不得誤抹未提交輸入。無同步要求時不憑空加入即時訂閱。
- 前端可用性不是授權保證。正式授權與安全投影由 API／Data 強制；原型不連真服務、不包含秘密金鑰。公開設定缺漏若會影響體驗，保留可見行為，服務端 CORS／部署程序交其主責。

## Good Example

```md
操作可先設計；「查明同一次調整」的路由及識別方式待 API 主責確認。
只展示本角色可讀歷史；假服務仍持有完整資料，但 renderer 只取該角色投影。
通知表示應重新讀取；舊回覆不倒退，刷新保留未提交輸入，重新同步前暫停寫入。
```

## Bad Example

```md
沒有已確認 API，卻固定 POST /stock/retry 並承諾 exactly-once。
把假服務全部資料渲染給每個角色；通知內容直接當最終庫存。
隱藏按鈕就表示安全，原型載入管理金鑰以便串接正式服務。
```

# Rule 4 - 無障礙與響應配置落在可操作內容

- Level: `MUST`
- 使用語意 HTML、可辨識名稱及對應 label；錯誤文字與欄位關聯。提供可見焦點與合理鍵盤順序，表單可用 Enter 提交；驗證失敗定位第一個錯誤，重繪後保留或移至合理焦點，避免使用者失去操作位置。
- 載入、拒絕、未知及恢復用文字和適用 live status 傳達，不只改顏色；停用操作須有可理解原因。只有實際用讀屏執行過才可稱讀屏驗證通過。
- 依指定裝置、觸控及放大文字檢查內容順序、長文／數字換行與主要操作；窄畫面可調整排列，但不得遮蔽必要資訊或使主要操作依賴水平捲動。無既有尺寸規範時採可用的首輪寬度並註明實測範圍。
- 互動控制具足夠觸控面積，預設至少 44 CSS px；若專案已有規範依其驗證。實際文字字形、前景／背景對比、錯誤訊息及 reduced-motion 行為需檢查，純色票推薦不等於通過。

## Good Example

```md
輸入錯誤以 aria-describedby 關聯，焦點回到該欄位；結果區有文字與 live status。
390px 排成單欄，主要操作及完整拒絕原因無水平溢出；已以鍵盤完成提交。
未執行讀屏，故僅記語意與鍵盤檢查通過，保留正式讀屏驗證。
```

## Bad Example

```md
支援 RWD、無障礙；失敗變紅、成功變綠。
以點擊 div 作主要操作且無鍵盤處理；只看桌面截圖就宣稱所有裝置、讀屏皆通過。
```

# Rule 5 - 簡短紀錄保留開發者真正需要的差異

- Level: `MUST`
- Markdown 提供實際 HTML 入口、自由操作／導覽方式、畫面意圖與狀態、少量契約位置、模擬限制及本次檢查；有重大視覺選擇才記來源與理由，不重新抄錄全部畫面文字、欄位 Schema 或業務規格。
- 共用未決引用 Plan 並只補 UI 局部影響；無 Plan 時在此保留必要未決、接手責任及處理時點。缺少必要決策只阻塞相關結論，明示可獨立使用部分。
- 檢查紀錄只寫本輪真正執行的內容與結果。範例過往 lint、瀏覽器、版本與裝置數據可作案例背景，不得抄為新產物證據。不要另建交接報告、Pencil 檔或固定預覽圖。

## Good Example

```md
入口：[prototype](ui/index.html)。主要操作與拒絕可在原型直接試用。
API 的 x-interfaces 定義恢復語意；欄位與狀態以該契約為準。
Plan U2 未定保留期限；原型不新增自動刪除。今日實測窄畫面與鍵盤，未測真實服務。
```

## Bad Example

```md
把 API 與資料欄位整份抄進文件，再新增三份下游交接表。
範例曾通過瀏覽器測試，所以本次也全數通過；實際 HTML 尚未開啟。
```
