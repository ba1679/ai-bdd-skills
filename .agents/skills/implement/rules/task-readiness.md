# Rule 1 - 開工條件由真實相依與產物可用性決定

- Level: `MUST`
- 比對 Task 的規則版本、領域契約與上游就緒結果。若憲法變動使必要契約尚待修正，保留該依賴未就緒並交回原主責。已定案契約仍缺執行證據時，依任務分工驗證。
- 任務須有可定位落點、動作及可觀察完成條件；前置 ID 存在、無循環，任務文字、相依圖與批次安排一致。矛盾未解時，受影響工作保持阻擋，其他獨立工作可繼續。
- 前置可用性須核對消費的實際成果：契約與型別、schema／migration、fixture／可信身分、被呼叫實作、正式接線及驗收紀錄；前置有勾選但成果缺失或不相容時，不視為就緒。
- 標示由前置任務產生的文件，在建立者完成並有實際產物後才查閱；空檔、目錄或計畫中的路徑不是已可用成果。
- 階段標題、故事優先級與清單排列不自動形成全階段相依；明確指定的交付順序及檢查點仍須遵守。隔離 fixture 能獨立驗證，不代表正式接線無相依。
- 可由已確認來源修正的任務缺漏可局部修正；會改變產品決策的缺口交回主 SOP 的澄清分支，不自行填造政策。

## Good Example

```md
T012 的隔離元件可先驗證；正式頁面接線 T014 等待 T009 的真實路由。
T015 讀取 T014 產生的驗收紀錄，只有紀錄實際建立後才核對。
T009 阻擋時，無共用寫入或產物相依的 T011 可繼續。
```

## Bad Example

```md
US2 優先級較低，所以等全部 US1 做完；不必查真正前置。
T009 已勾選，即使路由尚未註冊，也直接開始正式頁面驗收。
規劃列了驗收紀錄路徑，所以把該紀錄當成已存在。
```

# Rule 2 - 閱讀指引須承接足以實作的完整約束

- Level: `MUST`
- Must Read 的指定區段須在實作前掌握；逐項判定 Optional 的具體觸發條件，成立即必讀。輸入索引供定位，不代替任務閱讀指引，也不要求預讀所有文件。
- Markdown 沿語意章節及適用 US／AC／FR／NFR／成功標準定位；OpenAPI 核對 method＋path、operationId、參數、requestBody、成功及錯誤 responses，沿必要 `$ref` 追到具名定義及相關擴充約束。
- 資料責任須涵蓋相關表、欄位、FK、index、唯一性及交易／歸屬／生命週期 Notes；介面責任須涵蓋操作、角色、載入、變更、成功、明確拒絕、未知結果及恢復，以及適用的焦點、可及性與版面要求。
- 未確認結果與明確拒絕分別處理；來源要求停止新變更、重讀或禁止重送時，須保留該約束。格式與擴充名稱以真實來源為準，不憑範例補造 API、資料庫或政策。
- 已讀、未變更且仍在上下文的區段可沿用；來源改版、版本不確定或上下文遺失時重讀。引用失效或來源衝突須揭露，程式現況不能擅自取代已確認契約。

## Good Example

```md
移動項目任務讀取 PATCH 操作、輸入 schema、409 回覆及 x-recovery。
UI Optional 的「未知結果恢復」條件成立，補讀逾時後停止變更與重讀政策。
列鎖任務讀取表的唯一 index 及交易 Notes，不只看欄位列表。
```

## Bad Example

```md
只讀操作摘要；授權與交易在共用定義中，太長所以跳過。
Optional 一律不讀；所有請求逾時都自動重送，避免卡住。
```

# Rule 3 - 平行安全須在所有寫入前確認

- Level: `MUST`
- `[P]` 只表示特定前置與批次下可平行；每次派工前重新核對產物等待及完整實際寫入集合。
- 集合包含主要程式、測試、共用型別、設定、migration 序列、生成檔、lockfile 及開發／驗收紀錄；同檔不同函式或區段仍是共享寫入。檔案不同但共享資料庫、fixture 或其他可變資源時，也須確認隔離或序列化。
- 有共享寫入或產物相依時預設序列執行；契約足以支援獨立實作時可拆出互不干擾的部分，再按明確順序整合。
- 實際修改超出原集合時，須先重新判定安全再寫入；不能等衝突出現後才協調。
- 平行是可選執行方式，不因 `[P]` 自動啟動多代理；採平行時須有明確責任、寫入邊界、整合順序及任務狀態回寫者。

## Good Example

```md
T006 與 T007 各改不同測試，但共寫 validation.md，故紀錄回寫序列化。
T008 預計修改共用型別，先暫停該寫入並重排批次，再進行修改。
```

## Bad Example

```md
看到 [P] 就同時開工；兩個任務改同一設定的不同區段，所以沒有衝突。
先覆寫共用紀錄，最後再設法合併。
```
