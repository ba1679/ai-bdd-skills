# Rule 1 - 驗證選擇須對應責任、來源與實際風險

- Level: `MUST`
- 依規則的適用範圍和通過判準決定驗證層級。規則只約束上游文件時承接其檢查結果，實作驗證依任務指定的已定案契約執行。需要真實執行結果時，取實際回應、資料庫結果或其他指定證據。
- 承接 Tasks 與來源指定的驗證及完成條件，再依變更影響選擇必要層級；基線使用可用的相關既有檢查。工具或依賴未就緒時，先依本檔環境準備與連線恢復規則處理，再選取可執行檢查；不把未執行算通過。
- 依適用性核對以下維度，省略無關層但不省略必要證明：
  - 邏輯／元件：預設值、轉換、邊界、不變性、互動及狀態分支。
  - 資料：真實約束、歸屬、migration、並行、鎖定、交易及 rollback。
  - 服務／契約：正式路由、可信身分、參數與 body、成功及錯誤回覆、拒絕後資料不變與敏感資料邊界。
  - 正式頁面／整合：真實接線、主要使用路徑、明確拒絕、未知結果恢復、保存／重新整理，以及適用鍵盤、焦點、可及性及版面。
  - 跨任務品質：相關型別檢查、lint、建置、受影響既有行為、來源 NFR 與成功標準；性能門檻及覆蓋率沿用已確認要求，不自行發明數值。
- 驗證正常、邊界、拒絕、失敗及恢復等適用分支。測試層多不等於充分，數量少也不能作為略過必要邊界的理由。
- mock／stub 只證明其涵蓋範圍，不能證明真實 DB 約束、交易、並行及正式接線；單元測試不替代必要故事驗收或版面檢查。

## Good Example

```md
排序 repository 用真實測試 DB 驗證唯一位置、並行與 rollback。
頁面驗收透過正式路由核對成功、拒絕及遺失回覆後重讀。
純記憶體篩選只驗證邏輯、切換與鍵盤，不新增 DB 或壓力測試。
```

## Bad Example

```md
mock repository 通過，所以宣稱列鎖、HTTP 授權與正式頁面都通過。
只改顯示文字也強制建立整套端到端測試平台。
```

# Rule 2 - 測試順序及修錯須能證明目標行為

- Level: `MUST`
- 使用者、來源或 Tasks 要求測試先行時，先建立並執行測試，確認因缺少目標行為而失敗，再實作至通過；語法錯誤或缺依賴不能當作預期行為失敗。
- 其他情況依前置及風險選擇順序，不強制所有工作全面 TDD。bug 修復在適用時先保留最小重現並加入回歸；不能自動化的案例保存可重現操作及結果。
- 失敗判讀須區分：基線已存在的問題、本次變更新增或加劇的回歸、環境／工具／外部服務阻擋。原有失敗不自動豁免；若阻擋本輪必要證明，仍須保持未驗證。
- 定位須利用錯誤輸出、堆疊、變更差異及最小重現形成可核對原因，再修改相應責任並重跑受影響檢查；修復不能以無關大改替代診斷。
- 不以刪除測試、放寬有效斷言、停用檢查或吞錯換取通過。來源已確認變更使舊測試失效時，可依新契約更新測試並記錄依據，不把需求變更偽裝成單純修錯。

## Good Example

```md
回歸測試先重現拒絕時資料仍被寫入；修正交易邊界後通過，再跑相關路由測試。
測試 DB 無法連線：先檢查本機服務、連線設定與必要工具，啟動可自行啟動的服務後重驗；仍受外部條件限制才記錄阻擋。
```

## Bad Example

```md
測試因 import 失敗而紅，視為已完成測試先行。
把拒絕後資料不變的斷言刪掉，讓測試通過。
```

# Rule 3 - 驗收須對應增量與最終版本

- Level: `MUST`
- 故事驗收須等待其實作及正式接線成果可用；入口、fixture、操作、預期結果及所需依賴依 Tasks 及來源核對，通過的是指定需求增量，不泛稱全產品完成。
- 最終品質證據須適用於最後整合版本，覆蓋本輪適用需求、AC／FR／NFR／成功標準或等價條件；跨故事檢查不能由各自隔離通過推定。
- 後續修改後依受影響契約、呼叫端與共享實作選擇回歸；已通過且未受影響的檢查可沿用。只在新修改、失敗或未解疑慮有依據時擴大或重複驗證。
- 本規則提供驗證判準；任務勾選、證據紀錄及失效狀態由主 SOP 已載入的證據規則判定，不另定完成標準。

## Good Example

```md
US1 接線就緒即驗收；US2 後來改了共用錯誤映射，再驗 US1 的相關拒絕與恢復分支。
最終版本另執行來源要求的跨故事流程與建置。
```

## Bad Example

```md
兩個隔離元件都通過，所以不必驗證正式頁面接線。
最後改了共用契約，仍使用修改前的結果宣稱最終版本通過。
```

# Rule 4 - 必要工具與依賴由實作者主動準備

- Level: `MUST`
- 將本輪實作與驗證所需的 runtime、套件、CLI、瀏覽器及本機服務視為執行範圍。先辨識既有工具、版本與專案安裝方式；對來源可信、權限與副作用可接受的必要安裝或啟動，自行完成並接續驗證，不因「尚未安裝」就要求使用者代辦或宣告阻擋。
- 優先使用專案內依賴、隔離環境或使用者層級安裝；沿用已確認的技術與版本約束，保留其他專案及系統設定。查核官方套件身分、相容版本與安裝行為，以實際權限、安裝腳本及寫入範圍判斷風險，不以絕對零風險作為開工條件。
- 安裝指令由專案 manifest、lockfile 與套件管理器決定。例如 npm 專案初次建立或授權變更依賴時用 `npm install` 產生／更新 lockfile，既有一致 lockfile 用 `npm ci` 重現安裝；保留必要開發依賴供建置與測試。遇版本或 lockfile 衝突先定位原因，不盲目刪 lockfile、強制升版或假造完整性資料。
- 驗證 CLI 可執行、版本正確、必要服務健康及正式程式可載入，再回到原任務檢查；本機替身、借用其他專案套件或離線快取只能支持其實際驗證範圍，不能當作乾淨安裝已可重現。
- 只有剩餘操作確實涉及尚未授權的系統權限／系統範圍變更、付費、帳號操作、憑證或無法取得的外部資源時，才提出具體需求。先確認本機方案能否完成驗收，不將本機 CLI 或服務誤當成必須先申請雲端帳號。

## Good Example

```md
專案已選定某服務 CLI，但本機尚未安裝：查核官方來源與相容版本，加入專案開發依賴，完成安裝、版本檢查及本機服務啟動，再跑原本的整合測試。
既有 npm lockfile 與 manifest 一致：執行 npm ci 安裝完整開發依賴，不要求使用者先手動安裝 CLI。
```

## Bad Example

```md
找不到 CLI，直接結束並要求使用者自行安裝或申請雲端帳號。
用另一個專案的 node_modules 符號連結跑過測試，便宣稱本專案的依賴已完整安裝。
```

# Rule 5 - 連線失敗須經診斷與有界恢復才判定阻擋

- Level: `MUST`
- 下載、安裝或服務連線失敗時，先保存去敏後的錯誤、目標及執行環境，區分名稱解析、連線逾時、TLS、代理、認證／限流、套件不存在與版本衝突。工具的 cache miss 或離線 ETARGET 只表示本機資料不足，不證明遠端版本不存在。
- 用最小探測縮小範圍：比對目標與另一個相關官方來源是否可連、檢查實際 registry／代理設定及系統名稱解析；有差異時再依證據查 DNS、IPv4／IPv6 或程序環境。診斷範圍隨證據調整，不把第一次 timeout 或一個工具失敗直接等同於整台電腦無網路。
- 對短暫故障作有限次、帶退避且有逾時的重試；同樣失敗後改變有證據支持的診斷或恢復方式，不無限重送相同指令。優先採可還原、僅影響該程序或專案的修正、官方替代下載路徑或可驗證的既有快取，成功後重跑原始安裝與必要檢查。
- 保留 TLS 憑證與套件完整性驗證，遵守既有網路存取政策。修復不得靠關閉安全驗證、任意換不可信鏡像、繞過明確存取限制，或未授權改寫全機 DNS／代理／hosts；輸出不得洩漏代理密碼、token 或私密 registry 憑證。
- 只有合理且已授權的修復路徑已實際嘗試仍失敗，或有具體證據表明剩餘步驟需外部操作，才標記環境阻擋。記錄已確認原因與仍未知之處、已試方式及結果、受影響 Task ID、解除條件及恢復後第一個驗證指令；可獨立完成的工作繼續執行。

## Good Example

```md
registry 逾時，但另一官方網站可連；系統名稱解析與 DNS 查詢結果不同。以保留 TLS 驗證的程序級探測確認目標可達，採可還原的安裝方式重試，成功後產生真實 lockfile 並跑原驗證。
私有 registry 明確回覆 401，既有憑證未配置；其他公開依賴已完成。僅列出受影響任務與需要的登入步驟，不要求使用者貼出 token。
```

## Bad Example

```md
npm install timeout 一次，所以標記所有驗收為外部阻擋並交付。
反覆跑同一個無逾時指令，或關閉 TLS 憑證檢查讓下載成功。
```
