# Rule 1 - 證據須可定位且足以重現

- Level: `MUST`
- 公開可覆寫項目 `implementation-report-layout` 涵蓋交付紀錄的分組與呈現。實際驗證方式、版本、結果及限制仍須可追溯。
- 證據保存於 Tasks 指定的開發／驗證紀錄；未指定時沿用專案慣例，沒有慣例才在 Tasks 附近保存最小紀錄。可共同維護一份文件，不為每項任務新增文件或固定模板。
- 每個任務須可對應 Task ID、實際變更及檔案、驗證指令或操作步驟、必要環境／fixture、實際結果、證據位置及限制；可引用同一份已有紀錄，不重複抄寫。
- 證據須能辨識被驗證版本，例如 commit，或未提交差異範圍加紀錄時間；後續修改後須能判斷證據適用範圍。紀錄時間使用使用者時區。
- 自動檢查記錄可重跑指令與通過／失敗結果；人工檢查記錄入口、操作、預期及實際觀察。錯誤須保留必要上下文，紀錄不得暴露憑證、token 或敏感 fixture 資料。
- 未執行、失敗及因外部條件無法驗證，須分別記錄；估計、計畫與來源文件不是實測證據。

## Good Example

```md
T010：修改正式路由及授權檢查；未提交差異限於 route.ts、route.test.ts。
重現：使用測試 A／B session 執行專案既有 contract-test 指令；fixture 由 T003 建立。
結果：成功、越權拒絕及拒絕後資料不變通過；正式頁面驗收仍由 T014 承接。
```

## Bad Example

```md
T010：已測試，一切正常。（沒有指令、操作或結果範圍）
把計畫中的驗收步驟當作已經通過，並將 session token 寫入紀錄。
```

# Rule 2 - 完成標記只承認自身條件與有效證據

- Level: `MUST`
- 憲法驗證證據須可定位規則 ID、版本、適用的 Task ID 與實際產物。規則或附件變更後，核對條件差異並只失效需要重驗的證據。
- 任務只有在自身完成條件、必要來源及所需驗證皆有有效成果支持時才勾選；來源缺失、檢查未執行、失敗或必要證明受阻時保持未完成。
- 按任務責任判定，實作任務可在其自身必要驗證通過後完成；另列的故事驗收任務及檢查點須有各自證據。不得以局部實作勾選推定整個故事完成。
- 初次接手與恢復時核對既有勾選及證據；保留仍有效的 Task ID、狀態與紀錄。契約、程式、fixture 或驗證方式變更使證據失效時，標示原因、受影響任務及重驗範圍，恢復相關任務未完成。
- 證據失效以實際影響判定，不清空全部狀態，也不盲目沿用全部勾選；被消費的前置成果失效時須檢查下游任務。

## Good Example

```md
T008 的 repository 實作及必要 DB 測試通過，勾選 T008；正式頁面驗收 T012 尚未執行，保持未完成。
共用錯誤 schema 改變：T009、T012 恢復未完成並註記需重驗；未受影響的 T003 保留完成。
```

## Bad Example

```md
所有程式檔都建立了，將實作、接線、故事驗收一起勾選。
檢查無法執行但應該會過，仍標示完成。
```

# Rule 3 - 任務更新與交付須保留真實完成範圍

- Level: `MUST`
- 由已確認來源可確定的必要漏項可局部補入 Tasks，指定明確落點、來源、前置與完成條件；新增 ID 不衝突且保持未完成。更新相依與統計，保留既有有效 ID 及證據，不重新生成整份清單。
- 涉及新增能力、政策或驗收決策的缺口不以補任務擅自決定，交回主 SOP 的澄清分支。
- 全部本輪必要任務、檢查點及最終版本驗證皆有有效證據，才可宣稱本輪完成；因外部阻擋而交付時須明示部分完成、受影響 Task ID、未通過／未執行項與解除條件。
- 報告須區分實際驗證、mock 涵蓋範圍、人工尚待檢查及外部限制；不承諾零 bugs，不以任務數量或通過比例代替必要完成條件。

## Good Example

```md
來源已明定逾時後重讀，清單漏列：新增 T019 接線與恢復驗收，更新相依及統計後執行。
交付：T003～T018 完成；T019 因測試服務不可用未驗證，保持未完成，列出重現指令及解除條件。
```

## Bad Example

```md
為補清單缺口自行新增自動重送政策，並重編全部 ID。
通過率 95%，其餘都是環境問題，所以宣稱全部完成、沒有 bugs。
```
