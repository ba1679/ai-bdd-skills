# Rule 1 - 任務分組必須來自需求增量與實際責任

- Level: `MUST`
- 每個故事或需求增量都必須能對照來源中的目標、適用 AC／FR，以及影響本輪的 NFR／成功標準。來源只有完整文字需求時，以需求增量建立可追溯分組；可新建本地故事標記，但必須明示由本輪整理，不能假稱來源已有 US／FR 編號，也不為配合模板硬造故事。
- 對每個增量核對以下責任，僅保留本輪確實有工作的項目：
  - 資料：模型／約束、讀寫、交易、歸屬與生命週期的實作。
  - 服務：輸入／輸出契約、授權邊界、錯誤映射與既有服務接線。
  - 介面：呈現、互動、非同步狀態、恢復、可及性及頁面接線。
  - 驗證與交付：適用測試、故事整合驗收、必要回歸與可重現證據。
- 各責任必須對應當前專案的檔案落點或可定位對象；分組可以跨檔案，亦可在同一檔案承接多個故事。來源決定的責任比「前端／後端」名稱更重要。
- 純前端、腳本或其他單一責任需求仍須有適用的驗證與故事整合驗收；無需為湊齊端別新增 API、資料庫、登入或部署。
- 故事數、階段數、端數、技術與任務數由實際工作決定；範例的旅遊情境與 22 項任務僅示範寫法。
- 來源充分性及未定政策交由已載入的來源缺口規則判定；本規則只將可拆解的決策轉成工作。

## Good Example

- 一個純前端增量已涵蓋它真正需要的責任。

```md
需求增量：只看未完成（本輪整理的分組；來源沒有 US／FR 編號）；預設關閉、取消恢復全部、原清單不變、重新整理重置。
責任：filter.ts 的衍生清單、view.ts 的 checkbox／空狀態／live status、既有頁面接線。
驗證：純函式覆蓋切換與不變性；正式頁面覆蓋鍵盤、取消與重新整理。
不新增保存機制或服務端任務，因本輪行為僅限頁面生命週期。
```

## Bad Example

- 以範例外觀取代本案責任分析，產生沒有來源依據的工作。

```md
需求雖然只有前端篩選，仍固定拆兩個故事、五個階段及 22 項。
每個故事都建立資料表、HTTP API、登入、前端與部署任務。
```

# Rule 2 - 每項任務必須有動作、落點與可觀察完成條件

- Level: `MUST`
- 任務必須說明做什麼、改哪個真實路徑或可定位對象，以及完成後可觀察到什麼。落點為計畫中新檔案時，明示要建立；已有檔案則沿用查得的落點與路徑基準。
- 完成條件必須描述適用的行為、介面、資料不變條件或可驗證產出，例如「保留輸入並聚焦欄位」「變更及清單查詢同交易，失敗全部 rollback」。僅寫「完成」「可用」「測試通過」不足以判定責任是否完成。
- 同一任務可以修改多個檔案，只要它們共同產生一項明確成果；不得機械地按一個檔案、一個按鈕或來源操作清單各造一個任務。
- 出現以下情況時，拆分具有實際價值：
  - 一項成果是後續工作的前置契約或產物，可獨立完成與核對。
  - 責任、驗證入口或執行者不同，拆開能明確交接與定位失敗。
  - 實作與正式接線有不同前置，合併會掩蓋等待條件。
  - 一項任務混入互不相干的行為或風險，無法以一組明確完成條件評估。
- 拆分後各任務仍須有實質成果；反之，只有同一行為的細碎操作、重複驗證或無獨立意義的檔案建立，應合併。

## Good Example

- 同一責任的多檔案工作可合併，正式接線因前置不同而另列。

```md
- [ ] T010 在 api.ts、view.ts、styles.css 建立新增 client、輸入與清單呈現；提供事件回呼，無效輸入保留文字，空清單顯示指定提示。
- [ ] T011 在 pages/day-itinerary.ts 接上目前日期與正式 API；成功採用完整清單，連線結果未確認時停用新變更並提供重新讀取。
T011 依賴 T010 及已接通的服務操作。
```

## Bad Example

- 前者沒有可驗收責任，後者細分也沒有帶來可交接成果。

```md
- [ ] T010 完成前端，測試通過。
- [ ] T011 建立 view.ts。
- [ ] T012 加一個輸入框。
- [ ] T013 加提交按鈕。
- [ ] T014 把輸入框和按鈕放在一起。
```

# Rule 3 - 共用前置只容納真正阻擋增量的工作

- Level: `MUST`
- Setup 僅包含本輪缺少的工具、目錄、啟動入口、隔離環境或重現指令；既有工具、登入與基礎資料可沿用時，任務描述應指定沿用而非重建。
- Foundation 僅包含多個增量共用且確實構成前置的契約、資料骨架、可信身分邊界或其他基礎；只服務單一增量的實作應留在該增量。
- 共用與故事工作以「誰消費哪個產出」區分，不以名稱或模板階段決定。未經工作分析，不把全部資料／服務實作塞入 Foundation，也不讓所有故事等待無關基礎。
- 前置任務須有明確產物與完成條件；消費者須能找到建立者與可用時點。空目錄、未填紀錄或尚未接線的元件不能被視為功能已可用。
- 開發指令、fixture、驗收紀錄若由本輪任務建立，應安排建立／寫入工作與消費相依；它們不是生成任務當下已存在的證據。

## Good Example

- 共用資料與契約先建立，業務行為留在各故事；既有帳號系統僅供使用。

```md
Setup：建立本輪隔離 fixture 與測試指令，沿用既有 session。
Foundation：共用 DTO、日期歸屬入口及 day_items schema。
新增故事：list／add 實作、正式接線與驗收。
排序故事：move／remove 實作、正式接線與驗收。
驗收紀錄由故事驗收任務寫入，交付核對任務等待這些紀錄。
```

## Bad Example

- Foundation 變成全部實作的容器，且把尚未產生的紀錄當成現況。

```md
Foundation：重建登入，完成所有故事的資料、API、畫面與驗收。
故事階段：各寫一句「確認功能正常」。
交付核對：直接引用尚無建立任務的 docs/validation/result.md 作已通過證據。
```

# Rule 4 - 驗證工作須覆蓋實際風險與整合邊界

- Level: `MUST`
- 驗證層由來源要求、變更責任與風險決定；已有來源指定測試落點及驗證層時須承接。依適用性核對：
  - 純邏輯／元件：轉換、預設值、不變性、邊界、互動及狀態分支。
  - 資料：實際約束、歸屬、並行、鎖定、交易與 rollback；記憶體替身不足以證明資料庫行為。
  - 服務／契約：正式路由、可信身分、參數與 body、成功及錯誤回覆、拒絕後資料不變與敏感資訊邊界。
  - 正式頁面／跨責任整合：真正接線、使用者主要路徑、錯誤及未知結果恢復、重新整理或保存結果，以及適用可及性與版面。
  - 回歸與交付：變更影響的既有行為、來源成功標準及足以重現結果的指令／紀錄。
- 每個故事須有能觀察其需求增量的驗證入口及檢查點。沒有跨端工作時，以適用的故事整合驗收確認完成，無需製造跨端測試。
- 不為每個小改動強制建立所有層、重複既有測試或全套基礎建設；選擇的驗證仍須覆蓋會失真的行為與邊界。
- 來源或使用者要求測試先行時，明確安排測試建立、預期失敗及實作通過的次序；否則依工作前置安排，不從範例推導所有需求皆須先測。
- 測試通過只證明其涵蓋範圍；必要的型別檢查、建置、正式接線、人工版面／讀屏核對或實測紀錄仍須各有工作與證據。任務規劃時只列出要執行的驗證，不預報成功。

## Good Example

- 針對不同責任採用能證明該責任的工具，整合檢查另有完成訊號。

```md
資料任務：真實測試 PostgreSQL 驗證同日位置唯一、列鎖序列化及 rollback。
契約任務：透過正式 routes 與 A／B session 驗證成功、拒絕及資料不變。
故事驗收：操作正式頁面，驗證重新整理與遺失回覆時不自動重送；記錄結果。
純前端篩選：單元測試涵蓋不變性，頁面測試涵蓋切換／取消／重整與鍵盤，不新增資料庫測試。
```

## Bad Example

- 替身通過被擴張為未驗證邊界的證據，另一小需求又被強塞全套工作。

```md
mock repository 的單元測試通過，即認定列鎖、HTTP 授權與正式頁面都已通過。
只改 checkbox 篩選，也必須先建立 DB、HTTP、壓力與部署測試才可實作。
```

# Rule 5 - 相依須由產物、接線與修改衝突證明

- Level: `MUST`
- 每條相依須能指出消費的產物或需等待的工作，按以下維度核對：
  - 契約：型別、介面、參數與錯誤形狀是否已足以供消費者開工。
  - 資料：schema、migration、fixture、身分或初始化資料是否已可用。
  - 實作產物：被呼叫的函式、元件、路由或工具入口是否已有相容成果。
  - 正式接線：元件可用與接入正式服務／頁面是不同完成條件，後者須等待實際供應者。
  - 共用寫入：同一檔案、遷移序列、共用產物或驗收紀錄的修改是否需要先後順序。
  - 驗收證據：整合驗收等待其實作與接線；交付核對等待必要驗證紀錄。
- 優先級表示交付次序，不能單憑 P0／P1 或故事排列宣告技術相依；若確有共享實作或修改衝突，指出具體依據。
- fixture、stub 或隔離入口能使某故事獨立驗證，不代表該故事的正式接線獨立於共用 repository、routes 或頁面。獨立驗證條件與正式整合前置須分別寫清楚。
- 不憑假定全階段障礙隱藏可平行工作；若採整個故事完成後再開下一故事的保守順序，須能以共用寫入、接線基線或明確交付策略解釋。
- 依賴對象須存在且可達；相依關係須無環。形成環時檢查是否把共用契約、互相接線或驗收混入同一工作，拆出真正前置後再排順序。

## Good Example

- 將可用 fixture 與正式接線分開描述，依賴各有原因。

```md
排序可用三筆 fixture 獨立驗證，不必操作新增表單。
排序 repository 修改同一 repository.ts，等待新增 repository 基線完成。
排序 routes 等待排序 repository 及契約測試；頁面接線等待 API 與控制元件。
故事驗收等待正式頁面接線，交付核對等待驗收紀錄。
```

## Bad Example

- 優先級與隔離驗證被誤當依賴證明。

```md
US2 是 P1，所以必定依賴所有 P0 任務，無須指出產物。
US2 有 fixture，所以可與 US1 同時重寫 repository.ts、routes.ts 及正式頁面。
```

# Rule 6 - 平行標記必須通過前置與實際寫入集合核對

- Level: `MUST`
- `[P]` 表示在所述批次前置滿足後，可與該批其他工作安全並行，不表示從任意時點獨立執行。
- 判定平行時須列清楚每項任務實際會寫入的集合，包含主要程式、測試、共用型別、migration、生成檔、設定與證據紀錄；同一檔案不同函式、不同故事或不同區段仍是共享寫入。
- 同批工作若共改 repository、routes、view、頁面入口、migration 序列或驗收紀錄，預設序列化；可先拆出不改共享產物的獨立部分，再安排整合任務。不得只看任務主要檔名不同便標記平行。
- 即使寫入集合互不相交，若一項工作需要另一項尚未產生的型別、資料或正式接線，也不能在同批直接執行；已確認契約可支持各自實作時，清楚標出其共同前置。
- 相依圖、文字順序、平行批次範例與 `[P]` 必須描述同一安排。高層圖可合併任務，但不能暗示與詳列前置相衝突的同時開工；圖不得存在循環。

## Good Example

- 平行批次有共同前置且寫入集合互不重疊，共享紀錄留至整合時更新。

```md
共同前置：DTO、schema 與測試 fixture 已就緒。
同批：資料測試寫 tests/database/day-items.test.ts；契約測試寫 tests/contract/day-items.test.ts；呈現元件寫 view.ts／styles.css。
接線等待正式 repository 與 API；整合驗收最後更新 docs/validation/day-items.md。
```

## Bad Example

- 主路徑不同掩蓋共享寫入與尚未可用的正式接線。

```md
T010 [P] 修改 view.ts，順便更新 pages/day-itinerary.ts 與 validation.md。
T011 [P] 修改 api.ts，順便更新同一 pages/day-itinerary.ts 與 validation.md。
兩者可同批，因任務標題列的檔名不同，且 API 預計稍後才建立。
```

# Rule 7 - 檢查點必須證明需求覆蓋與可展示增量

- Level: `MUST`
- 任務集合須覆蓋本輪來源中的故事／需求、適用 AC／FR／NFR／成功標準；每項需求須能找到承擔實作與必要驗證的工作，不能僅因在來源索引出現就算覆蓋。
- 故事檢查點須指出可展示的行為、驗證入口及必要前置。檢查點應區分共用基線成立、隔離驗證成立、正式整合成立與交付證據齊備。
- 可展示增量以使用者或消費者能觀察的成果定義；「完成所有檔案」「測試已建立」不足以表示功能完成。
- 工作交接需要的指令、fixture、紀錄或其他前置證據須有產出任務及消費時點。已建立、已執行及已通過是不同狀態，僅能在後續執行時依實際證據判定。
- 交付檢查須能核對仍需的既有能力、未通過或尚待執行項目；本 Skill 產生的任務文件不構成產品已實作或已驗收的證據。
- 精確引用格式與任務文件的 ID／統計／狀態品質，交由對應閱讀與品質規則維護；本規則的覆蓋要求聚焦是否真的有工作承接需求。

## Good Example

- 檢查點包含行為與證明方式，且對階段能力作出精確界定。

```md
Foundation 檢查點：共用 schema 與型別可用，尚未證明景點操作。
新增故事檢查點：以 A 的空日期在正式頁面新增兩筆、重新整理保留；無 session 與 B 拒絕且資料不變，資料／契約／頁面證據已由驗收任務記錄。
排序故事檢查點：以三筆 fixture 驗證相鄰移動、同名指定刪除及刪光空狀態；正式接線另等待共用頁面基線。
```

## Bad Example

- 來源有列入，卻沒有實作、驗證或前置證據能支撐完成宣稱。

```md
來源索引已含所有 FR，所以覆蓋完成。
檢查點：檔案都列完，所有功能已驗收。
即使跨擁有者拒絕及網路結果未知沒有對應工作，也由一般 happy path 測試代替。
```
