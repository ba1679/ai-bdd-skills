# Rule 1 - 每項任務的閱讀指引必須有來源、語意定位與當前用途

- Level: `MUST`
- 每項任務依其行為、介面、約束及完成條件，選取最小且足夠的來源區段；每筆引用同時提供文件位置、可辨識的語意定位及本任務使用它的目的。
- 輸入索引只供尋找來源，不能取代逐任務閱讀指引；不得讓所有任務一律閱讀整份 spec、所有端點或完整分析索引。
- 同一任務可引用多筆必要來源；同一文件的相關位置可合併一列，但各區段與用途仍須清楚。只有任務本身核對全體需求時，才使用對應的完整需求章節。
- 行號可輔助已核對的章節、需求 ID、操作或欄位名稱，不能單獨承擔容易隨編輯失準的定位。

## Good Example

- 指定變更介面及用途，執行者可直接找到本任務需要的約束。

```md
T009 在 server/features/stops/routes.ts 接上新增操作，通過契約測試。
Must Read：specs/stops/api.openapi.yaml 的 POST /days/{dayId}/stops
（addStop）、該 path 的 parameters、AddStopInput、StopList 及適用錯誤 responses。
用途：核對日期參數、名稱驗證、201 回覆及拒絕結果的映射。
```

## Bad Example

- 全檔索引與裸行號都無法說明當前任務要採用的契約。

```md
所有任務必讀：spec.md、plan.md、api.openapi.yaml、data-model.dbml、ui-plan.md。
T009 參考 API 第 80～160 行，照文件完成。
```

# Rule 2 - Must Read 與 Optional 由當前任務的需要決定

- Level: `MUST`
- Must Read／必讀承載執行任務前須掌握的當前行為、介面及技術約束。影響正確實作的授權、交易、資料一致性、錯誤或恢復政策，必須放在必讀或可明確沿用的既有必讀上下文。
- Optional／按需讀取必須同時列出具體觸發條件、來源位置及讀取用途；條件成立時即須讀取，不能視為可任意忽略的建議。「有需要時」不構成可判定的觸發條件。
- 以任務而非文件分類；同一 UI 文件在呈現任務可為必讀，在僅檢查資料持久化的驗收任務則可依版面或焦點回歸觸發讀取。
- 已讀、未變更且仍在上下文中的區段可沿用；來源變更、版本不確定或上下文遺失時重讀。沿用閱讀不表示刪除任務文件中供後續執行者使用的來源定位。

## Good Example

- 同一來源依責任分級，按需條件可觀察，核心恢復政策保留為必讀。

```md
呈現任務 Must Read：analysis/ui-plan.md「新增表單」「焦點」；用途：建立操作及焦點行為。
驗收任務 Must Read：analysis/api.openapi.yaml 的 x-recovery；用途：檢查遺失回覆後不重送。
驗收任務 Optional：analysis/ui-plan.md「焦點」。
觸發：瀏覽器測試發現移除後焦點回歸時；用途：確認應回到下一筆、前一筆或輸入框。
```

## Bad Example

- 把本任務不可缺少的政策推遲到任意觸發，會讓不同執行者產生不同產品行為。

```md
接線任務 Optional：API 的 x-recovery，有需要再看。
所有任務一律將 ui-plan.md 列 Optional，因為 UI 文件只是參考。
來源已改版，但之前讀過，所以不必重讀。
```

# Rule 3 - Markdown 與 API 引用必須保留可實作的契約粒度

- Level: `MUST`
- Markdown 來源使用實際章節及適用的 US、AC、FR、NFR、SC 等編號；沒有這些編號時使用可定位的小節或具體條列，不替來源創造編號或格式。
- OpenAPI 以 method＋path 定位操作；來源存在 operationId 時一併保留或清楚對應。只寫「新增 API」或只指整個 paths 不足以定位。
- 依任務選取 path／operation 層的 parameters、requestBody、成功及錯誤 responses、具名 schemas／responses，沿必要的 `$ref` 找到影響該任務的定義。不要只讀操作摘要而漏掉輸入限制、額外欄位、識別值、回覆形狀或共用錯誤。
- 同時核對來源實際存在且影響該任務的具名擴充，例如 `x-session` 的可信 caller／歸屬、`x-transaction` 的提交／rollback 邊界、`x-recovery` 的未確認結果／重讀政策；擴充名稱以真實來源為準。
- 以 Markdown 表格提供 API 語意時，引用該小節、method＋path 與實際 DTO／錯誤名稱即可；不要求將它補造為 YAML，也不聲稱完成 YAML 或跨檔 `$ref` 解析驗證。

## Good Example

- 保留操作、輸入、錯誤與跨操作政策，且只涵蓋當前移動任務。

```md
Must Read：analysis/api.openapi.yaml 的 PATCH /days/{dayId}/stops/{stopId}
（moveStop）、path parameters、requestBody、200／400／404／409 responses；
跟隨 MoveStopInput、StopList、Boundary 的 $ref，以及 x-session.ownership、x-recovery.network。
用途：實作方向驗證、歸屬拒絕、邊界回覆及逾時後停止變更。
```

## Bad Example

- 操作的其他端點與名稱靠猜測補入，必要共用契約反而失去定位。

```md
Must Read：API 的全部 paths；新增、刪除、更新應該都差不多。
使用未在來源中出現的 MoveResponse schema，錯誤碼自行選擇。
```

# Rule 4 - 資料與 UI 引用必須涵蓋影響任務的約束及狀態分支

- Level: `MUST`
- DBML 引用實際表、相關欄位、FK、index、唯一性及其他 constraint；涉及授權、列鎖、交易、位置維護或生命週期時，連同對應 Notes 定位，不只列資料表名稱。
- UI 引用實際操作區段、角色可見性或可用操作，以及本任務適用的載入中、變更中、成功、明確拒絕、未知結果與恢復分支；相關可及性、焦點及版面要求亦需定位。
- 未確認結果與明確拒絕不可混為同一錯誤分支；來源若要求停止新變更、重新讀取、核對或禁止自動重送，接線與驗收任務都須掌握相關規則。
- 僅選取真實存在且影響當前任務的格式與分支。純前端記憶體功能不因此增加 DBML、API 或後端工作；來源未定的行為交回缺口處理。

## Good Example

- 來源定位同時解決資料約束與非同步行為，而非只取得欄位外觀。

```md
資料任務 Must Read：analysis/data-model.dbml 的 stops.day_id/position、
stops_day_position_unique、trip_days 的列鎖及交換位置 Notes。
用途：實作同日序列化與交易內位置交換。
接線任務 Must Read：analysis/ui-plan.md「非同步與恢復」的變更中、409、
逾時與重新讀取分支；用途：控制可用操作並保留未確認結果。
```

## Bad Example

- 表名與頁名不能呈現交易、授權及恢復的實作邊界。

```md
資料任務：讀 stops 表。
接線任務：讀行程頁，所有錯誤都重試原請求。
篩選 checkbox 任務：額外要求建立 API 與資料庫，確保模板完整。
```

# Rule 5 - 正式引用須查核存在性，前置產物須揭露建立者

- Level: `MUST`
- 正式任務的生成依據須來自當前專案可查核的需求或契約；逐項核對文件、章節、操作、schema、欄位及必要引用鏈確實存在，且內容足以支持所寫用途。無法解析或讀取的來源保留缺口，不宣稱查核成功。
- `templates/tasks.example.md` 的虛構路徑只示範寫法，無須尋找、補建或追讀；它們不能複製成正式來源，也不能當作當前專案已存在的證據。
- 執行時才由前置任務建立的程式、fixture、開發指令或驗收紀錄，可以列為後續任務的閱讀對象，但須標示建立任務 ID、預期產出、查閱位置及前置關係。
- 區分「來源現已存在」與「前置任務完成後才查閱」；尚待決定的產品契約不能以未來任務會產生它為理由，假定已具備完整可實作決策。其充分性由來源缺口模組把關。

## Good Example

- 未產生的交付紀錄有明確建立者與查閱條件。

```md
T018 前置：T010、T016、T017 完成。
Must Read：docs/validation/stops.md 的 US1／US2 與整體驗收紀錄
（T010、T016、T017 產生）。用途：核對實測結果、重現指令及未通過項目。
目前狀態：紀錄待前置任務建立；本次規劃未讀取或驗證其內容。
```

## Bad Example

- 把未建立的文件及範例假路徑都算成已驗證來源。

```md
已讀取 docs/validation/stops.md，產品測試全部通過。（該檔尚未產生）
正式任務照抄 Example 的 specs/day-itinerary/api.openapi.yaml，無需核對。
```

# Rule 6 - 品質核對必須覆蓋需求、任務與閱讀證據

- Level: `MUST`
- 來源覆蓋：逐項核對本輪故事、AC、FR、NFR、SC 或等價需求，在實作、接線、驗證與檢查點有承接；排除或待確認部分須可辨識，不以任務數量代表覆蓋完整。
- 閱讀可用性：每項任務有本身相關的來源定位與用途；Optional 有可判定觸發，核心約束沒有錯放 Optional；來源存在性及前置產物標示符合 Rule 5。
- 任務可執行性：動作、檔案路徑或可定位對象、責任範圍及可觀察完成訊號清楚；檢查點能由相應任務與驗證產物支持，不只寫「完成功能」「測試正常」。
- 修正僅處理可由既有來源確定的缺漏與不一致；若為了填滿清單必須另定權限、保存或 API 政策，保留缺口並回到受影響階段，不改寫產品需求。

## Good Example

- 核對結果指出缺口與修正依據，能確認品質檢查的實際範圍。

```md
FR-005 的未確認結果已有頁面接線，但原驗收任務漏了回覆遺失案例；
依來源「非同步與恢復」補入該案例及閱讀位置，維持任務未完成。
純前端篩選的取消還原、空結果與原清單不變均有任務及完成訊號承接。
```

## Bad Example

- 數量與格式看似完整，卻沒有查核實際承接關係。

```md
已有 22 項任務，與範例相同，所以需求覆蓋完整。
沒有保存政策，先自行加上 localStorage，避免留下空白。
```

# Rule 7 - 相依表達、識別與文件結構必須一致

- Level: `MUST`
- 相依核對：前置產物的建立者能被找到，任務文字、相依圖、執行順序、平行批次及 `[P]` 同意同一組真實前置；圖無循環。故事層級的概覽箭頭不得掩蓋與逐任務前置衝突的執行限制。
- 平行核對：依任務實際寫入集合與接線等待檢查；共用檔案的修改及證據回寫順序安全。分解與依賴的詳細判定依已載入的 `task-decomposition-and-dependencies.md`，此處核對各種表達是否忠實一致。
- 識別核對：task ID 唯一、前置引用存在、故事標記能映射實際 US／需求；新建清單編號連續。更新清單允許保留既有 ID 的間隔，不為了連續重編而破壞引用。
- 文件核對：階段任務範圍與數量、故事統計及合計相符；內部連結、路徑基準、表格、code fences、checkbox 有效，正式內容沒有未填 placeholder 或不適用模板段落。

## Good Example

- 驗證範圍涵蓋圖、平行集合與任務識別，而非只掃 Markdown。

```md
T008 等待 repository 實作及契約測試；圖與文字均列出這兩項前置。
同批任務各自寫 database.test.ts、contract.test.ts、view.ts，可安全平行。
統計已依實際 12 項重算；更新時保留既有 T005 與外部引用，新增 T013。
```

## Bad Example

- 標記、前置與實際寫入對象彼此矛盾。

```md
T008 [P] 與 T009 同時修改 routes.ts，因為它們屬於不同故事。
圖示 T008 無前置，文字卻要求等待 T009；T009 又等待 T008。
清單有 12 項，統計保留範例的 22 項，更新時將所有舊 ID 重編。
```

# Rule 8 - 規劃檢查與產品完成狀態必須分別陳述

- Level: `MUST`
- 新建任務及更新時新增、重拆的工作保持未勾選；來源範例、規劃推導、未執行的測試或計畫建立的程式／紀錄，都不是實作通過的證據。
- 更新既有清單時，核對原有完成狀態及證據是否仍適用；保留有效 ID、狀態與證據。需求或契約變更使證據失效時，標明受影響任務、原因與需重驗的範圍，不一律清空，也不盲目沿用完成標記。
- 交付如實列明本輪實際完成的規劃檢查、未解決來源缺口與尚未執行的產品驗證。任務文件就緒與產品實作／驗收是不同完成訊號。

## Good Example

- 區分保留的實作證據、新工作及本次規劃成果。

```md
既有 T003 的完成證據仍符合未變更契約，保留勾選。
T007 因錯誤回覆契約調整需重驗，記錄失效原因；新增 T013 維持未完成。
本次已核對來源定位、覆蓋、相依、編號與統計；產品測試尚未執行。
```

## Bad Example

- 將規劃品質或模板外觀誤報為實作完成。

```md
清單已生成並通過 Markdown 檢查，因此所有 task 勾選完成，產品驗收通過。
更新時為保持乾淨，清空全部既有狀態與證據。
```
