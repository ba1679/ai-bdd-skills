# Rule 1 - 來源基準須對應本輪功能、版本與授權範圍

- Level: `MUST`
- 可拆解範圍必須能對應本輪確認的功能目標、包含與排除事項、既有能力及本次授權。只產生任務的授權，不延伸為實作、部署或修改產品規格的授權。
- 功能目錄、輸出文件與路徑基準須明確；相對路徑依已確認的專案根目錄或來源所述基準解讀，不把 Skill 目錄或 Example 的假想專案當成目標專案。
- 有多份版本、舊 tasks 或延續對話時，依明確的使用者決策、適用版本及修訂紀錄判定有效基準；檔案時間或名稱中的「最新」不足以單獨證明有效性。
- 已存在的登入、頁面、資料與工具只在本輪需要的接點上拆工作；既有能力不因 Example 示範而重新建置。未經查核的既有實作不能當作已通過驗收的證據。

## Good Example

- 功能、落點與既有能力均來自當前來源。

```md
本輪：在既有待辦頁新增記憶體清單篩選；不增加保存機制。
基準：使用者已確認的需求及現有 web/src/features/todos/。
輸出：專案根目錄下 specs/todo-filter/tasks.md。
既有頁面與測試工具沿用，僅安排篩選、接線及必要驗證；本輪只規劃。
```

## Bad Example

- 把範例的專案位置與責任當成本案基準。

```md
使用者要求待辦篩選，但照旅遊 Example 新增登入、PostgreSQL 與四個 API。
將任務寫入 Skill 的 templates/，完成規劃後直接實作並部署。
```

# Rule 2 - 以實際可查核內容判定充分性，不固定來源檔案組合

- Level: `MUST`
- 來源可為已確認的對話需求、規格、分析、現有程式或其他指定內容；plan、OpenAPI、DBML、UI 記錄與獨立 spec 都是適用時使用的格式，不是每案必備的五份文件。
- 充分性依任務所需的行為、介面、責任與約束是否已決定判斷。完整的純前端需求可直接拆解；缺少不適用的 API 或資料模型文件不構成阻擋。
- 引用當前可取得且實際查閱的來源。找不到的來源須保持缺失狀態，不能填上想像的章節、endpoint 或 schema 冒充已查核內容。
- `templates/tasks.example.md` 的假路徑只示範寫法，不需要尋找或補建實體 reference；此例外僅適用範例。真實產物的來源仍須可查核，不能因 Example 用假路徑就免除查核。

## Good Example

- 同一份確認需求即可提供完整行為契約。

```md
來源：本輪已確認需求「只看未完成」段落。
其中已定義預設關閉、切換條件、空結果、取消還原、原清單不變、
重新整理重設及可及性。來源充分，直接拆前端與驗證任務。
本案無 API／資料庫工作，不要求補齊 OpenAPI 或 DBML。
```

## Bad Example

- 把來源形式當門檻，或以假文件補足門檻。

```md
沒有 spec.md、plan.md、api.openapi.yaml、data-model.dbml、ui-plan.md，停止規劃。
或者先引用不存在的 analysis/api.openapi.yaml 的 getTodoFilter，視為來源已備齊。
```

# Rule 3 - 區分給定、推導、查核與不可自決的資訊

- Level: `MUST`
- **Prompt 已給定**：本輪目標、來源與輸出位置、工作範圍及明示限制可直接採用；遇到語意衝突仍須釐清適用版本。
- **來源已定**：實際來源明載的故事、驗收條件、介面、資料約束、權限及恢復行為，轉成任務時保留其語意。
- **可推導**：在既定產品決策下，從責任與既有落點推導所需工作、接線、驗證及前置產出；推導須能說明依據，不能改變已定行為。
- **需查核**：來源位置、章節、操作、型別、欄位、既有能力與前置產出的建立者，要依當前內容確認；名稱看似合理不代表存在或適用。
- **不可自決**：欠缺的角色權限、服務邊界、保存範圍、資料生命週期、流程及 API 政策，若會改變使用者承諾、系統責任或驗收結果，須取得有效決策。
- 分類以該項資訊的實際性質為準，不必在產物機械新增五類欄位；來源已明定的 API 或保存政策不再視為待問事項。

## Good Example

- 推導只把已定契約轉成工作。

```md
Prompt：只產生 tasks.md。
已定來源：新增項目由 server 產生 UUID，成功回完整清單。
可推導：安排服務驗證、資料操作、client 套用清單及相關驗證。
需查核：指定 routes 及 DTO 是否存在、清單回覆位於哪個來源區段。
不可自決：若來源未定保存及同步政策，不能自行加入跨裝置同步。
```

## Bad Example

- 以「技術推導」替產品做決定。

```md
需求只說會員收藏景點，因此可推導成雲端同步、永久保存、支援分享。
API 名稱先寫 POST /favorites；之後實作時再確認契約，現在視為已定。
```

# Rule 4 - 衝突依有效決策收斂，產品來源由原主責維護

- Level: `MUST`
- 同一行為有衝突時，保留衝突來源及定位、各自內容與受影響任務；追查對應範圍的有效決策，不以任意選檔、混合兩版或較容易實作作為裁決。
- 後續明確確認可以取代先前決策，但須能指出其適用對象；沒有可確認的取代關係時，保持受影響範圍待決並提出最小問題或交回原分析主責。
- 任務規劃只反映已確認的決策；發現 spec、API 或資料契約需修訂時，交接差異與影響，由原規格／分析流程修正。不能為使 tasks 看似一致而自行回寫產品來源。

## Good Example

- 已確認的取代關係可直接沿用，未確認衝突則保留。

```md
舊 plan 說本機保存；後續確認明定本輪改為登入後跨裝置同步，適用同一功能。
以後續確認為基準，將舊 plan 的保存段落交回分析主責修訂。
若無此確認，列出兩段位置並詢問本輪採哪個保存範圍；其餘無關任務可續拆。
```

## Bad Example

- 任務規劃擅自裁決並改寫契約。

```md
spec 寫刪除成功回 204，API 寫 200 完整清單。
因為前端處理 200 較方便，直接改 spec，並聲稱來源一致。
```

# Rule 5 - 只有會改變責任或驗收的未定事項才阻擋相關範圍

- Level: `MUST`
- 缺口須描述缺少哪項決策及其實際影響，至少辨識：角色與權限、服務邊界、保存範圍與生命週期、操作流程與恢復、未定 API 輸入／輸出／錯誤政策。僅列「規格不足」無法作為阻擋判斷。
- 已有來源可解決的問題先由來源收斂。資訊充分時直接作業，不因缺少正式文件或慣用格式重問已確認事項。
- 仍未定且會改變責任、落點或驗收時，最小問題聚焦能解除阻擋的決策；可交回原主責時，交接缺口、相關來源、受影響工作與需要的決策，不把所有分析問題丟回使用者。
- 未受影響的工作可繼續，但須區分已確認與待決範圍。局部任務或缺口交接不得標示為完整可直接實作的清單。

## Good Example

- 一個關鍵決策即可切開收藏功能的責任分支。

```md
缺口：尚未確認收藏的保存範圍；本機與跨裝置會改變身分、服務與資料責任。
最小問題：本輪收藏只保存在目前瀏覽器，還是登入後可跨裝置同步？
待決期間保留保存、API 與資料工作；已確認且不依賴該決策的文案可整理。
目前狀態：局部規劃，尚未達完整可實作。
```

## Bad Example

- 任意選擇責任分支，或不分影響就停止一切工作。

```md
先選 localStorage，會員及同步之後再說，輸出完整可實作清單。
或者因收藏保存未定，連另一個已確認、無保存責任的篩選功能也完全不拆。
```

# Rule 6 - 區分缺失契約與計畫中由前置任務建立的產物

- Level: `MUST`
- **應有來源缺失**：生成任務時就必須決定、卻沒有有效來源的產品行為或介面政策，依影響保留缺口；不能把「先設計 API」列為普通前置任務就視為契約已充分。
- **前置任務產物**：依已定契約實作的程式、fixture、操作說明及驗收紀錄，可以尚未存在；須標出建立任務、預期落點與後續使用者的依賴，執行到使用任務時再讀取實際產出。
- **既有成果**：來源聲稱已存在、後續任務又依賴的介面或程式，須查核是否可用；不存在時判斷是能依既定契約補建的實作，還是連契約也缺失，不一律歸成待建立檔案。
- 計畫中的產物不得作為當前已完成或驗收通過的證據。前置任務可建立已定決策的實作，不能藉此補造未確認產品政策。

## Good Example

- 尚未產生的驗收紀錄有建立者，未定契約則另行保留。

```md
T002 將建立 docs/development.md；T022 依賴 T002 並核對其實際指令。
T012 將建立 docs/validation/day-items.md；目前檔案未存在不構成契約缺口。
若 API 成功回覆尚未決定，服務接線任務保持待決，不以 T003「自行訂回覆」解除阻擋。
```

## Bad Example

- 混淆產物是否存在與產品決策是否成立。

```md
驗收紀錄還沒產生，所以不能規劃任何驗證工作。
API 沒有回覆契約也沒關係，先加一個設計任務，後續接線視為已知且可直接實作。
T012 預計會通過，因此 T022 現在已可勾選完成。
```

# Rule 7 - 更新既有清單須保留仍有效的識別、狀態與證據

- Level: `MUST`
- 更新前須將既有任務、ID、勾選與完成證據對照新範圍及有效來源；同一工作仍適用時保留其 ID 與可查證狀態，避免破壞既有引用及執行紀錄。
- 新增或重拆工作使用不衝突的新 ID 並維持未完成；既有未使用編號可以跳過，不以新建清單的連續編號偏好整檔重編。
- 需求、契約或責任變更使原證據不足時，指出受影響 ID、失效原因及需重驗範圍；受影響工作恢復未完成或明示需重驗，不沿用不再成立的勾選。未受影響且證據有效的工作保留。
- 已排除或被取代的工作須留下可辨識的變更說明，不能讓其舊證據繼續表示當前需求已完成。只有實際有效的證據能支撐完成狀態，模板不能要求清空全部紀錄。

## Good Example

- 更新保存可沿用的紀錄，只撤回受影響的完成宣告。

```md
T008 已完成的輸入驗證與證據仍適用，保留 ID 及勾選。
T009 因成功回覆由 204 改為 200 清單而需重驗，取消其完成狀態，註明契約變更。
新增 UI 恢復工作使用未占用的 T023，保持未勾選；既有 T001～T022 不整檔重編。
```

## Bad Example

- 套模板時破壞追溯，或未檢查就沿用完成狀態。

```md
為使所有編號連續，把原任務重排重編並清空每個 checkbox 與證據。
或者 API 回覆已變更，仍因舊任務勾選而宣稱目前接線完成，不標示重驗。
```
