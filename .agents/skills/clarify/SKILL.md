# 需求澄清

本專案的 `clarify` 衍生自 GitHub Spec Kit 的 clarify 命令樣板。完整上游內容保存在 [官方流程](references/spec-kit-clarify.md)，原始 MIT 授權與著作權聲明保存在 [LICENSE](LICENSE)。分類掃描、問題排序、逐題問答及答案整合沿用官方流程；輸入、環境與規格格式依「專案執行對應」，澄清範圍、預算計數與停止時機依「澄清邊界與提問預算」。

# SOP

## Phase 1 -- 確認澄清對象

1. READ 讀取目前需求、已確認決策、待澄清事項與本輪澄清狀態，辨識原呼叫流程；若已提供規格路徑，讀取該檔案，確認本輪只處理指定目標。
2. READ 讀取 `references/spec-kit-clarify.md`，依下方「專案執行對應」與「澄清邊界與提問預算」確認處理模式、剩餘額度與停止狀態，完成適用的前置檢查。

## Phase 2 -- 收斂缺口並保存答案

1. THINK 依已讀官方流程完成缺口分類與候選問題排序，在剩餘額度內選擇問題，篩除已回答、低影響與超出本次範圍的項目。
2. WRITE 依已讀流程與本輪預算逐題問答、更新澄清狀態；使用所選模式保存每個已接受答案，並修正答案影響的需求或規格內容。

## Phase 3 -- 驗證並交回原流程

1. READ 依已讀官方流程完成寫入後檢查、既有清單複核及適用的後置檢查，確認仍待處理的缺口；有未解決的高影響事項時，維持待確認狀態。
2. WRITE 回報本輪已問、已答與剩餘題數、停止原因、已確認決策、實際更新位置及剩餘缺口，連同澄清狀態交回原呼叫流程；由 Specify 轉交時回到 Specify 完成規格，需求模式須明示本輪尚未寫入規格檔。

## 專案執行對應

以下項目取代官方流程中對應的環境假設；掃描分類、問題呈現、逐答整合與檢查保持適用，提問額度與停止邊界依下一節執行。

| 官方項目 | 本專案對應 |
| --- | --- |
| `$ARGUMENTS`、`{ARGS}` | 目前對話或 Specify 傳入的原始需求、已確認決策、待澄清點及明確規格路徑。原對話中已確認的內容可直接沿用。 |
| `FEATURE_SPEC`、`FEATURE_DIR`、`{SCRIPT}` | 已提供且可讀取的規格路徑優先，規格目錄即其父目錄，無須再執行路徑偵測。未指定目標且專案存在 `.specify/scripts/bash/check-prerequisites.sh` 時，才依官方方式執行一次以定位；偵測失敗時說明原因並詢問目標路徑。 |
| 尚未有規格檔或 `.specify/` | 若只有需求 Prompt，以需求模式在本輪工作狀態中逐答整理「已確認需求、問答紀錄、待確認事項」，交回原流程供後續寫入。若使用者要求修改某個規格但該檔不存在或無法讀取，先詢問正確位置。 |
| 官方逐答存檔與最終回寫 | 規格模式每接受一個答案就更新同一份檔案；需求模式每接受一個答案就更新工作狀態，交回時完整列出已確認結果。資料與規則僅採已提供或已確認內容。 |
| `/memory/constitution.md` | 僅在專案已有 `.specify/memory/constitution.md` 時讀取。 |
| `.specify/extensions.yml` 與品質清單 | 檔案存在才依官方規則處理，沒有相依檔案時跳過；本 skill 的使用不要求初始化整套 Spec Kit。 |
| `Clarifications`、`Session`、`Q / A` | 沿用目標檔案既有語言與格式；使用本專案繁中樣板時，對應「需求澄清」「澄清紀錄 YYYY-MM-DD」「問／答」，日期採使用者時區。 |
| FR、NFR、驗收條件及其他規格章節 | 在需求主要歸屬 US 的既有分組內修改，其他 US 引用同一 ID；全域需求留在原全域分組。保留 ID、既有階層及無關內容，新增澄清紀錄時使用既有樣板的對應標題。 |
| 官方問題、建議、選項及完成報告的語言 | 使用繁體中文，保留完整問句、影響說明、建議選項、選項表格或短答格式，以及官方逐題問答限制。 |
| `__SPECKIT_COMMAND_SPECIFY__`、`__SPECKIT_COMMAND_PLAN__`、`__SPECKIT_COMMAND_CLARIFY__` | 分別對應原本的規格撰寫流程、由使用者決定的後續規劃，以及本專案 `$clarify`。完成後先交回原呼叫流程，不自動啟動規劃或其他 Skill。 |

## 澄清邊界與提問預算

### 何時需要澄清

- 先查閱本輪輸入、既有規格與已接受答案；只有仍無法確認、且會改變角色權限、資料含義、流程狀態、業務規則、範圍或驗收結果的缺口，才向使用者提問。
- 純實作方式、技術選型比較與任務拆解交給後續規劃；只有其缺口直接影響需求正確性或驗收時才在此確認。低影響細節可明列假設。
- 釐清的是目前需求，新增獨立能力或擴大範圍須先列為候選，不能假設使用者已同意。目標檔案無法定位時，可先確認要處理的規格。

### 額度與計數

- 同一個功能需求的這次規格撰寫或更新任務，共用一份 clarification budget，沿用官方的 **最多 5 題**；使用者指定更少題數時採較小值。
- 每次提出一個新的獨立問題就先扣除一題，尚未收到答案也算已問；每次只問一題，一題只處理一項決策，不能把多項決策包成一題規避額度。
- 使用者的回答不清楚時，同一題最多補問一次，不另扣新題，但須記錄補問次數；補問後仍無法確認就保留為未解缺口。若補問需要另一項獨立決策，改算新題並檢查剩餘額度。
- 提問時顯示「第幾題／本輪上限」，同題補問須標明。額度歸零後不再提出新題；最後一題仍可等待答案、進行允許的同題補問並整合結果。
- 本輪工作狀態保留：處理目標、題數上限、已問問題、已接受答案、待回答題目、各題補問次數、剩餘題數、未解缺口與停止原因。已問數按獨立問題計算，補問次數分開保存。
- 跨對話訊息、Specify 與 Clarify 交接、Phase 4 重驗或同一任務的恢復，均沿用這份狀態。重新呼叫 skill、修改檔案或日期改變，都不重置額度；每題只能使用一次的補問額度也不重置。
- 只有使用者明確要求新一輪澄清，或開始另一項獨立需求任務時，才建立新預算。這份提問預算與 Specify 的自動修正輪次分開計算。

### 何時停止並交回

- 沒有值得提問的關鍵缺口，或必要決策已收斂時，直接交回，不為用完額度繼續提問。
- 使用者表示停止或先交付時，立即停止提問；記錄原因，同一任務返回時維持停止狀態，直到使用者明確要求繼續。
- 題數用盡且沒有待回答題目時，停止本輪提問；保留額度內已確認的結果與剩餘缺口，不能透過再次交接繼續取得額度。
- 仍有會改變需求或驗收的未解事項時，規格保持待確認草稿，列出缺口與影響後交回原流程；不以猜測補齊關鍵決策，也不宣稱已可進入規劃。
