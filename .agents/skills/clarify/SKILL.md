# 需求澄清

本專案的 `clarify` 衍生自 GitHub Spec Kit 的 clarify 命令樣板。完整上游內容保存在 [官方流程](references/spec-kit-clarify.md)，原始 MIT 授權與著作權聲明保存在 [LICENSE](LICENSE)。分類掃描、問題排序、單題呈現格式及答案整合沿用官方流程；輸入、環境與規格格式依「專案執行對應」，提問方式、澄清範圍、預算計數與停止時機依「澄清邊界與提問預算」。

# SOP

## Phase 1 -- 確認澄清對象

1. READ 讀取目前需求、已確認決策、待澄清事項與本輪澄清狀態，辨識原呼叫流程；若已提供規格路徑，讀取該檔案，確認本輪只處理指定目標。
2. READ 讀取 `references/spec-kit-clarify.md`，依下方「專案執行對應」與「澄清邊界與提問預算」確認處理模式、剩餘額度與停止狀態，完成適用的前置檢查。
3. READ 讀取目標 repo 的 `constitution/README.md` 和適用的 `constitution/shared/rules.md`。依[憲法套用約定](../constitution/SKILL.md#憲法套用約定)，寫回規格時讀 `constitution/spec/rules.md`，複核需求清單時讀 `constitution/requirements-checklist/rules.md`。需求模式沿用交接提供的適用規則，裁決規格或清單的覆寫時沿用規格主責公布的項目。

## Phase 2 -- 收斂缺口並保存答案

1. THINK 依已讀官方流程完成缺口分類與候選問題排序，在剩餘額度內選擇問題，篩除已回答、低影響與超出本次範圍的項目。
2. WRITE 依「問題呈現與回答處理」一次列出剩餘額度內所有目前能形成的有效問題；收到回覆後，保存每個已接受答案並修正其影響的需求或規格內容，更新澄清狀態。重新評估剩餘缺口，需要補問時依同一規則集中提出，直到符合停止條件。

## Phase 3 -- 驗證並交回原流程

1. READ 依已讀官方流程完成寫入後檢查、既有清單複核及適用的後置檢查，確認仍待處理的缺口；有未解決的高影響事項時，維持待確認狀態。核對本輪變動涉及的憲法規則與證據。
2. WRITE 回報本輪已問、已答與剩餘題數、停止原因、已確認決策、實際更新位置、適用憲法的檢查結果及剩餘缺口，連同澄清狀態交回原呼叫流程。由 Specify 轉交時回到 Specify 完成規格。需求模式須明示本輪未寫入規格檔。

## 專案執行對應

以下項目取代官方流程中對應的環境假設與互動規則；掃描分類、單題呈現格式、逐答整合與檢查保持適用，提問方式、額度與停止邊界依下一節執行。

| 官方項目 | 本專案對應 |
| --- | --- |
| `$ARGUMENTS`、`{ARGS}` | 目前對話或原呼叫流程傳入的需求、已確認決策、待澄清點及適用的規則來源或規格路徑。原對話中已確認的內容可直接沿用。 |
| `FEATURE_SPEC`、`FEATURE_DIR`、`{SCRIPT}` | 需求模式直接沿用本輪工作狀態。規格模式中，已提供且可讀取的規格路徑優先，規格目錄即其父目錄，無須再執行路徑偵測。未指定目標且專案存在 `.specify/scripts/bash/check-prerequisites.sh` 時，才依官方方式執行一次以定位；偵測失敗時說明原因並詢問目標路徑。 |
| 需求模式 | 呼叫者指定需求模式時直接採用。若只有需求 Prompt，也以需求模式在本輪工作狀態中逐答整理「已確認需求、問答紀錄、待確認事項」，交回原流程供後續寫入。若使用者要求修改某個規格但該檔不存在或無法讀取，先詢問正確位置。 |
| 官方逐答存檔與最終回寫 | 規格模式每接受一個答案就更新同一份檔案；需求模式每接受一個答案就更新工作狀態，交回時完整列出已確認結果。資料與規則僅採已提供或已確認內容。 |
| `/memory/constitution.md` | 有模組化憲法時依 Phase 1 載入。僅在專案尚未導入模組化憲法且已有 `.specify/memory/constitution.md` 時沿用舊路徑。 |
| `.specify/extensions.yml` 與品質清單 | 檔案存在才依官方規則處理，沒有相依檔案時跳過；本 skill 的使用不要求初始化整套 Spec Kit。 |
| `Clarifications`、`Session`、`Q / A` | 沿用目標檔案既有語言與格式；使用本專案繁中樣板時，對應「需求澄清」「澄清紀錄 YYYY-MM-DD」「問／答」，日期採使用者時區。 |
| FR、NFR、驗收條件及其他規格章節 | 在需求主要歸屬 US 的既有分組內修改，其他 US 引用同一 ID；全域需求留在原全域分組。保留 ID、既有階層及無關內容，新增澄清紀錄時使用既有樣板的對應標題。 |
| 官方問題、建議、選項及完成報告的語言 | 預設使用繁體中文。適用的交付文字依 `artifact-language` 解析，並保留每題的完整問句、影響說明、建議選項、選項表格或短答格式。 |
| 官方步驟 4–5 的逐題呈現、隱藏候選問題及同題消歧後才前進 | 由下一節「問題呈現與回答處理」取代，包含 `Do NOT output them all at once`、`Present EXACTLY ONE question at a time`、`Never reveal future queued questions in advance` 與 `do not advance`。答案逐項驗證及整合仍適用，一題未解不妨礙整合其他已確認答案。 |
| `__SPECKIT_COMMAND_SPECIFY__`、`__SPECKIT_COMMAND_PLAN__`、`__SPECKIT_COMMAND_CLARIFY__` | 分別對應原本的規格撰寫流程、由使用者決定的後續規劃，以及本專案 `$clarify`。完成後先交回原呼叫流程，不自動啟動規劃或其他 Skill。 |

## 澄清邊界與提問預算

### 何時需要澄清

- 先查閱本輪輸入、既有規格與已接受答案；只有仍無法確認、且會改變角色權限、資料含義、流程狀態、業務規則、範圍或驗收結果的缺口，才向使用者提問。
- 純實作方式、技術選型比較與任務拆解交給後續規劃；只有其缺口直接影響需求正確性或驗收時才在此確認。低影響細節可明列假設。
- 釐清的是目前需求，新增獨立能力或擴大範圍須先列為候選，不能假設使用者已同意。目標檔案無法定位時，可先確認要處理的規格。

### 額度與計數

- 整個需求任務（包含尚無規格檔的需求澄清、規格撰寫或更新）共用一份 clarification budget，**最多 5 題**；使用者指定更少題數時採較小值。
- 每次列出問題時，按新增的獨立問題數扣除額度，尚未收到答案也算已問；例如一次列出 3 題即使用 3 題額度。一題只處理一項決策，不能把多項決策包成一題規避額度。
- 使用者的回答不清楚時，同一題最多補問一次，不另扣新題，但須記錄補問次數；補問後仍無法確認就保留為未解缺口。若補問需要另一項獨立決策，改算新題並檢查剩餘額度。
- 每題使用整個需求任務內固定且唯一的 Q1、Q2 等題號，提問時顯示「本次任務已問 X／上限 Y 題」（含本次列出的新題），同題補問沿用題號並標明。額度歸零後不再提出新題；已問題目仍可等待答案、進行允許的同題補問並整合結果。
- 本輪工作狀態保留：處理目標、題數上限、已問問題、已接受答案、待回答題目、各題補問次數、剩餘題數、未解缺口與停止原因。已問數按獨立問題計算，補問次數分開保存。
- 跨對話訊息、Specify 與 Clarify 交接、Phase 4 重驗或同一任務的恢復，均沿用這份狀態。重新呼叫 skill、修改檔案或日期改變，都不重置額度；每題只能使用一次的補問額度也不重置。
- 只有使用者明確要求新一輪澄清，或開始另一項獨立需求任務時，才建立新預算。這份提問預算與 Specify 的自動修正輪次分開計算。

### 問題呈現與回答處理

- 完成分類掃描、去重與優先排序後，一次列出剩餘額度內所有目前能形成的有效問題；候選題超過額度時，依官方的影響程度 × 不確定性選出優先題，其餘列為未解缺口並說明影響，不以問句要求額外回答。有效問題不足額度時照實列出。
- 能事先表達的相依條件隨題標示，例如「僅在 Q1 選 A 時回答 Q2」；條件題提出時仍計入額度，之後不適用則標記並保留已問計數。必須取得前題答案才能形成的問題先記錄為待確認缺口，取得答案後再依剩餘額度處理。
- 使用者可依題號一次回答全部或部分問題，也可用自由文字、跳過或標記待定。將回覆對應到各題；僅在指涉明確時，才將「同意建議」套用至對應題目。
- 逐項驗證並保存已明確接受的答案，沿用逐答整合與寫入後檢查；未答、跳過、待定或有歧義的題目保留狀態，不推定接受建議，也不阻擋其他答案整合。跳過或待定不自動觸發追問；部分作答時等待其餘待答題目，不重複整份問題清單。
- 整合回覆後重新檢查候選問題及相依條件，移除已解決或失效的候選題。必要的同題消歧集中補問；新浮現或現在才能形成的獨立問題，仍在剩餘額度內一次列出，不刻意分批或逐題揭露。

### 何時停止並交回

- 沒有值得提問的關鍵缺口，或必要決策已收斂時，直接交回，不為用完額度繼續提問。
- 使用者表示停止或先交付時，立即停止提問；記錄原因，同一任務返回時維持停止狀態，直到使用者明確要求繼續。
- 題數用盡且沒有待回答題目時，停止本輪提問；保留額度內已確認的結果與剩餘缺口，不能透過再次交接繼續取得額度。
- 仍有會改變需求或驗收的未解事項時，規格保持待確認草稿，列出缺口與影響後交回原流程；不以猜測補齊關鍵決策，也不宣稱已可進入規劃。
