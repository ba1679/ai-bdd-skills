# Rule 1 - 研究問題必須回到需求、約束或未解限制

- Level: `MUST`
- 每項研究都要能說明它支持哪個規劃決策，以及該決策來自哪個需求、既有約束或未解限制。已明確選定的技術視為研究條件；只有出現具體不相容證據時，才說明衝突並提出調整建議。
- 依本次需求及相依關係檢視下列切入點，只展開會改變本次規劃的問題；不以範例的題目或項數當成必填清單：
  - **責任邊界與資料流**：應用、共用契約與平台各自負責什麼；瀏覽器能存取什麼；狀態、快取與表單的 owner 是否衝突。
  - **版本與環境**：runtime、工具鏈、SDK、driver、作業系統與瀏覽器的支援範圍能否組合使用。
  - **身分與授權**：登入與業務角色如何區分；綁定、降權、撤銷及 session／快取切換如何反映權限變化。
  - **資料與計算正確性**：交易、一致性、冪等、並行修改、版本／snapshot、日期與精度、外部副作用的責任邊界。
  - **外部整合與文件**：API／連線模式、逾時、重試、背景工作、檔案存取、文件生成及失敗後的回復條件。
  - **部署與維運條件**：local／CI／cloud 差異、地域、連線池、休眠、還原、保存期限、成本與服務限額。
  - **有需求才展開的交付限制**：公開 demo 的資料隔離、重設與清理；領域或法規規則；品牌、語系、裝置與學習要求。沒有對應需求時不為湊齊題目加入。
- 優先處理會使方案無法成立、影響授權或資料正確性、牽動多項決策的問題，再處理局部工具偏好。缺口須能具體說明影響；低影響細節可明列假設，不重新詢問已確認的決策。

## Good Example

- 問題由已確認條件與正確性需求導出，研究範圍可辨識。

```md
已確認：採用關聯式資料庫；敏感命令需在交易內讀取最新授權後再更新資料。
研究問題：候選 driver／連線模式是否支援同一交易內的互動讀寫？
規劃影響：決定資料存取邊界及交易使用方式；不重新選擇資料庫類型。
```

## Bad Example

- 以範例項數取代需求分析，並重新打開已定案的選型。

```md
範例有 14 項，所以這個只需比較兩項工具的小專案也必須填滿 14 項。
使用者已決定採關聯式資料庫，但先重新詢問要不要改用另一種資料庫。
```

# Rule 2 - 證據必須可追溯到適用的來源與時間

- Level: `MUST`
- 技術主張以實際讀取的官方文件、發布紀錄、官方 registry metadata 或原始碼支持；領域與法規問題使用對應主管機關或第一手來源。引用放在支持的主張附近，連到實際支持該主張的頁面或版本。
- 版本、支援範圍、費用、配額、地域與服務行為需交代查核日期及適用條件。版本結論優先引用固定版本的 metadata、文件或 commit；`latest`、可變文件與歷史摘要本身不足以證明某個歷史版本的內容。
- 明確區分官方事實、使用者已確認約束、專案自行設定的政策及研究者推論。來源說明能力或限制，推論則說明它如何影響本案；不得將自行設定的限額或保存策略稱為官方預設。
- 重用既有研究時保留原基線的日期與語意；只把本輪實際重查的部分標為新證據。現有專案的實際版本與設定以可讀取的 manifests、lockfile、設定或驗證紀錄判斷，不由舊研究推定現況。
- 來源無法存取、互相矛盾或不適用目前版本時，交代缺口及其影響；可繼續提出有條件的建議，但不能捏造來源、查核結果或把推論寫成已證實事實。

## Good Example

- 歷史基線與本案推論分別呈現，沒有宣稱重新查核。

```md
此配額沿用原研究日期的供應商資料，本輪尚未重新查核。
依據：原研究附有當時來源與適用方案。
本案推論：該配額不足以證明長期保存與成本可行，正式導入前須重查現行條件並估算用量。
```

## Bad Example

- 用可變入口與舊內容宣稱今天的查核結果。

```md
直接複製舊範例的版本與配額，把研究日期改成今天。
來源只貼 registry 的 latest 入口，因此所有歷史版本與目前費用都已確認。
```

# Rule 3 - 版本選型必須檢查組合相容性

- Level: `MUST`
- 涉及套件或平台版本選型時，針對實際依賴逐項核對 engines、peerDependencies、官方支援範圍，以及相關 runtime、編譯器、lint、SDK、driver、plugin 與型別套件的交集；不是每個套件個別可安裝就代表整組可用。
- 依使用者要求及執行環境區分 stable、LTS、Current、preview 等版本條件。若「最新」與工具支援範圍衝突，說明受影響的元件、衝突條件與選擇理由，避免默默換版或擴大升級範圍。
- 納入實際相關的作業系統、瀏覽器引擎、ESM／CommonJS、TypeScript 及部署環境限制。型別與 runtime 的能力應對應；開發機可用也不直接推定 CI 與部署環境可用。
- 版本表只列本次研究確實涉及的依賴，並對應查核時間及用途。把安裝、編譯、測試或特定環境驗證仍需確認的部分留給後續驗證，不以 metadata 交集宣稱實測通過。

## Good Example

- 假設查核後得到下列支援範圍，選擇建立在整組工具的交集上。

```md
工具 A 支援編譯器 major 4–5，候選編譯器最新 stable 為 major 6。
本案需要工具 A，且未要求編譯器必須採最新 major，因此建議採受支援的 major 5。
理由附上雙方適用版本的官方支援依據；實際安裝與編譯仍待驗證。
```

## Bad Example

- 忽略互相依賴的支援範圍，並混淆文件查核與實測。

```md
工具 A 與編譯器各自都有最新版，所以都選 latest。
registry 可讀取這兩個套件，因此整個專案已通過相容性測試。
```

# Rule 4 - 決策必須說清楚機制、成立條件與替代方案代價

- Level: `MUST`
- 決策說明採用什麼、解決哪個需求、在何種條件下成立；理由連接來源證據與本案限制。替代方案比較實際可行選項及排除原因，不虛構無人考慮的方案，也不只寫「較簡單」或「最佳實務」。
- 使用者已指定方案時，研究該方案的可行條件、整合邊界與代價；其他方案可作為取捨背景，不把原本已確認的選擇寫成研究者重新決定。
- 資料正確性與安全主張需指出機制覆蓋的邊界：身分驗證是否等於業務授權、撤銷何時生效、snapshot 是否能防止過期寫入、資料庫交易是否涵蓋外部檔案或服務，以及失敗與重試後會留下什麼狀態。
- 按實際相依關係交叉檢查決策：前端 SDK 與瀏覽器存取邊界、driver 交易能力與業務命令、連線池模式與 session 狀態、HTTP 逾時與背景工作、日期／金額表示與儲存，以及免費額度與保存／還原需求。跨項衝突須一併修正或明示限制。
- 保持足以支持規劃的深度；資料表細節、任務拆解與程式實作只在它們是決策成立的必要依據時提及，不藉研究新增未要求的架構或政策。

## Good Example

- 區分兩種系統各自能保證的範圍，且替代方案有具體代價。

```md
決策：資料庫交易只提交文件工作狀態，外部檔案生成採可重試工作處理。
理由：資料庫的 commit 不涵蓋外部儲存；失敗後須能辨識未完成文件並重試。
替代方案：同步生成可減少工作狀態，但需確認請求逾時及部分成功的回復方式。
```

## Bad Example

- 將跨服務的一致性問題壓成沒有成立條件的結論。

```md
選用支援 transaction 的資料庫，所以資料列、PDF 與外部儲存天然全部原子完成。
替代方案：其他方式都比較複雜。
```

# Rule 5 - 未解事項必須區分決策缺口、證據缺口與實作驗證

- Level: `MUST`
- 在相關研究及結論中區分下列狀態，不需為它們新增固定章節：
  - **待使用者決策**：答案會改變研究範圍、需求或方案取捨，且現有上下文無法推定；提出聚焦問題，並說明哪些結論因此仍是條件式建議。
  - **研究證據不足**：尚無可支持技術主張的適用來源，或來源衝突尚未解決；明列缺少什麼及影響，不能以查核日期、來源數量或待測試標籤掩蓋。
  - **留待實作驗證**：已有選型依據，但需安裝、整合、量測或演練才能驗證；記錄相關研究 ID、環境／條件、觀察對象與通過依據。沒有需求依據的數值不可自行補成驗收門檻。
- 會讓後續規劃無法成立的缺口必須明示為阻塞；允許後續以明列條件規劃的風險，則說明仍需驗證的範圍，避免一律要求先完成所有實作或雲端操作才能交付研究。
- 官方 metadata、文件宣稱、本機測試與雲端測試是不同證據。local／CI 的結果不能自動涵蓋雲端 IAM、連線池、休眠、跨區延遲、保留政策或還原能力；文件寫明支援也不等於本案已驗證。
- 「待驗證」記錄要確認的條件與結果；實際安裝、CI 通過、任務完成與部署結果由對應驗證或交付紀錄承接，不回填成這份規劃前研究的完成進度。

## Good Example

- 分開處理需要人決定的邊界，以及可留待實作量測的風險。

```md
決策缺口：使用者尚未決定是否開放匿名寫入，demo 的授權與資料隔離方案因此仍待確認。
待驗證事項（R03）：供應商文件支持候選連線模式；仍需在候選地域驗證冷連線、逾時與還原流程。
驗證依據：量測結果對照專案已定義的延遲要求；若要求尚未提供，明列門檻待確認，不自行填入數值。
```

## Bad Example

- 把決策缺口藏成測試事項，並把來源能力誤寫成本案完成證據。

```md
是否允許匿名寫入不必確認，實作時測試一下就好。
供應商文件提到備份，因此本案的還原測試與雲端部署都已通過。
```

# Rule 6 - 交付與更新須保持研究問題、證據及引用一致

- Level: `MUST`
- 每個已收斂的研究問題須有對應決策或明示未解原因；結論不得把條件式建議改寫成已證實可行。數量依實際問題展開，不能靠湊題或刪掉難題宣稱完成。
- 研究項目、相鄰理由與文末待驗證事項的 ID 引用須對得上；仍有效的既有 ID 保持穩定。修訂一項選型時，同步檢查依賴它的其他研究、版本表、結論及待驗證事項，移除矛盾內容。
- 新研究以實際查核日期記錄；局部更新則標明更新部分的日期與適用來源，保留未重查部分的歷史基線。維持「官方事實、專案政策、推論與實測限制」的區分。
- 產物結構依已載入模板，清除填位與填寫提示，確認相對連結符合實際輸出位置；不存在或未讀取的輸入與後續產物不能寫成已存在的證據。
- 交付時反映實際完成程度：能修正的引用或內容問題直接修正，仍缺來源或使用者決策時明示限制；不以格式完整替代證據完整。

## Good Example

- 保留研究 ID 並修正所有受影響的推論，更新範圍可追溯。

```md
R02 的版本選型已於本輪重查並更新；其他項目保留原查核日期。
同步檢查 R04 的 driver 支援範圍及結論中的相容性限制。
仍缺實際整合證據，因此文末保留引用 R02／R04 的驗證事項。
```

## Bad Example

- 只改局部版本與整份文件日期，留下互相矛盾的建議。

```md
更新版本表後，把整份研究改成今天已重新驗證。
依賴該版本的其他決策不需檢查，舊 ID 全部重新編號，文末引用維持原樣。
```
