# Rule 1 - 總覽必須涵蓋本次計畫採用的完整技術組合

- Level: `MUST`
- 彙整範圍是本次計畫實際會使用的主要語言、runtime、框架、直接依賴、服務及開發／驗證工具，包含沿用、新增與替換後採用的項目；依計畫範圍決定粒度，不擴成整份 lockfile 的間接依賴清單。
- 原研究與已確認的專案基線共同決定採用範圍。既有技術若尚無可引用的研究項目，先在研究文件補足來源清楚的沿用基線，標明它是既有約束，無須假裝重新比較所有替代方案。
- 被替換的舊技術與僅供比較的替代方案，不列為計畫同時採用的技術；只有計畫明確需要共存或過渡時才保留，並由研究說明條件。
- 局部研究或版本更新後仍須保留本次計畫中其他有效的採用項目。既有總覽可作盤點索引，選擇與版本仍須回到研究及適用的專案來源確認。

## Good Example

- 本輪新增資料庫 driver 研究，總覽仍呈現計畫會使用的完整組合。

```md
沿用：既有語言、前端框架與身分服務，來源已記錄於研究基線。
新增／替換：新資料庫與 driver，引用本輪的選型研究。
總覽保留上述全部採用項目；被取代的舊資料庫只在研究保留比較或過渡說明。
```

## Bad Example

- 把本輪研究增量誤當成完整技術棧，並混入未採用方案。

```md
這次只研究了 driver，因此總覽只剩 driver。
所有比較過的資料庫都放進採用欄，讓讀者自行判斷實際使用哪一個。
```

# Rule 2 - 分類、版本與待定內容必須忠實反映研究

- Level: `MUST`
- 正文依已載入模板呈現分類選用總覽與待定事項。分類依本次技術組合增減，相關項目歸入適合的領域；共用技術可歸入共用分類，同一責任項目不因跨層使用就重複列管。Example 的分類數量、名稱與項目數不是必填清單。
- 採用技術、版本、方案及配置均由研究彙整，不在總覽獨立重新拍板。來源只確定 major、版本政策或服務選擇時，就保留該精度；版本或配置未定時明列待定，不補出未查核的 patch 或參數。
- 總覽沿用已讀骨架的欄位，維持已確認的精簡格式；詳細用途、責任邊界、比較理由與證據時效由研究文件承接。
- 待定事項只彙整仍影響技術選用、版本、方案或配置的內容，區分已確定基線與未定部分；沒有待定事項時填「無」。不把整份實作驗證清單、任務進度或部署完成紀錄搬入總覽。

## Good Example

- 服務已確定，但地域仍在評估，兩種狀態清楚分開。

```md
採用技術：研究已決定使用的代管資料庫服務。
待定事項：候選地域與連線配置，引用同一研究項目的未定條件。
小型本機計畫依實際需要只分「執行環境」與「品質工具」，不補出雲端分類。
```

## Bad Example

- 從範例複製分類與版本，或把未定值寫成已確定採用。

```md
不論計畫內容，都照填六個分類及範例中的全部版本。
研究尚未選定地域，但總覽自行填入某地域並標成最終配置。
```

# Rule 3 - 研究依據必須可跳轉且與雙產物更新一致

- Level: `MUST`
- 每筆採用或待定條目，以行內超連結引用支持它的研究 ID；多筆依據各自連結。以實際輸出檔案的相對位置及研究標題形成路徑與章節錨點，不能只貼純文字 ID，也不能在正式輸出沿用範例檔名。
- 研究章節必須已存在，連結標示的 ID 必須符合目標章節，內容也要支持該列技術、版本或未定條件。沒有支持內容時，回到研究補足來源或明列缺口，不捏造研究 ID。
- 更新研究選型、版本、標題或 ID 後，同步檢查總覽的採用項目、待定內容與所有受影響連結；研究標題變更即使 ID 不變，也可能需要更新錨點。
- 兩份文件有衝突時，先核對原始來源並修正研究，再更新總覽。只改總覽會形成第二套決策；只改研究則留下失真的採用快照。

## Good Example

- 依實際目錄連結到正式研究，且局部更新後重新核對標題。

```md
同目錄交付：總覽中的研究連結指向實際 research.md 的對應章節。
不同目錄交付：從總覽位置計算研究的相對路徑。
研究標題更新：保留原 ID，重新核對總覽各處的章節錨點與版本內容。
```

## Bad Example

- 正式總覽留下範例連結，或將來源更新視為不影響摘要。

```md
正式 techstack.md 的所有引用都仍連到 research.example.md。
研究已改版、章節也已改名，但總覽沿用舊版本與舊錨點。
```
