# Rule 1 - 依使用者成果判斷 US 的拆分與合併

- Level: `SHOULD`
- 每個 US 應聚焦一項使用者能辨識的成果，說明誰在什麼條件下完成什麼目標，以及如何判定完成。
- 同一成果需要多個角色協作時，可以放在同一故事；角色、頁面、資料表或 CRUD 動作的數量不決定故事數量。
- 兩部分若有不同成果、優先級或驗收邊界，應考慮拆分；只有合起來才形成可用成果的步驟，應考慮合併。
- 獨立驗證可使用其他流程已產生的合成資料作為前提，應能驗證該故事的成果，而非要求完整重做所有前置故事。

## Good Example

- 依兩種成果拆分，跨角色的請假流程仍保有完整驗收邊界。

```md
已確認需求：行政登錄請假，由負責人核准或退回；員工查閱已發布薪資。
US-001：行政完成請假登錄及負責人確認，結果可供後續作業使用。
獨立驗證：建立合成員工，完成送出、退回修正與核准。
US-002：員工查閱自己的已發布薪資。
獨立驗證：準備已發布與未發布的合成薪資，驗證可見範圍。
```

## Bad Example

- 只有角色分類，無法辨識成果或判斷故事是否完成。

```md
US-001：負責人功能。
US-002：行政畫面。
US-003：一般員工資料表。
```

# Rule 2 - 以來源與必要性界定需求範圍

- Level: `MUST`
- 需求依據可來自本次輸入、適用的既有規格、已接受的澄清答案，或已查證且適用的外部依據；範例中的個別政策僅在本次也有依據時採用。
- 推導出的必要條件須能說明它支持哪項已確認成果，以及缺少它會造成什麼具體失敗。若會新增獨立能力、角色責任或服務範圍，須列為候選需求並取得確認。
- 外部規則須確認適用對象、版本或生效期間及來源；外部制度提供的可選方案，仍須依使用者已確認的選擇決定。
- 會改變權限、狀態、計算或驗收的未知事項，交回主 SOP 的澄清步驟；可明列的低影響假設須可辨識且不冒充已確認決策。

## Good Example

- 區分已知需求、必要條件與仍需確認的範圍。

```md
已確認：員工只能查看自己的已發布薪資。
必要條件：每次查閱核對員工身分與資料歸屬，避免讀到他人薪資。
待確認：薪資由系統計算，還是匯入既有結果；此選擇會改變功能範圍。
候選需求：銀行匯款，尚無本次需求依據，未列為必做功能。
```

## Bad Example

- 將展示案例與一般經驗直接升格為本次已確認需求。

```md
輸入只要求行政登錄請假與員工查看薪資。
因為範例使用 Google 登入，所以本次也必須綁定 Google。
因為完整人資系統通常要計薪，所以加入保費試算、銀行匯款與公開 demo。
```

# Rule 3 - 沿故事的操作與資料變化展開適用規則

- Level: `MUST`
- 對每個故事檢視下列面向，保留影響其成果的具體規則；不適用面向可略過，清單本身不構成新增功能的依據。
- **角色與資料範圍**：誰可執行、查看或修改，作用於本人、指定對象或整體資料，越權時的可見結果。
- **輸入與識別**：必要資料、身分或唯一來源、欄位範圍、單位、空值及重複來源如何辨識。
- **狀態與生命週期**：初始與完成狀態、轉換條件、執行角色、退回或撤回、更正與歷史結果的關係。
- **計算與時間**：計算基準、公式或判斷順序、精度與取整、生效日、跨期間歸屬，以及預計、確認與實際發生的區別。
- **失敗與恢復**：缺資料、無適用規則、重複操作、重疊或並行異動、過期版本、取消或重試，及其對已保存資料的影響。
- **實體與來源**：核心業務資料的身分、關聯及必要歷史；依賴的外部資料、版本與不可用時的處理。

## Good Example

- 同一故事具體交代資料、狀態、規則及失敗時的效果。

```md
已確認：行政送出請假後，由負責人核准；同一員工的請假時段不得重疊。
輸入：員工、假別、起訖時段；以穩定員工識別碼關聯資料。
狀態：送出後為待審核，只有負責人可改為已核准或退回。
檢核：送出時重新檢查時段重疊；重疊時列出原因並保留可修正輸入。
資料效果：送出失敗不建立新的生效請假；核准與退回結果各自可辨識。
尚未確認的扣薪公式列為缺口，不自行以固定日薪計算。
```

## Bad Example

- 雖列出功能名稱，仍缺少足以實作與驗收的業務語意。

```md
支援請假 CRUD、審核及計薪。
做好權限、日期、例外處理與資料一致性。
```

# Rule 4 - 需求條目應有可分辨的驗證邊界

- Level: `SHOULD`
- 一條需求應聚焦一項可辨識的行為、規則或品質主張；可獨立變更、由不同故事負責或需不同驗收方式的主張，應考慮拆開。
- 同一規則必要的前提、公式、例外與結果可共同描述，避免拆到失去完整意義。
- FR、NFR 的分類依已讀樣板處理，具體業務條件保留在條目中。

## Good Example

- 每項有可辨識的檢核方式，同一規則的條件與效果仍放在一起。

```md
FR-001：建立請假時必須提供員工與有效起訖時段，無效輸入須指出欄位。
FR-002：待審核請假修改時段後須重新送審，先前審核結果不沿用。
```

## Bad Example

- 將欄位驗證、審核規則與畫面風格綁成同一條，難以分別變更與驗收。

```md
FR-001：可以請假、審核、算薪資，介面使用品牌色且反應快速。
```

# Rule 5 - 共享需求依主要責任判斷歸屬並追蹤影響

- Level: `MUST`
- 需求歸屬與引用格式沿用已讀樣板；判斷主要歸屬時，辨識哪個 US 負責建立或維護該能力，哪些 US 只是使用其結果。
- 無單一故事能承擔的跨流程共同規則，才作為全域候選，並說明其涵蓋的操作與不可歸屬單一故事的原因。
- 修改共享規則時，回查引用者的資料前提、操作及驗收結果；保留未受影響的需求與既有 ID，重新分類時保留來源對照。

## Good Example

- 能辨識主要責任、引用關係與變更的傳遞範圍。

```md
帳號綁定由「管理員工與角色」US 定義，員工查薪資 US 引用該需求。
跨主檔、請假、審核與下載的操作稽核，另說明其跨流程責任後列為全域需求。
變更帳號綁定規則後，回查員工登入與薪資查閱的驗收條件是否仍成立。
```

## Bad Example

- 依引用數量決定全域歸屬，且修改時忽略受影響流程。

```md
帳號綁定被兩個 US 使用，所以直接移到全域需求。
兩個 US 各保留一份需求全文，變更時只更新其中一份。
```

# Rule 6 - 全文以業務讀者與可觀察成果為主

- Level: `MUST`
- 使用者故事、FR、NFR、實體、邊界情境、SC 與假設，均須讓需求相關人理解角色需要什麼、為何需要，以及如何判定結果；必要領域術語在首次出現時交代含義。
- 以使用者動作、業務規則、可見輸出、資料意義與品質條件描述需求；未被指定的框架、程式分層、資料表結構或內部機制，留給後續規劃。
- 本次輸入或適用的既有依據明確指定技術限制時，保留其內容與來源，放在補充輸入或適用限制的位置；功能行為與 SC 仍須能說明可驗證的需求成果。
- 開發者本身是使用者時，API、CLI、檔案格式或協定可屬於對外需求；描述其契約與可觀察結果，依據其用途判斷，不能只因出現技術名詞就刪除。
- 審閱時區分已指定限制與自行選定的實作方式；後者應改寫為其支持的需求成果，必要技術決策交給後續規劃。

## Good Example

- 保留明確限制，同時讓需求與成果可由行為驗證。

```md
補充輸入：使用者指定資料庫採 PostgreSQL，技術配置交由後續規劃。
FR-001：員工可依年月查閱本人已發布薪資，未發布或他人資料不可取得。
SC-001：以已知員工及發布狀態核對查閱結果，允許與拒絕案例皆符合 FR-001。
開發者介面需求：匯出指令遇到無權限資料時回報拒絕原因，且不輸出該資料。
```

## Bad Example

- 未經指定便選定內部實作，也沒有交代使用者成果。

```md
使用者只要求員工查薪資。
FR-001：用指定前端框架、三張資料表和快取層完成查詢。
SC-001：資料表與快取建立完成。
```
