# Rule 1 - 驗收情境必須能觀察並判定通過或失敗

- Level: `MUST`
- Given 提供會影響結果的角色、資料或狀態；When 指定可執行的動作；Then 描述可核對的輸出、狀態、資料效果或拒絕結果。
- 涉及計算時，提供已知輸入及可核對的預期結果；涉及權限、發布或審核時，明確區分允許及拒絕條件。
- 「操作正常」「符合需求」「容易使用」等無可判定依據的文字，須改為具體結果。驗收描述以使用者可觀察的行為與業務結果為主。

## Good Example

- 資料狀態與可見範圍足以直接判定結果。

```md
Given 員工 A 有一張已發布及一張未發布薪資單，員工 B 另有已發布薪資單，
When 員工 A 查詢薪資列表，
Then 只顯示 A 的已發布薪資單，未發布及 B 的資料均不可取得。
```

## Bad Example

- 缺少測試前提與可核對結果。

```md
Given 使用者已登入，When 點薪資，Then 系統正常顯示。
```

# Rule 2 - 依會改變結果的風險選擇失敗與邊界情境

- Level: `MUST`
- 每個故事須覆蓋主要成功結果，並針對已推導規則中會改變結果的失敗或邊界補上驗收。
- **輸入邊界**：已定義的空值、零值、上下限、精度及無效資料。
- **權限與狀態**：無權限、非本人、未核准或未發布、已取消或已失效等適用條件。
- **時間與計算**：生效前後、跨期間、部分量、取整與資料缺漏等會影響結果的分支。
- **重複與異動**：重送、重疊、舊版本、取消、更正或外部依賴失敗等已納入需求的風險。
- 失敗情境須說明應提示什麼，以及哪些資料或狀態應保留或不生效。不適用項目可略過，既有相同案例可引用，不為湊數建立新功能或窮舉無關組合。

## Good Example

- 從已確認規則選擇會改變判斷結果的邊界。

```md
已確認：預約時長接受 1–120 分鐘，無效輸入不建立預約並保留輸入供修正。
成功：1 分鐘與 120 分鐘均可建立。
拒絕：0 分鐘與 121 分鐘顯示時長範圍錯誤，未增加預約資料。
保留：失敗後仍可看到原輸入並修改。
```

## Bad Example

- 只測一般值，沒有覆蓋規則的通過與拒絕邊界。

```md
預約 60 分鐘可以成功，所以時長限制驗收完成。
```

# Rule 3 - NFR 須具備適用條件、品質判準及驗證依據

- Level: `MUST`
- 每項 NFR 須能說明品質對象、適用條件、通過判準與驗證方式。數值型目標須寫明單位、資料或負載條件，以及適用的量測起訖、統計方式或期間。
- 時間、容量、正確率及可用率等門檻，採使用者提供或已確認的目標，或經查證且適用的依據；測試資料的選取不得冒充已確認的產品容量或服務保證。
- 非數值限制可用明確的通過條件、對照清單或可審閱證據驗證，無須硬造數字。
- 若缺少的目標會影響設計、範圍或驗收，列為待確認並交回主 SOP；無獨立品質要求時依樣板處理，不套用通用數值填滿欄位。

## Good Example

- 以下條件是本案例已確認目標，量測範圍及證據明確。

```md
已確認：在指定參考環境、1,000 筆合成單據下，連續 100 次查詢的 P95 不超過 2 秒。
NFR-001：從送出查詢至結果完整可見量測耗時，保留該環境、資料量及 100 次量測紀錄，核對 P95。
另一項已確認限制：金額加減項不能僅靠顏色區分；以移除顏色後仍有名稱或符號可辨識的畫面檢查驗證。
```

## Bad Example

- 以一般經驗編造門檻，且缺乏量測條件。

```md
使用者只要求「查詢要快」。
NFR-001：為了商用品質，回應必須小於 100 毫秒，可用率為 99.999%。
```

# Rule 4 - 成功標準須衡量需求成果並與 NFR 保持一致

- Level: `MUST`
- SC 須描述使用者或業務達成的可量測成果，包含適用條件、通過門檻及核對方法，避免只列畫面、功能數量或技術選擇。
- NFR 用於約束服務或操作的品質，SC 用於判定整體成果；若共用同一指標，以 SC ID 連結同一標準，條件與門檻須一致。
- 正確性可由明確預期值、允許與拒絕案例或一致性關係量測；缺少時間目標時，可使用已有需求支持的成果指標，無須自行新增完成時間。
- 具體需求與 SC 均有依據時，才將其作為完成判準；待確認目標須清楚標示。

## Good Example

- 使用已確認的業務成果作為標準，品質要求引用同一條件與門檻。

```md
已確認目標：20 名員工、資料已核對時，行政在 10 分鐘內完成薪資試算、檢查與提交。
SC-001：以該條件演練，記錄行政從開始操作到成功提交的時間，須不超過 10 分鐘。
NFR-001：月結操作品質依 SC-001 的條件與門檻驗收。
```

## Bad Example

- 技術清單未說明使用者成果，且兩處品質門檻互相矛盾。

```md
SC-001：做完五個畫面，使用指定資料庫。
SC-002：相同條件下，行政應於 10 分鐘內完成月結。
NFR-001：相同條件下，月結操作只需達到 30 分鐘內完成。
```

# Rule 5 - 以需求追溯與跨章節一致性判斷規格是否完成

- Level: `MUST`
- 每項明確要求須能對應到規格內容，或有已確認的排除原因；新增主張須有需求依據。此對照可在工作狀態中完成，無須另產製一份追溯文件。
- 逐一核對整份規格唯一定義的 FR，包含全域 FR 與跨 US 引用的主要定義；每條 FR 中會改變結果的行為與條件，均須有具體可定位的驗收情境，包含適用的允許、拒絕與邊界結果。
- 驗收依據可用「US ID／驗收第幾條」或具備前提、動作與預期結果的邊界驗收案例定位，單純重述規則不足以作為驗收依據；同一情境可支持多條 FR，同一 FR 也可由多個情境共同覆蓋。故事已有主要成功情境，不等於故事內所有 FR 都已驗收覆蓋。
- FR 與驗收的逐條對照可保留在工作狀態；缺少依據時，品質檢查紀錄須列出 FR ID、所在 US 或全域位置，以及缺少的條件或預期結果，無須強制新增完整追溯矩陣。
- 驗收前提、FR 行為、NFR 限制、實體狀態、邊界處理與 SC，須對同一角色、資料、版本及期間給出相容結果。
- 更新共享需求或接受澄清答案後，回查受影響的故事、引用及驗收，替換失效敘述，而非保留互斥版本。
- 格式、ID 與引用結構依已讀樣板核對；來源對照與現行需求定義須能區分。仍有會改變成果的未解決決策時，維持待確認狀態。

## Good Example

- 同一政策在需求、驗收及成功標準中一致生效。

```md
確認答案：員工只可查閱已發布薪資。
FR：已核准但尚未發布的薪資對員工不可見。
驗收：員工查詢尚未發布的薪資時不可取得內容。
SC：發布與本人存取案例依上述允許及拒絕結果核對。
既有「核准後立即可見」的驗收敘述已同步更正。
FR-001 的覆蓋定位：US-001 驗收第 1 條驗證本人已發布可見，
第 2 條驗證本人未發布不可見，第 3 條驗證他人資料不可見。
```

## Bad Example

- 僅增加澄清紀錄，仍保留互斥的行為與驗收。

```md
澄清紀錄：員工只可查閱已發布薪資。
FR：尚未發布的薪資不可見。
既有驗收：薪資一經核准，員工立即可見。
狀態：已完成，因為澄清問題已回答。
FR-001 的拒絕條件尚無情境，卻只因 US-001 有一條成功情境便宣稱全部 FR 已覆蓋。
```
