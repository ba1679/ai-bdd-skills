# Rule 1 - 品質清單須完整檢查現行規格

- Level: `MUST`
- 以實際規格檔的父目錄作為功能目錄，品質清單須與同一份規格對應。新清單依已讀樣板建立；既有清單保留自訂檢查、原建立日期與無關內容，缺少的必要檢查項才補入。
- 保留樣板的「內容品質」「需求完整性」「規劃就緒」三組檢查，逐項套用已載入的需求推導、驗收及品質規則，並核對規格樣板要求的章節、ID、引用與填位清理。
- 核取項目只有在本次確實檢查並通過時才標為 `[x]`；未通過或尚未檢查者保持 `[ ]`。某面向不適用時，記錄確認依據後才可標為已通過適用性檢查。
- 品質檢查驗證規格能否支持規劃與驗收，不宣稱尚未實作的產品已達到 SC。測試可執行性與產品測試實際通過須可區分。
- 清單須檢查完整需求覆蓋，包含每條 FR 的驗收依據與既有的 NFR、SC、一致性及來源要求；不能只檢查標題與 Markdown 格式。

## Good Example

- 同時檢查內容與格式，並記錄適用性。

```md
- [x] 必填章節已完成，選填章節依適用性處理。
- [ ] 每條 FR 的行為與適用條件均有可定位的驗收依據。
定位：全域 FR-003 的非本人拒絕條件尚無驗收情境。
NFR：本功能無獨立品質目標，已核對需求來源與適用性。
目前驗證的是規格完整性，產品驗收尚待實作後執行。
```

## Bad Example

- 只依章節存在便宣稱內容通過。

```md
所有標題與 FR 編號都有出現，因此全部核取通過。
沒有找到 NFR，就自行補一個通用效能數字讓清單通過。
規格的 SC 寫好了，所以產品已通過所有成功標準。
```

# Rule 2 - 檢查紀錄須可定位問題並呈現狀態變化

- Level: `MUST`
- 新清單複製骨架結構並替換填位；更新既有清單時，保留原核取項文字及順序，僅切換狀態確實改變的標記。缺少的必要項追加至適用分組，避免整份重建而遺失自訂項。
- 計數與狀態比較只採 code fence 以外的 Markdown 核取行，接受 `[ ]`、`[x]`、`[X]` 與前置縮排；未變動的標記保留原樣。
- 每次初驗、修正後重驗或澄清後重驗，依樣板新增一個具使用者時區時間的批次紀錄，最新批次在前。保留之前批次作為當時快照，當前項目狀態以核取方塊為準。
- 紀錄當次通過數、全部核取項數、已用修正輪次及 FR 覆蓋數；FR 分母為全份規格唯一定義的 FR 數，跨 US 引用不重複計數。只有適用行為與條件均具驗收依據的 FR 才計為已覆蓋。
- 檢查依據須能定位至規格章節、需求 ID 或驗收情境；通過證據可按檢查主題合併，未通過項逐項列出位置、具體缺口及下一步。沒有剩餘問題時填「無」。
- 有前次基準時列出新增通過、退步與仍未通過的項目；「仍未通過」指前後皆未通過，全部當次失敗另列於當次問題。初驗無前次基準時明示此事，不虛構變化。

## Good Example

- 通過數與缺口可核對，也能看出退步。

```md
修正後重驗：15/16 項通過，FR 覆蓋 2/3，已用自動修正 1 輪。
退步：逐條 FR 驗收覆蓋。
定位：新加入的 FR-003（US-001）缺少非本人讀取的拒絕情境。
新增通過：需求來源已補齊。
仍未通過：無。
當次問題：FR-003 驗收缺口，下一步補充適用拒絕情境後重驗。
```

## Bad Example

- 摘要沒有定位，或更新時覆蓋掉既有內容。

```md
檢查結果：大致正常，可能要補一些例外。
把既有清單全部改成新樣板，自訂檢查與上一輪失敗紀錄一併消失。
```

# Rule 3 - 每輪任務最多自動修正並重驗三輪

- Level: `MUST`
- 同一輪任務針對同一規格，初驗的已用自動修正輪次為 0；一次依缺口修改規格並完成整份清單重驗，計為一輪，最多三輪。
- 每輪集中修正已知且不需要新決策的問題；記錄更新或純檢查本身不消耗修正輪次。原始需求更新、初稿撰寫及使用者答案整合也不冒充自動修正輪次。
- 初稿寫入後，為處理檢查缺口而改動規格均屬自動修正，不因回到其他 Phase 就重新歸為初稿；沒有新增需求的同輪恢復任務，從現行規格接續重驗。
- 第三輪後仍有失敗項時，停止自動修正，保存規格及品質清單的當前狀態，依剩餘問題判定就緒狀態並交付具體原因。
- 同一任務的澄清往返、重新交接或重試均沿用已用計數；使用者提出新任務時才建立新一輪預算。

## Good Example

- 已用預算在流程往返後仍持續有效。

```md
初驗：未通過，已用 0 輪。
兩輪自動修正後：仍有缺口，已用 2 輪。
clarify 整合一個已接受答案後重驗：仍沿用已用 2 輪。
再自動修正一輪後：已用 3 輪；仍有問題便保存並交付，不再自動修第四輪。
```

## Bad Example

- 以流程往返重置預算，形成沒有上限的迴圈。

```md
第三輪仍失敗，所以回到 clarify 再回來，把已用輪次設回 0。
因為還有失敗項，就繼續自動修正直到全部通過。
```

# Rule 4 - 澄清往返須保留狀態並重新檢查受影響結果

- Level: `MUST`
- 缺口需要使用者決策時，交回主 SOP 的澄清步驟，附上規格路徑、品質缺口、已用修正紀錄與本輪澄清狀態；提問額度及停止邊界以 clarify 為準。
- 等待答案期間保持待確認狀態；澄清停止而關鍵決策仍未解時，交付已知內容及待確認草稿，不以猜測讓檢查通過。
- 提問數與停止條件由 clarify 負責，自動修正輪次由本驗證規則負責；往返不重置任一計數。使用者答案整合後仍須重新檢查完整清單，包含先前已通過項目的退步。
- clarify 已能複核清單並切換核取標記；回到 specify 後，以實際更新的規格與清單作為基準，補記本次重驗證據、剩餘問題與就緒結果。

## Good Example

- 答案整合後回查原先通過的驗收。

```md
使用者確認：未發布資料不可見。
clarify 已整合答案並將一致性檢查退回未通過。
specify 返回後發現舊驗收仍寫「核准立即可見」，在剩餘修正預算內更正並重驗。
若提問上限已達且另一項關鍵決策仍未解，交付待澄清草稿。
```

## Bad Example

- 只看問題已回答，或把重新交接當成額外提問額度。

```md
澄清已回答，所以沿用先前全部通過的結果，不檢查舊驗收。
clarify 的提問已達上限，再重新呼叫一次以取得新的提問額度。
```

# Rule 5 - 就緒狀態須由目前缺口與檢查結果判定

- Level: `MUST`
- 依下列順序選定一個就緒狀態：
  - **待澄清**：仍有影響範圍、角色權限、流程狀態、業務規則或驗收結果的未解決決策；同時列出其他品質問題。
  - **品質未通過**：沒有上述關鍵未決事項，但仍有未通過或未完成的檢查。
  - **可進入規劃**：關鍵決策已解決、所有檢查均完成並通過，且 FR 驗收覆蓋完整。
- 延後的純實作選擇可列入後續規劃；會改變本次需求或驗收的決策仍屬待澄清，不能只改標為「延後」。
- 就緒判定與規格的草稿狀態分開解讀；可進入規劃代表規格已可供規劃，不代表產品已完成或通過實際驗收。
- 交付須包含實際規格及品質清單路徑、主要內容、檢查通過數、FR 覆蓋數、已用自動修正輪次、就緒狀態及理由、剩餘問題與後續處理。清單或規格未成功保存時，明示實際失敗位置與原因，不宣稱完整交付。
- 所有摘要須根據最終重驗結果產生；交回原需求流程，不自動啟動規劃。

## Good Example

- 三種結果有明確不同的成立條件。

```md
16/16 項通過、FR 3/3 覆蓋、無關鍵未決事項：可進入規劃，規格仍可標為草稿。
15/16 項通過、FR 2/3 覆蓋、規則已確認但缺驗收：品質未通過，列出缺少情境。
15/16 項通過、尚未決定誰能核准：待澄清，同時列出其他未通過項。
```

## Bad Example

- 因為已達上限或寫完檔案便直接宣稱就緒。

```md
雖然第三輪還缺 FR 驗收，但已用完預算，所以標成可進入規劃。
規格已保存，因此未決權限問題留給實作者自行選擇。
```
